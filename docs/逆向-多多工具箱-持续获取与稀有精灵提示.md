> 目标：还原 `多多工具箱 4.2` 中「持续获取模式」和「稀有精灵提示」的真实实现，并给出在「洛克工具箱」落地的可行性分析与技术实现方案。

## 0. 结论摘要

| 问题 | 结论 | 置信度 |
| --- | --- | --- |
| 持续获取模式怎么实现 | 外部 PCAPdroid 负责 VPN 抓包 → 本机 TCP/HTTP 接收成 `*.pcap` → 每 2.5 s 读取文件增量 → 增量解析 TCP/TGCP/AES → 聚合器实时落盘 → 结果页实时刷新 | 高（代码路径完整） |
| 为什么能"边玩边抓" | 抓包和解析是两个进程/两条线程：PCAPdroid 持续写，工具箱持续读；前台保活服务 + 画中画保证进程不被杀 | 高（前台服务调用可见；保活插件内部为推断） |

## 2. 持续获取模式

### 2.1 一句话版本

> 用 PCAPdroid 持续抓 `com.tencent.nrc` 的 TCP 流量，把 PCAP 流落到本机文件；工具箱每 2.5 秒只读"新增的那一段"，增量喂给常驻解析器，解析结果一有变化就写进结果存储，所以不需要点"停止"。

### 2.2 数据流

```
┌──────────────┐  VPN 抓包（app_filter=com.tencent.nrc）
│  PCAPdroid   │──────────────────────────────┐
│ (独立 APK)   │                              │
└──────────────┘                              ▼
        │ ① CaptureCtrl Intent start      ┌─────────────────────┐
        │   tcp_exporter → 127.0.0.1:1234 │ 本机 TCP 接收/落盘   │
        └────────────────────────────────▶│ duoduoKeepcaptive    │
                                          │ (UTS 前台保活服务)   │
                                          └──────────┬──────────┘
                                                     │ 写 _downloads/roco_live_<ts>.pcap
                                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│ PcapManager（utils/pcap.js）                                     │
│  每 2500 ms：readLocalFileBytes(整文件) → 只取 [liveOffset, EOF) │
│  → liveParser.feed(delta)（PCAP 记录 → IP/TCP）                  │
│  → liveSession.processTcpPacket（TCP 重组 → TGCP 帧 → AES 解密）  │
│  → 事件（pet.snapshot / box.snapshot / egg.inventory / nearby…）  │
│  → liveAgg（聚合器）→ flushLiveResult() → result_store + 回调     │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 启动链路（观察）

`PcapManager.startCapture()`（对应 `utils/pcap.js` 约 400 行起）做了 6 件事：

1. **重置状态**：清空 `EXPORT_JSON`、`PARSED_*` 等本地键。
2. **设置实时文件路径**：`_downloads/roco_live_<Date.now()>.pcap`，通过 `setLivePcapPathByJs(path)` 告知保活插件。
3. **启动前台保活服务**：`startKeepCaptureServiceByJs()`。
4. **拉起 PCAPdroid**：`sendCaptureCtrl("start", 1002)`。
5. **启动流监控**：`startStreamMonitor()`。
6. **启动轮询**：`startLivePoll()`（2500 ms）。

`sendCaptureCtrl` 的 Intent 参数（关键证据）：

```js
s.setClassName("com.emanuelef.remote_capture",
               "com.emanuelef.remote_capture.activities.CaptureCtrl");
s.putExtra("action", "start");
s.putExtra("pcap_dump_mode", "tcp_exporter");
s.putExtra("collector_ip_address", "127.0.0.1");
s.putExtra("collector_port", 1234);
s.putExtra("app_filter", "com.tencent.nrc");
s.putExtra("dump_extensions", true);
s.putExtra("full_payload", true);
s.putExtra("ip_mode", "both");
s.putExtra("snaplen", "262144");
```

即：PCAPdroid 只抓目标游戏，把 PCAP 通过 TCP 导出到本机 1234 端口，载荷完整、snaplen 256 KB。

同时还有一条 **HTTP 备用链路**：`http://127.0.0.1:4567/pcap`（失败回退 `8080`），由 `plus.downloader` 持续下载到同一个 `liveFileName`。这条链路主要用于兼容 PCAPdroid 的 Web 接口/旧版本。

### 2.4 保活与前后台（观察 + 推断）

- **前台服务**：`FOREGROUND_SERVICE_*` 权限 + `startKeepCaptureServiceByJs()`，保证接收 socket 不被系统回收。
- **画中画**：`onAppHide()` → `enterKeepPip()`；`onAppShow()` → `exitKeepPip()`。目的是让 WebView 进程在切到游戏时仍存活。
- **推断**：UTS 插件 `duoduoKeepcaptive` 暴露了 `receiverRunning / receiverPath / serverSockets / handleStreamByJs` 等代理字段，合理实现是「`ServerSocket(1234)` 接收 PCAPdroid 的 TCP 流，顺序写入 `receiverPath`」。dex/so 未反编译，这一层只能算强推断。

### 2.5 增量读取（观察）

```js
startLivePoll(e, t) {
  this.livePollTimer = setInterval(() => { this.livePoll(e, t); }, 2500);
}

async processLiveDelta(e, t) {
  const bytes = await this.readLocalFileBytes(this.liveFileName);
  if (bytes.length < this.liveOffset) this.initLiveParser();   // 文件被截断/重建
  else if (bytes.length <= this.liveOffset) return;            // 没有新增
  const delta = bytes.subarray(this.liveOffset);
  this.liveOffset = bytes.length;
  this.liveParser.feed(delta);                                 // 只解析新增段
  this.liveSession && (this.stats.keyCaptured = ...);
  this._syncLiveCounts();
  this.liveMode && this.flushLiveResult();                     // 持续模式实时落盘
  ...
}
```

要点：
- **每次读整文件，但只解析 `liveOffset` 之后的新增字节**；内存峰值取决于文件大小，CPU 只消耗在增量上。
- 文件变短 → 认为会话重建，重置解析器。
- 轮询固定 2.5 s，不做文件监听（避免 Android 文件监听兼容性问题）。

### 2.6 解析链（观察）

三层状态机，全部常驻：

1. **PCAP 层** `Ti.feed()`：识别大小端/微秒纳秒（magic `0xa1b2c3d4` 等）、linkType，逐条记录切包。
2. **TCP 层** `Ei.feed(seq, payload)`：按序号重组，缓存乱序段，返回连续字节。
3. **TGCP 帧层** `Ii.feed()`：
   - 跳过 6 字节零填充；找帧同步头 `0x33 0x66`；
   - `kind = bytes[6..7]`，`headerLength = u32BE(13)`，`bodyLength = u32BE(17)`；
   - 帧总长 = `headerLength + bodyLength`，上限 16 MiB。
4. **解密层** `Ai.processFrame()`：
   - `kind == 0x1002`（`"1002"`）且方向为 s2c → **会话密钥帧**：取 `raw[23..39]` 的 16 字节作为 AES-128 key；
   - `kind == 0x4013`（`"4013"`）→ 业务帧：
     - 若 `len >= 32 && (len-16) % 16 == 0`：前 16 字节是 IV，剩余是密文（`embedded`）；
     - 否则若 `len % 16 == 0`：零 IV（`fixed`）；
     - `AES-128-CBC` 解密后校验 `plaintext[4] == 0x55 && plaintext[5] == 0xAA`；
     - **opcode**：s2c 取 `plaintext[2..3]`，c2s 取 `plaintext[6..7]`（大端 u16）。
   - 密钥错误会在 s2c 帧上做一次校验，校验失败即清空 key 重新等 `0x1002`。

> 这一段和洛克工具箱 `core.js` 里已有的 `aesKey = frame.slice(23,39)`、`kind 16/2`、`kind 64/19`、`resolveFramePayload` 完全同构——说明两边的协议基线一致。

### 2.7 实时落盘（观察）

```js
flushLiveResult() {
  const revision = this.liveAgg.revision;
  if (revision === this._lastLiveRevision) return false;   // 没变化就不写
  const data = this.liveAgg.build();
  this._applyPlacementsToBoxes(data, ...);
  const counts = this.getResultCounts();
  this.exportJson = JSON.stringify(data);
  resultStore.set(this.exportJson, counts, false);         // 写结果存储
  this.onLiveUpdate({ counts, at: Date.now(), liveMode: true, ... });
  return true;
}
```

- **只有聚合器 revision 变化才写**，避免每 2.5 s 重复序列化。
- 结果页订阅 `onLiveUpdate`，新抓到的精灵、放生的精灵、数量变化实时更新。
- 普通模式不做这步：普通模式只在"停止"时构建导出 JSON。

### 2.8 完成判定与通知（观察）

`isCollectionComplete()` 需要同时满足：

- 已拿到会话密钥；
- 有角色信息；
- 精灵盒子数 > 0；
- 见过蛋仓（`eggsSeen`）；
- 见过炫彩色卡（`handbooksSeen`）；
- 且 `coverage().complete_enough` 为真，或任一 TCP flow 的 `petSyncComplete` 为真。

满足后只触发一次：

- 通知 id `9527`，渠道 `roco_capture`，标题「数据收集完成 ✅」，正文包含精灵/盒子/蛋/色卡数量；
- 震动 600 ms。

### 2.9 异常兜底（观察）

| 场景 | 处理 |
| --- | --- |
| 3 s 内未连上 HTTP 源 | 中止下载任务，1.2 s 后重试 |
| 连续重试 | 端口 `4567` 失败 3 次 → 回退 `8080` |
| 多次未连上（首次从未成功） | 自动重置抓包驱动，最多 2 次 |
| 停止时文件仍有尾部 | 再读一次文件，补解析 `liveOffset` 之后的数据 |
| 文件解析结果比内存结果少 | 回退到内存聚合结果（避免"越解析越少"） |
| PCAPdroid 状态异常 | `CaptureCtrl get_status` Intent 查询（requestCode 1004），4 s 超时 |
| 进程被杀 | 停止时自动把实时文件复制到 `Download/roco_live_*.pcap` + `stop_report_*.txt` |

## 3. 稀有精灵提示

### 3.1 数据来源（观察）

`PcapManager.initLiveParser()` 对每个解析事件做分派：

```js
nearbyRuntime.handles(opcode) ? nearbyRuntime.consumeEvent(event)
: opcode === 307 ? nearbyRuntime.consumeSelfMove(event)
: opcode === 348 ? nearbyRuntime.consumeTeleport(event)
: opcode === 338 ? nearbyRuntime.consumeEnterScene(event)
```

其中：

| opcode | 用途 | 事件类型 |
| --- | --- | --- |
| `330` | 场景实体全量快照 | `nearby.entities` |
| `1043` / `1044` | 实体进出/移动增量 | `nearby.entities` |
| `307` | 自己移动（c2s） | `self.move` |
| `348` | 传送 | `scene.teleport` |
| `338` | 进场景 | `scene.enter` |

> 同一组 opcode 在洛克工具箱的 `home.js` 里被当作"家园全量场景 / 住户增量"解析。两者是否完全同构（野外是否也发 330）是本次落地的**第一验证点**。

### 3.2 实体字段（观察）

`ra()` 从实体消息中取值：

```js
// 顶层 field 11 → actor
actorId   = identity.field 1（或 actor.field 1）
level     = identity.field 11
cfgId     = petData.field 1          // 只接受 10000–19999
height    = petData.field 11
weight    = petData.field 12
mutation  = petData.field 14
voice     = petData.field 31         // dB，可正可负
uniqueId  = petData.field 17
refreshId = petData.field 10
glassType = glass.field 1
glassValue= glass.field 2
pos       = identity.field 8 → field 1 → { x: f1, y: f2, z: f3 }
```

过滤条件（`pa` / `ca`）：

- `height > 0 && weight > 0`；
- `cfgId ∈ [10000, 19999]`；
- 有 `uniqueId`；
- `|x|, |y| ∈ [100000, 2000000]`（世界坐标有效范围）。

移动增量（非 330 帧）：`token(field 1, uint64) + pos(field 3)`，用 token 绑定到已有实体；token 前 4 次投票用于识别"自己"。

### 3.3 跟踪与去重（观察）

- 去重键：`uniqueId` 优先 → `refreshId` → `cfgId + 取整后的坐标`。
- `left` 标记：330 帧里未出现的实体标记为"离开视野"；`includeLeft=false` 时列表直接跳过。
- 距离：`distanceM = hypot(dx,dy) / 100`（游戏坐标 → 米）。
- 方位：`bearing` 用八方向（`北/东北/…` + `↑↗→…`）。
- 没有精确自身坐标时，用"附近实体坐标的几何中位数"近似自身位置。
- 列表默认只显示 120 m 内；按"稀有优先、距离次之"排序。

### 3.4 稀有判定（观察）

三层：

**A. 显示用牌子 `_kinds()`**

```js
kinds = [];
(glassType !== 0 || (mutation & 8))  && kinds.push("colorful");   // 炫彩
(mutation & 1)                       && kinds.push("shiny");      // 异色
(mutation & 166)                     && kinds.push("pollution");  // 污染
weightPct >= 98 ? "big" : weightPct <= 2 ? "small" : null;        // 大块头/小不点
voice >= 96 ? "high" : voice <= -96 ? "low" : null;               // 婉转声/粗嗓门
```

**B. 体重百分位 `za()`**

```js
pct = (weightKg - low) / (high - low) * 100   // 0..100，线性夹取
```

体重上下限来自内置宠物图鉴（`A[cfgId] = [weightLow, weightHigh, heightLow, heightHigh]`，单位克/厘米）。

**C. 提醒判定 `un()`（严格版）**

```js
reasons = [];
if (voice >= 100 || voice <= -100) reasons.push("+100dB 婉转声" / "-100dB 粗嗓门");
if ((有 big|small) && (有 high|low)) reasons.push("大块头·婉转声" 等组合);
hit = reasons.length > 0;
```

注意两个阈值差：
- **牌子/列表**：`±96 dB` 就算"婉转声/粗嗓门"；
- **提醒**：`±100 dB` 才算"±100dB"；`96–99 dB` 必须再叠加体重牌（大块头/小不点）才提醒。

这正是帮助页写的「±100dB，或者同时具备体重牌 + 声音牌」。

### 3.5 提醒节流（观察）

```js
setInterval(() => { if (capturing) checkRareAlerts(); }, 1000);
```

`_n.scan(list)`：

- `_seen: Map<key, firstSeenAt>`；
- 首次命中 → 进入本次提醒队列；
- 再次命中 → 只更新时间，不重复提醒；
- 不再命中 → 从 `_seen` 删除（允许下次再提醒）；
- 已从列表消失超过 **10 min** 清理；任何条目最多保留 **30 min**。

通知：

- id `9528`，渠道 `roco_capture`；
- 标题：单只「稀有精灵出现！」/ 多只「稀有精灵 ×N」；
- 正文：最多 3 行，超出加「…另有 N 只」；
- `BigTextStyle` + 10 s 后自动 `cancel` + 震动 300 ms；
- 默认开启，开关存 `DUODUO_RARE_ALERT`。

### 3.6 UI 层（观察）

- 附近页支持 `rareOnly`（只看稀有）、`voice100Only`（只看 ±100dB）、`radar/list/map` 三种视图。
- 可选悬浮窗（`SYSTEM_ALERT_WINDOW`）：把附近列表推到游戏内小窗，默认折叠、可调透明度。
- 这些是"提示"的展示层，不影响核心判定。

## 6. 可行性分析

### 6.1 总体结论

| 功能 | 可行性 | 理由 | 主要风险 |
| --- | --- | --- | --- |
| 持续获取模式 | **高** | VPN、落盘、增量边界、解码器都在；只缺常驻会话与实时结果 | WebView 后台节流、长时间解析 CPU、128 MiB 上限 |
| 稀有精灵提示 | **中高** | 330/1043/1044 已在解码器中出现，字段结构可复用；判定规则简单 | 野外实体帧字段需真机验证；游戏协议更新；通知权限 |
| 悬浮窗/雷达 | **中** | Android 悬浮窗权限 + 现有 WebView 数据可做，但不是必需 | OEM 权限、审核与观感 |

### 6.2 关键差异（多多 vs 洛克工具箱）

| 维度 | 多多工具箱 | 洛克工具箱 | 影响 |
| --- | --- | --- | --- |
| 抓包来源 | 外部 PCAPdroid（需另装 APK） | 内置 VpnService | 我们少一个安装步骤与 Intent 兼容风险 |
| 抓包范围 | app_filter 全量 TCP/UDP | 只 TCP/8195 | 附近实体帧是否在 8195 内，需验证 |
| 解析位置 | JS（uni-app 服务层） | JS Worker（Rspack/Vite） | 同样可做常驻会话 |
| 实时性 | 2.5 s 增量 | 3 s 全量重解 | 我们要补增量，否则大文件会越来越慢 |
| 结果落盘 | 每次 revision 变化写 | 停止后导入 | 要做"实时快照 + 停止后正式导入"双轨 |
| 上限 | 未明确（PCAPdroid 侧） | 128 MiB | 长会话要早停/滚动 |
| 通知 | 完成 + 稀有提醒 | 只有采集前台通知 | 需新增通知渠道与权限处理 |

### 6.3 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 野外场景不发 330 / 字段与家园不同 | 中 | 稀有提示做不出来 | P0 先用真实野外抓包验证；不通过则降级为"抓到后提醒" |
| 游戏协议更新导致 opcode/字段漂移 | 中 | 两功能都失效 | 解码失败即 fail-closed；保留诊断计数；不伪造数据 |
| 长会话解析卡顿/发热 | 中高 | 体验差、掉帧 | 真增量；限制 live 会话只保留必要事件；关闭 rawProtocol 留存 |
| WebView 切后台被冻结 | 中 | 实时中断 | 采集本身在前台 Service；实时解析可在回到前台时 `catchUp`（与多多一致） |
| 通知权限被拒 | 中 | 提醒不可见 | 首次开启时请求；被拒时页面内提示 + 不反复弹 |
| OEM 杀后台 | 中 | 采集中断 | 前台服务 + 电池优化引导；不承诺"永远在线" |
| 合规/封号争议 | 低中 | 口碑/账号风险 | 只做被动旁路、不修改游戏、不注入；明确提示与免责声明 |

  `field10 = 等级`、`field15/42 = petId`、`field26/27 = 身高/体重`、`field47 = 血脉`、`field93 = 声音`。

- **战斗帧 4886 的单位详情里 `field7` 恒为 30，不是性格**，不要用那个结构。

  不能提前看野生性格。实现见 `core.js#parseOwnedPetDetails` + `inspectCapture` 的
  `petId + level + height + weight` 关联。

**实时刷新（2026-11-06 用户反馈）**：附近页的 live 轮询不再按文件尺寸跳过解码，每 1.5 秒重新解码一次，
并增加手动「刷新」；避免出现「文件在涨但界面不动、切页面才更新」。
自身坐标参考实现走 **opcode 307**（跳过前 14 字节，取 `field2` 的坐标，范围 100000–2000000）。
此前解码器的 `readGameFlows` / `decodeFlow` 只收集 `serverToClient` 段，**上行帧被整段丢弃**，
所以永远拿不到 307；现在 `core.js` 会同时保留 `clientSegments`，用下行握手拿到的 AES key 试解上行帧
（并保留明文兜底），把 307 的自身坐标通过 `extractPcap().nearbySelf` 一路带到 `NearbySnapshot.self`，
雷达用它做可信中心（`buildRadar` 的 `trustOrigin`，不再落回最密集精灵）。
上行帧是否与下行完全同构仍待真机验证：解析失败时 `nearbySelf` 为 null，页面自动退回估算中心并标注说明。

**2026-11-06 实测修正（capture-1793905516970）**：上行 TCP 段确实被采集到了（145 段 / 122 个数据帧），
但上行数据帧的帧头长度是 25（下行是 30），且用下行 AES key 按「零 IV」「body 前 16 字节做 IV」
「整帧 16 字节做 IV」三种组合都解不出明文。也就是说上行是另一套加密，**307 目前拿不到**，
`nearbyPets` 能进、`nearbySelf` 仍为 null，雷达中心继续是估算值。

**特殊场景精灵（2026-11-06 验证）**：蛋包蛋（petId 3808）在场上不是 10000–19999 的常规野生实体，

现在 `core.js` 保留了一个 `SPECIAL_ENTITY_CFG_IDS` 白名单（29401），`src/pcap/wildNearby.ts` 用

### 7.5 关键算法（可直接落地）

```ts
// 体重百分位：与多多一致，线性夹取 0..100
function weightPercentile(weightKg: number, lowKg: number, highKg: number) {
  if (!Number.isFinite(weightKg) || !Number.isFinite(lowKg) || !Number.isFinite(highKg) || highKg <= lowKg) return null;
  return Math.max(0, Math.min(100, (weightKg - lowKg) / (highKg - lowKg) * 100));
}

// 显示牌子
function kindsOf(pet: NearbyPet): RareKind[] {
  const kinds: RareKind[] = [];
  if (pet.glassType !== 0 || (pet.mutation & 8)) kinds.push('colorful');
  if (pet.mutation & 1) kinds.push('shiny');
  if (pet.mutation & 166) kinds.push('pollution');
  if (pet.weightPct != null) {
    if (pet.weightPct >= 98) kinds.push('big');
    else if (pet.weightPct <= 2) kinds.push('small');
  }
  if (pet.voiceDb >= 96) kinds.push('high');
  else if (pet.voiceDb <= -96) kinds.push('low');
  return kinds;
}

// 提醒判定：±100dB，或 体重牌 + 声音牌
function alertReason(pet: NearbyPet) {
  const reasons: string[] = [];
  if (pet.voiceDb >= 100) reasons.push('+100dB 婉转声');
  else if (pet.voiceDb <= -100) reasons.push('-100dB 粗嗓门');
  const body = pet.kinds.includes('big') || pet.kinds.includes('small');
  const voice = pet.kinds.includes('high') || pet.kinds.includes('low');
  if (body && voice) reasons.push(`${labelOfBody(pet)}·${labelOfVoice(pet)}`);
  return reasons.length ? reasons.join(' · ') : null;
}
```

### 7.7 需要拍板的三个点

1. **提醒范围**：只做"附近刷新提醒"（需 P0 验证通过），还是同时做"抓到后提醒"（现有数据即可，风险低）？建议两者都做，后者作为兜底。

## 9. 一句话给决策者

多多的"持续获取"本质是**把抓包与解析解耦**：PCAPdroid 持续写文件，工具箱每 2.5 秒读增量、增量解析、变化即落盘；"稀有提示"本质是**从场景实体帧里读声音/体重/异色字段，用两条硬阈值规则做本地提醒**。洛克工具箱已经具备 VPN、PCAP 落盘、快照读取和同一套协议解码器，落地不需要引入 PCAPdroid；真正的新工作是"常驻增量会话"和"附近实体模型"，其中后者必须先拿一份真实野外抓包验证。
