## 0. 结论摘要

1. **能理解。** 它不是一个"会聊天的机器人"，而是「早柚核心 gsuid_core + RocomUID 插件」的一台**游戏数据查询/推送机**：群内查图鉴/蛋/配种/家园/排行，定点推送远行商人，再通过一个 HTTP 桥把「换蛋提醒」接通工具箱网页。真正有价值、也最容易坏的是最后那条桥。
2. **最严重的问题不是某个 bug，是"没有工程底座"**：机器人代码**不在任何 git 仓库里**，没有历史、没有 diff、没有回滚；框架核心 `core.py` 还被 `codex_*.py` 脚本直接改写过去做真实发消息测试（现已还原，脚本和备份还留在目录里）。这决定了后面所有问题都只能"线上盲改"。
3. **有 4 个 P0（前 3 个正在造成用户可见损失）**：
   - 定时任务 `poll_toolbox` 没有异常兜底，**今天已抛 7 次、11-19 抛 39 次**；每抛一次，这一分钟所有群的提醒全部不发；
   - 桥接**环境混线**：`ingest`（家蛋进蛋仓）和手动巡查硬编码打**测试站**，其余打正式站；而 `ingest` 这个接口**只存在于一个没合并的分支**上 → `rc生蛋了吗` 每次都会附一句"蛋仓同步失败"或把蛋写进测试库；
   - 上游接口轮询**单次最长 5 分钟**、`生蛋了吗` 对全部 UID 并发查、且**任意 6 位以上 UID 都能查别人**，没有频控——一条命令就能把共享 key 的额度烧掉、把事件循环占住。
4. **朋友改不了你的机器人代码。** 机器人代码既不在 GitHub 上、也不在网页仓库里；你朋友是 fork + PR 模式，公开事件里**没有任何一次他 push 到你的仓库**。他能改的只有网页仓库的"提案"，能不能进由你 cherry-pick 决定。

   ▼

### 1.2 换蛋提醒的真实数据流（最关键的一条）

```
网页：组主生成接入码
   → 群管理员发 rc换蛋接入 <码>
   → 插件 POST /egg-bot/redeem  ← 拿到 groupId + bindingVersion
   → gs_subscribe 落一条 session 订阅（TASK='[RocomUID] 工具箱换蛋提醒'）

每 60 秒（APScheduler interval）：
   poll_toolbox()
      ├─ POST /egg-bot/tick                       （让服务端算巡查、生成排队事件）
      └─ for 每条订阅: send_subscription()
            ├─ POST /egg-bot/claim   （带 botId/群号/组号/bindingVersion，拿租约）
            ├─ 逐条 POST /egg-bot/validate（发送前复核，防止已失效/已换群）
            ├─ 查 RocomUser 全部用户 → 逐个查绑定 UID（N+1 查询）
            ├─ deliver(): 去重 → UID 归一到一个 QQ → 发群消息（@ 人）
            └─ POST /egg-bot/ack  （sent / failed / unbound）
```

设计上算是对的：**租约 + 发送前复核 + 本地已发记录 + 回执**，比"直接推到群里"稳。问题全在实现细节和运维面。

## 2. 严重问题（按后果排序）

> 每条给「现象 / 证据 / 后果 / 怎么修 / 验收」。P0 = 正在造成用户可见损失，本周内必须处理。

### P0-1 · 机器人代码没有版本管理，且框架核心被脚本改过

- **现象**：插件目录没有 `.git`；网页仓库里也没有任何机器人代码（全仓库 grep `RocomUID|gsuid_core` 只命中 docs）。
- **证据**：
  - `Test-Path "D:\QQBot\gsuid_core\gsuid_core\plugins\RocomUID\.git"` → `False`
  - `D:\QQBot\codex_patch_core.py` 直接 `p.write_text(...)` 改写 `gsuid_core/core.py`，替换 `handle_event` 调用链；`codex_patch_repeat_small.py` 更是把一段硬编码的
    `target_send([at 3037447901, " @测试：机器人@功能验证", group 1124313894], ...)` 塞进 `core.py`。
  - 目前 `core.py` 已还原（grep `codex|_live_bot` 无命中），但备份 `core.py.codex-test-direct-at-20261117` 还躺在包目录里。
- **后果**：改错一句话无法回滚；换机器/重装插件即丢改动；任何"上周改过什么"都只能靠记忆；两个人同时改必然互相覆盖。
- **怎么修**：把插件变成独立私有仓库（见 §3 Phase 0），`git commit` 当前线上版本作为 baseline，再把 `codex_*.py`、`start_all.bat`、`guard_uins.ps1` 收进 `ops/` 目录并写清用途；框架核心**永不再手改**，必须改就走 patch 目录 + 记录。
- **验收**：`git log --oneline` 有 baseline；`git status` 干净；`grep -r "write_text" ops/` 只出现在备份/还原脚本里。

### P0-2 · 定时任务没有异常兜底：一次网络抖动 = 这一分钟所有提醒都不发

- **现象**：APScheduler 每 60 秒跑 `poll_toolbox`，第一句 `await call('tick', {})`，而 `call()` 里 `httpx` 的异常完全没接。
- **证据**：
  - `rocom_toolbox/bridge.py:49-63`：`async with httpx.AsyncClient(...)` → `client.post(...)`，**没有 try/except**，只处理了 `status_code != 200`。
  - `rocom_toolbox/__init__.py:177-184`：`poll_toolbox` 里 `await call('tick', {})` 之后才遍历订阅，前面一抛，后面全部跳过。
  - 日志统计（`data/logs/*.log` 里 `Job "poll_toolbox" ... raised an exception`）：

    | 日期 | 次数 |
    | --- | --- |
    | 11-16 | 1 |
    | 11-17 | 3 |
    | 11-18 | 21 |
    | 11-19 | 39 |
    | 11-20 | 14 |
    | 11-21 | 21 |
    | 11-22（到 09:10） | 7 |

    最近一条（08:22:29）的 traceback 明确是 `httpx.ConnectError` → `bridge.py:53` → `poll_toolbox`。
- **后果**：① 那一分钟所有群都不提醒；② 若异常发生在 `claim` 之后，被领走的提醒**租约到期后不会再发**（与 `docs/code-review/2026-11-19/R2a.md` 的 R2a-U01 是同一个坑），网页显示"失败"，用户只能等 30 分钟冷却手动再催；③ 异常只进日志和 `error_reports/`，没人看。
- **怎么修**：
  1. `call()` 内整体 `try/except (httpx.HTTPError, msgspec.DecodeError, Exception)`，返回 `Reply(error='工具箱连接超时')`；
  2. `poll_toolbox` 里 `for` 每条订阅单独 `try`，一条坏不影响其他群；
  3. 加失败计数 + 指数退避（连续失败 3 次后降频到 5 分钟），恢复后自动回到 1 分钟；
  4. 连续失败 10 分钟发一条**私聊主人**的告警（不是群）。
- **验收**：新增离线用例 mock `httpx` 抛 `ConnectError` → `call()` 返回 `ok=False` 且不抛；`poll_toolbox` 在单条订阅抛错时其余订阅仍执行。上线后 24 小时 `raised an exception` 计数为 0。

### P0-3 · 桥接环境混线：`ingest` / 手动巡查固定打测试站，而 `ingest` 接口还没上线

- **现象**：
  - `rocom_homeinfo/egg.py:92`：`call('ingest', {...}, test=True)` —— `rc生蛋了吗` 查完蛋，把结果"蛋仓同步"到**测试站**；
  - `rocom_toolbox/__init__.py:67`：`rc换蛋巡查` 也固定 `test=True`；
  - 其余 `redeem/disable/tick/claim/validate/ack` 走 `bridge.BASE`（正式站）。
- **证据**：
  - `git grep -l ingest release -- functions`、`git grep -l ingest test -- functions` **都无结果**；只有 `codex/test-personal-stock-20261121` 分支的 `functions/_lib/eggBotBridge.ts`、`eggPatrolStock.ts` 里有 `ingest`，该分支的 3 个提交**没有合进 `test`/`release`**。
  - 两个站点 `/api/egg-bot/ingest` 无凭据探测都是 `401`，但那是鉴权门先返回，**不能据此认为接口存在**（不存在的 action 也是 401，已实测 `zzz-no-such-action` → 401）。
- **后果**：按当前部署，正式站用户每次 `rc生蛋了吗` 都会得到一句「蛋仓同步失败，请稍后重试。」（服务端没有这个 action），或者即使有，蛋也被写进**测试库**而不是正式库 —— 两条都是用户可见的错。
- **怎么修**：把环境从代码里挪到配置（`RC_bridge_env = prod | test`，默认 prod）；删掉两处 `test=True`；`ingest` 在网页侧正式上线并跑通一次真实链路前，**先从机器人侧移除调用**（或 feature flag 默认关）。
- **验收**：`grep -rn "test=True" RocomUID/` 为 0；`rc生蛋了吗` 的回复里不再有"蛋仓同步失败"；正式站 D1 里能看到 ingest 产生的记录。

### P0-4 · 上游接口 5 分钟无上限轮询 + 无频控 + 任意 UID 可查

- **现象**：
  - `utils/rocom_api.py:93-110`：上游返回 202 就进入 `while time.time()-now_time <= 300` 的轮询，每 3 秒一次，**单个请求最长 5 分钟**；`get_home_info`/`get_home_pet_data` 还带 `wait_ms: 20000`。
  - `rocom_homeinfo/__init__.py:230`：`rc生蛋了吗` 不带参数时对**全部已绑定 UID** `asyncio.gather` 并发查。
  - `rocom_homeinfo/__init__.py:113-151` `_resolve_uid`：只要是 6 位以上数字就直接查，**不校验该 UID 是否属于调用者**；插件里也没有任何按人/按群的频控或配额代码。
- **后果**：一条命令能占住事件循环数分钟；群里多人同时用就排队（图像渲染也是同步 CPU 活）；任意人可拿别人的 UID 刷家园/蛋/精灵，既烧共享 key 额度，也把"某个 UID 有蛋"这种信息暴露给无关的人；上游一慢，机器人整体像卡死。
- **怎么修**：统一 10 秒硬上限（含轮询）+ 单次请求最多 1 轮；全局 `asyncio.Semaphore(2)` 控制上游并发；每人每群 30 秒/次、每天 N 次的频控；查非绑定 UID 需要显式开关（默认关）；把出图丢 `asyncio.to_thread`。
- **验收**：`rc生蛋了吗` 在 5 个 UID 下 15 秒内返回；压测两路并发时第 3 个请求被频控拒绝并给出中文提示；日志里单次上游耗时 P99 < 12 秒。

### P1-1 · 凭据与隐私面：明文 token + 旧链路未下线

- **现象**：`RocomUser` 表把扫码登录得到的 `framework_token`/`cookie` **明文**存 SQLite（`utils/database/model.py:39-43`）；`rc绑定token`/`rc token帮助` 旧链路还在（帮助里没有）；`data/.codex-test-token` 这类测试令牌文件直接躺在数据目录。
- **后果**：拿到这台机器（或拷走 `GsData.db`）就等于拿到 7 个用户的游戏登录态；旧 token 链路是绕过正常扫码的后门。
- **怎么修**：令牌字段至少用本机密钥加密（或直接改为"用完即弃 + 短存"）；删旧命令；`data/.codex-test-token` 移出数据目录并登记；`.gitignore` 明确排除 `data/`、`*.db`、`*.log`。
- **验收**：`sqlite3 GsData.db "select cookie from RocomUser limit 1"` 看不到可读 token；`rc绑定token` 返回"该命令已下线"。

### P1-2 · 群内消息治理：每天最多 8 条 @全体

- **现象**：`rocom_merchant/__init__.py:329`（每轮推送）与 `:382`（好货二次提醒）都 `MessageSegment.at('all')`；8/12/16/20 各一轮，11/15/19/22 各一次二次提醒。
- **后果**：小群会被 @全体 逼到静音/踢人；这也是最容易让群主直接禁掉机器人的原因。
- **怎么修**：`@全体` 改成配置（默认关，只 @ 订阅者或 @ 一个角色）；二次提醒默认关。
- **验收**：默认配置下，一天推送到群里的消息里 `at all` 计数为 0。

### P1-3 · 单点运行、无守护、无"在线"信号

- **现象**：机器人跑在你的 PC 上，靠一个 `.bat` 起两个窗口；挂了没人知道；`ROCO_TOOLBOX_BRIDGE_TOKEN` 只由 `start_all.bat` 从注册表注入，**换一种启动方式就会静默失效**（`bridge.enabled()` 返回 False，不报错、不发消息）。
- **后果**：网页照常生成提醒，群里永远没消息；排查要从日志翻到环境变量。
- **怎么修**：注册为 Windows 计划任务（开机启动 + 崩溃重启）；`poll_toolbox` 每轮把 `bot_self_id + 最后在线时间` 记到服务端，网页小组设置里显示「机器人最近在线 X 分钟前」，超过 10 分钟标红；启动时若 `enabled()==False` 直接私聊主人告警。
- **验收**：手动杀掉进程后 1 分钟内自动拉起；拔网线 10 分钟后网页显示离线。

### P1-4 · 可维护性：只有 4 个测试，改任何东西都是盲改

- **现象**：`tests/test_toolbox_delivery.py` 4 个用例只测纯函数 `deliver()`；真正会坏的 `bridge.py`、`__init__.py`（命令/调度）、`egg.py`（解析）零覆盖。
- **怎么修**：见 §3 Phase 1。优先补三类：① `bridge.call` 的错误分支（超时/401/非 JSON/HTML 502）；② `send_subscription` 的编排（mock 掉 call 和 send）；③ `egg.py` 的文本解析（真实样例 JSON 固定成 fixture）。
- **验收**：`pytest` ≥ 20 用例、全绿；`ruff check` 0 error；GitHub Actions 每次 push 跑。

## 4. 补充任务：你朋友能不能改你的机器人代码

### 结论

**不能。** 分三层说：

1. **机器人代码不在任何仓库里** → 没有"提交权限"这回事。
   `D:\QQBot\gsuid_core\gsuid_core\plugins\RocomUID` 没有 `.git`；网页仓库 `functions/`、`src/` 里也**没有**机器人代码（全仓库 grep `RocomUID|gsuid_core|rocom_toolbox` 只命中 docs 里的路径说明）。他能改的只有"他本地那台电脑上的副本"。
2. **网页仓库他是 fork + PR 模式，没有 push 权限的证据。**
   - 仓库公开：`https://api.github.com/repos/sasaki-ishiran/roco-toolbox` → `"private": false`、`"visibility": "public"`、`"forks_count": 1`、GPL-3.0。
   - fork 是他：`EavonChan/roco-toolbox`（`"fork": true`）。
   - 仓库公开事件（最近 100 条，实际 66 条）里，**43 次 PushEvent 的 actor 全部是 `sasaki-ishiran`**；`EavonChan` 只有 `ForkEvent` 1、`WatchEvent` 1、`PullRequestEvent` 3：
     | PR | 方向 | 状态 |
     | --- | --- | --- |
     | #1 `Codex/friend UI assets 20261117` | 他的 fork → 你的 `codex/friend-ui-assets-20261117` | **open** |
     | #2 配窝补全计划 | 他的 fork → 你的 `friend/20261119` | closed，未合并 |
     | #3 `Friend/20261119` | 他的 fork → 你的 `release` | closed，未合并 |

     全部是"从 fork 提 PR"，没有一次直接往你的分支 push。
   - 你自己的 `.github/CONTRIBUTING.md` 写的就是上游 + fork + PR 的流程；`AGENTS.md` 也写明"只摘取、不合并整支分支"。
3. **机器人是第三方开源插件的本地魔改版**（上游 [jiluoQAQ/RocomUID](https://github.com/jiluoQAQ/RocomUID)，GPL-3.0）。理论上他可以去**上游**提 PR，但那和你机器上的副本没有任何连接 —— 除非你手动把文件拷回来。

### 能确认到什么程度

- 「他没有 push 到你的仓库」= 有证据（公开事件 + 分支作者 + PR 形态）。
- 「他一定不是 collaborator」= **还不能 100% 确认**：未认证的 GitHub API 看不到协作者名单，本机也没装 `gh`。如果他曾被加为协作者但从未 push，事件里不会留下痕迹。

### 想 100% 确认，做这两步

1. 打开 `https://github.com/sasaki-ishiran/roco-toolbox/settings/access`，看 **Collaborators** 名单里有没有 `EavonChan`；
2. 或装 `gh` 后跑：
   ```powershell
   gh api repos/sasaki-ishiran/roco-toolbox/collaborators --jq '.[].login'
   ```
   顺带看 `Settings → Branches` 有没有对 `test` / `release` / `bot` 开保护。

### 建议

- 保持"只 fork、不邀请"：他的价值是提案，不是写权限。
- **PR #1 还开着**（`Codex/friend UI assets 20261117`，指向你的 `codex/friend-ui-assets-20261117`），按你自己的规矩给它一个结论（采纳哪些、关掉还是留着当讨论载体），别让它一直挂着。
- 如果哪天真要加协作者：**只给 `test` 分支的写权限 + 开分支保护**，`release`/`bot` 和生产部署密钥绝不外放。
- 机器人这边真正的风险不是"他改代码"，而是**有人拿到 `D:\QQBot` 整个目录**（含注册表里的 `ROCO_TOOLBOX_BRIDGE_TOKEN`、`GsData.db` 里 7 个用户的登录态）。给目录、给压缩包、远程连你电脑，风险都远大于一次 PR。
- 同理：以后收到"我帮你改好了，你把这个 zip 覆盖上去"这类消息，要按**不可信输入**处理（GPL 项目谁都能改），先 diff 再覆盖。
