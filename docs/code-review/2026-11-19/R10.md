## R10-M02 · 中风险 · 桌面版单次采集超过 128MiB 后，采集面板报「状态无效」并让进度与雷达一起停更

**① 问题描述**
**现状**：桌面采集端只把 128MiB 当作「不可读」上限——`inspect()` 超过上限返回空串，状态里的 `savedBytes` 也会超过上限；网页侧 `readCollectorState` 一旦看到 `savedBytes > MAX_CAPTURE_BYTES` 就整份判为无效并抛「本机采集状态无效，请重新打开小布助手」，`readCaptureSnapshot` 拿到空串则返回 `null`，hook 直接把进度清空且不报错。安卓端有 8MiB 触发、只留 4MiB 的滚动裁剪，桌面端没有任何裁剪或停采。
**用户影响**：用户看到的是「正在采集」但进度、附近雷达、战斗提示全部停住，或者直接弹出「状态无效，请重新打开小布助手」，完全看不出真实原因是文件到了上限。
**触发条件**：桌面版自动选全部网卡连续采集，单文件累计超过 128MiB（长时间挂机最容易触发）。
（证据：`desktop/capture/manager.cjs:15,173-184`；`src/collector/nativeCollector.ts:107,115-118`；`src/collector/useCaptureProgress.ts:208-214`。）

**② 优化方案**
A（推荐）：把「已到上限」做成显式状态——`inspect()` 与 `state()` 在超限时给出可读标记（如 `capped: true` / message「已达 128MiB 上限，请停止后重新开始」），网页侧在超限时显示提示而不是整份状态判无效；B：桌面端也做滚动裁剪（对齐安卓的 8MiB/4MiB 策略），代价是碰 PCAP 写入与增量读取链路，风险明显更高。推荐 A，改动集中在状态字段与一处提示。

**③ 优化后表现**
**解决**：超限时用户能看到明确原因并知道下一步，而不是面板假死或误报「状态无效」。
**验收**：把 `MAX_FILE_BYTES` 临时调小（或造一个 >128MiB 的 `capture-*.pcap`）后启动桌面采集，面板出现上限提示、采集可正常停止并重新开始；`npx vitest run src/collector` 通过。
