## R9-3-U01 · 不确定 · 野生精灵身高 98% 就被标「大块头」，与同模块「身高必须正好 100%」的判定口径不一致，是否算误报取决于图鉴区间取整误差

① 问题描述：现状是野生精灵的体型牌/需求判定把「身高 ≥98%」当成到顶，而同模块既有的体型口径是「身高必须正好 100%（容差 0）」；如果 98 不是刻意给图鉴区间取整留的容差，用户会看到附近把身高 98%~99.9% 的精灵报成「大块头/小不点」，抓回来却没有奖牌；触发条件是野生实体体重 ≥98%（或 ≤2%）而身高在 98%~99.9%（或 0.01%~2%）。
（`src/pcap/rareRules.ts:58-63`、`src/pcap/demandMatch.ts:41-45` 均写 `heightPct >= 98` / `<= 2`；同模块既有写法 `src/shared/bodySize.js:42-45`「身高必须正好到顶/到底才算极端体型（容差 0）」、`:69-83` `bodyGradeOf`；数据管线注释 `tools/data-pipeline/trim-catalog.mjs:119-125` 则明确「身高只用于合格判定，奖牌按体重 98%/2%」。两处口径谁对取决于野生 `raw.height`（整数 cm）与 wiki 区间取整的误差，静态无法定论；置信度：中）

② 优化方案：A——把两处身高条件收紧为 `>=100 / <=0`（体重保持 98/2），与 `bodySize.js` 的判定口径一致；B——保留 98，但在两处注明「98 是为图鉴区间取整留的容差，与合格判定的 100% 不同口径」并补边界单测；C——完全对齐 `bodyGradeOf`（身高 100% 且体重 ≥95/≤5）。推荐先把 B 落地（零行为变化、消除口径歧义），确认游戏实机后若 98 确实过宽再走 A；代价：A 需更新 `rareRules.test.ts:30-46`、`demandMatch.test.ts:40-58`、`wildNearby.test.ts:65-92`。

③ 优化后表现：口径显式化，避免「同一只精灵在附近页/需求里是大块头、导入后不是」的体验割裂；验收：`npx vitest run src/pcap`，按选定方案补「身高 99%」与「身高 100%」两条边界用例。

## R9-3-L02 · 低风险 · 刷新页面后，已抓精灵的 30 秒墓碑变成永久墓碑，与注释「30 秒后可重新出现」不一致

## R9-3-U02 · 不确定 · 静止一段时间后，附近列表可能整批消失（9 秒 TTL 依赖服务器对静止实体的重发周期）

① 问题描述：现状是每收到一帧 330/1043/1044 就执行一次「9 秒没更新即删除」，而 1043/1044 是增量帧，只有变更的实体才带；用户影响是如果服务器不会在 9 秒内重复下发静止实体，那么只要来一帧增量，视野里没动过的精灵会被整批清掉，列表/雷达突然变空；触发条件是站在精灵附近不动超过 9 秒后，服务器再下发任意实体帧。
（`src/pcap-decoder/.../core.js:25` `WILD_TTL_MS=9000`、`:1902-1918` `pruneWildPets`、`:1951-1978` `applyWildEntityFrame`；全仓 `git grep pruneWildPets` 只在 `core.js`，**没有任何单测**；置信度：中）

② 优化方案：先用真实抓包确认「静止实体在 330/1043 里的重发间隔」再定阈值。若重发间隔 >9s：A——TTL 与「距上次 330 的时间」联动（例如只有距上次 330 超过 TTL 才允许按 TTL 淘汰）；B——只在收到 330 全量帧后才执行 TTL 淘汰。若确认重发间隔 ≤9s，则补一条单测把该假设钉住，并保留现实现。

③ 优化后表现：静止精灵不会被误清、被其他玩家抓走的精灵仍会及时消失；验收：用一份包含「静止 >10s」的真实抓包跑 `npx vitest` 新用例，断言列表不因增量帧而清空。

## R9-3-U03 · 不确定 · 附近实体超过 80 只时普通精灵被静默淘汰，用户只看到「少了」

① 问题描述：现状是实体总数超过 80 就按「普通有坐标 → 无坐标 → 稀有 → 需求/告警」淘汰，被淘汰的普通精灵不进入列表/雷达，也没有提示；用户影响是拥挤场景（或长会话残留）下附近数量突然变少，用户无法判断是被裁掉还是真的没有；触发条件是同屏实体 >80。
（`src/pcap-decoder/.../core.js:27` `WILD_MAX_ENTITIES=80`、`:1883-1900` `wildKeepScore`、`:1919-1930` 淘汰；诊断只有 `nearbyWildDiagnostics` 的 `evicted` 计数，页面未展示；置信度：低，需真实场景数据）

② 优化方案：A——把上限做成可按场景调整，并在裁掉时通过 payload `total/evicted` 让面板文案能区分「被省略」；B——维持 80，但在 RocoPerf 里暴露 `wildEvicted` 供排障。推荐 B（零 UI 改动），若真机出现 >80 再升 A。

③ 优化后表现：拥挤场景的行为可解释；验收：`npx vitest run src/pcap`，补「81 只 → 普通先淘汰、需求/稀有保留」用例。
