## R4-H01 · 高风险 · 数据库一旦被拿走，用户常见的短密码很快就能被还原成明文

**① 问题描述**
**现状**：口令用 PBKDF2-SHA256 存储，但迭代次数只有 1 万次，注释写明是为守住 Pages Functions 的 CPU 上限；随机盐（16 字节、每用户独立）与固定长度比较这两点是对的。
**用户影响**：一旦 D1 的备份、导出或运维输出泄露，攻击者用显卡每秒能试十万量级的密码组合，纯数字/短字母密码往往几小时内就被还原，账号里的全部精灵数据、小组共享和复用同一密码的其它站点随之失守。
**触发条件**：数据库经任何途径外泄（备份、误提交、第三方导出、脚本输出被转发），不需要在线爆破——在线爆破已被「60 次/小时/IP + 20 次/小时/用户名」挡住（`functions/_lib/util.ts:89` 迭代常量与 `84-88` 注释；`util.ts:111-123` 哈希与校验；`util.ts:166-173` 固定长度比较；限流 `functions/_lib/auth.ts:147-152`）。

**② 优化方案**
把「一次算得尽量慢」补回来：A（推荐先做）加一个只存在环境变量、与数据库分开保管的「胡椒（pepper，服务端私有密钥）」——先 HMAC 再进 PBKDF2，数据库单独泄露也无法离线破解，改动约 15 行、不涉及表结构，风险是老哈希要兼容一条回退路径；B 把迭代次数提到 10 万并顺带在登录成功时按旧哈希里的次数做「静默升级」（存储格式 `pbkdf2$次数$盐$哈希` 已支持不同用户不同次数，`util.ts:117-123`），安全收益最大，但需要运维先压测正式环境单次登录 CPU（免费版 Pages 的 CPU 上限可能不允许，要提额或换付费 Workers）。建议 B 排期评估、A 先行上。

**③ 优化后表现**
**解决**：即使数据库被整份拿走，攻击者也拿不到能直接换来登录的凭据。
**验收**：本地 D1（wrangler 本地库）注册一个测试账号并登录，记录 `/api/auth/login` 单次耗时；`npx vitest run src/api` 保持全绿，并补一条「同一密码两次哈希盐不同、校验都为真」的用例。（验收只用本地库，不要对正式库跑 `--remote` 脚本。）

## R4-H02 · 高风险 · 改密码时原密码打错一个字，就被踢出登录

**① 问题描述**
**现状**：服务端把「原密码不对」当成未授权，返回 401；前端把**任何** 401 都理解为「登录失效」，清掉本地令牌并抛出「登录已失效，请重新登录」。
**用户影响**：用户只是想换个密码，打错一个字就被强制退出，页面跳回登录表单；刚设置完用户名密码、还没记牢的老用户可能就此进不去，只能再找管理员重置。
**触发条件**：已登录 → 我的身份 → 修改密码 → 原密码输错一次即触发。
（证据：`functions/_lib/auth.ts:209` 返回 401；`src/api/session.ts:85-88` 401 即 `clearSession()` 并抛出统一文案；表单入口 `src/ui/AccountPanel.tsx:202-218`。）

**② 优化方案**
A（推荐，一行）：把「原密码不对」改成 400（或 403），前端就只会显示「原密码不对」，会话不受影响。B（根治）：服务端所有受保护接口的鉴权失败统一带一个机器可读的错误码（如 `code: 'UNAUTHORIZED'`），前端只在收到该码时清会话——要动 `functions/_lib/*` 里所有走 `authenticate` 的接口，改动面大但能杜绝同类误判。先上 A，B 随下一次接口整理一起做。

**③ 优化后表现**
**解决**：输错原密码只提示「原密码不对」，登录状态与同步都不受影响。
**验收**：登录后打开「修改密码」，原密码随便填错并提交 → 面板仍是已登录态（「已登录 · 云端版本 …」还在），提示为「原密码不对」。

## R4-H03 · 高风险 · 只用恢复码的老用户换了手机，网页上再也没有回来的路

**① 问题描述**
**现状**：网页端的「用恢复码登录」入口被整段删除（`src/api/session.ts` 已不再导出 `recoverAccount`，`src/ui/AccountPanel.tsx:508-578` 只有注册/登录两种表单），而 2026-11-18 之前建的老账号没有用户名密码；管理员脚本 `scripts/reset-password.mjs` 只能按用户名找账号（`reset-password.mjs:59-65`，找不到就提示「用户需要先在应用里设置用户名」），`scripts/reset-recovery-code.mjs` 虽能重置恢复码，但网页已经没有任何地方能输入它。
**用户影响**：这批用户换手机或清了浏览器数据后，永久失去云端精灵数据与自己创建的小组，自助走不通、管理员也走不通（除非重新安装一个旧版安装包并用旧接口登录）。
**触发条件**：老账号（`username` 为空、从未设置用户名密码）在没登录的新设备上打开网页。
（证据：后端 `POST /api/auth/recover` 仍在且可用 `functions/_lib/router.ts:65`、`functions/_lib/auth.ts:222-237`；前端无任何调用/表单；`auth.ts:163-190` 的 setup 必须已有令牌。）

**② 优化方案**
A（推荐）：网页补一个「用恢复码登录」入口，直接复用现成的 `recover` 接口，登录成功后立刻引导设置用户名密码（这样账号才完成迁移）；注意这属于**新增界面**，按 `AGENTS.md`「新增 UI 必须先审核再实现」要先出 375/390 截图方案给用户确认。B：给 `reset-password.mjs` 加 `--set-username`，让管理员能为无用户名的老账号一次性写入用户名+密码（不改前端，但每次都要人工介入、还要人工核对身份）。建议 A 为主、B 兜底；若产品决定「老账号就此作废」，需要单独写公告，不能默认用户知道。

**③ 优化后表现**
**解决**：老用户换设备后能自己拿回账号，不必依赖人工，也不必装旧包。
**验收**：取一个 `username` 为空、`recovery_hash` 有值的测试账号，在网页输入其恢复码 → 进入已登录态 → 设置用户名密码成功 → 换另一个浏览器用新用户名密码登录能看到同一份云端数据。

## R4-H04 · 高风险 · 改完密码，别处还登着的设备和旧恢复码照样能进

**① 问题描述**
**现状**：改密码只更新了 `password_hash` 一列，既没有吊销该账号已有的其它令牌（`tokens` 表没有过期字段，`authenticate` 只判断令牌是否存在），也没有清掉老账号迁移时保留下来的 `recovery_hash`；而 `/api/auth/recover` 对任何账号都仍然只凭恢复码就发新令牌。
**用户影响**：用户因为「怀疑被人登过」去改密码，改完后旧手机、旧恢复码依旧能登录，改密码形同虚设；网页也没有「退出所有设备 / 重置恢复码」的入口，用户没有任何补救手段。
**触发条件**：改密码时该账号还有其它设备的令牌存活，或恢复码曾写在不安全的地方（聊天记录、便签、仓库里的明文文件）。
（证据：`functions/_lib/auth.ts:211-213` 只改 `password_hash`；`functions/schema.sql:31-37` 无过期列、`functions/_lib/util.ts:144-160` 不校验时效；`functions/_lib/auth.ts:183-185` setup 不动 `recovery_hash`；`auth.ts:229-236` 恢复码换令牌不看是否有密码。）

**② 优化方案**
A（推荐）：改密码成功时在同一个 `DB.batch` 里删掉该账号除当前令牌外的所有令牌，并把 `recovery_hash` 重置为随机占位（等于宣布「恢复码登录」对已迁移账号失效）；代价是老账号再也用不了恢复码，所以必须**先上线 H03 的恢复码登录入口**，再上这条，顺序不能反。B：只吊销其它令牌、保留恢复码兜底（改动更小，但泄露的旧码仍能进）。无论 A/B，都建议补一个可见的「退出所有设备」按钮（同为新增界面，需先过 UI 审核）。

**③ 优化后表现**
**解决**：改密码后其它设备被踢下线、旧恢复码失效，账号回到只有本人能进的状态。
**验收**：两台浏览器登录同一账号 → A 改密码 → B 的下一次请求收到 401 并提示重新登录；用旧恢复码调用 `/api/auth/recover` 返回 401。

## R4-M01 · 中风险 · 有人知道你的用户名，就能让你一直登不上

**① 问题描述**
**现状**：登录限流除了按 IP，还按用户名单独计数 20 次/固定 1 小时窗口，且成功登录也计入；窗口按整点对齐。
**用户影响**：任何人拿对方用户名连发 20 次错密码，对方这一小时就会被回「尝试太频繁」，每小时开头再来一轮就相当于长期锁死；正常用户完全无从自救。
**触发条件**：知道对方用户名即可，无需登录、无需被对方发现。
（证据：`functions/_lib/auth.ts:147-152`；`functions/_lib/util.ts:191-209` 固定窗口按 `Date.now() - Date.now()%windowMs` 对齐、计数在验密之前。）

**② 优化方案**
A（推荐）：把用户名维度换成「IP + 用户名」组合计数，另保留一个更宽松的全局每用户名上限（如 200 次/小时）只用于告警或延迟，不用来直接阻断——能挡住单点爆破，正常用户基本不会被误伤。B：只统计失败并把锁定时长改短（如 15 分钟滑动窗口），实现简单但分布式爆破的防护会弱一些。改动集中在 `handleLogin` 的限流键与 `util.ts` 的窗口计算，约 10~20 行。

**③ 优化后表现**
**解决**：别人无法用你的用户名把你锁在门外。
**验收**：从 IP1 连打 25 次错密码后，从 IP2 用正确密码仍能登录成功；IP1 继续爆破仍返回 429。

## R4-M02 · 中风险 · 用户名一栏不是文字时，注册/登录直接返回服务器错误

**① 问题描述**
**现状**：三个接口都对请求体里的 `username` 直接调 `.trim()`，没有类型判断；同模块既有写法是先判断 `typeof x === 'string'` 再处理。
**用户影响**：正常界面不会触发，但任何脚本化请求（自动化、扫描器、手写 curl）发 `{"username": 123}` 都会拿到 500 和一份未处理异常，日志里看不出是入参类型问题。
**触发条件**：`POST /api/auth/signup|login|setup`，`username` 传数字、对象或布尔值（`null` 会被 `??` 兜底）。
（证据：`functions/_lib/auth.ts:111`、`141`、`167` 直接 `.trim()`；同模块写法 `functions/_lib/collectionGroups.ts:378`、`455-456`。）

**② 优化方案**
三处统一改成「不是字符串就按格式错误处理」：登录仍回 401，注册/设置回 400，与同模块已有写法对齐，约 3 行改动。

**③ 优化后表现**
**解决**：畸形请求得到可读的 4xx，不再制造无意义的 500 告警。
**验收**：`curl -X POST <站点>/api/auth/login -H 'Content-Type: application/json' -d '{"username":123,"password":"12345678"}'` 返回 401/400 而不是 500。

## R4-M03 · 中风险 · 老账号设置用户名密码后，别人先设一步就再也改不回来

**① 问题描述**
**现状**：`/api/auth/setup` 只校验「当前令牌有效」，不要求恢复码或任何二次确认；设置成功后同账号再调用一律 409，且写库语句没有 `WHERE username IS NULL` 条件。
**用户影响**：任何拿到过这个旧令牌的人（共享过的设备、曾贴进聊天/日志的请求）可以先一步把账号永久绑到自己选定的用户名密码上，原主人既改不掉也抢不回，只能注销重来；两台设备同时提交时，先设置的那份凭据会被静默覆盖。
**触发条件**：旧令牌泄露；或同一账号在两处同时点「保存」。
（证据：`functions/_lib/auth.ts:163-190`（`183-185` 的 `UPDATE` 无条件）、`auth.ts:176` 已设用户名即 409。）

**② 优化方案**
A（推荐）：设置时多要一项「恢复码」作为所有权凭证（老账号本来就有一张，丢了可用 `scripts/reset-recovery-code.mjs` 重发），并把 `UPDATE` 加上 `AND username IS NULL`。B：只加条件更新（1 行，解决并发覆盖，不解决抢注）。这关系到「用户身份以什么为准」的产品口径，**需产品确认是否愿意在迁移时多要一步恢复码**；选了 A 再动代码。若走 A，表单也是新增界面，需先过 UI 审核。

**③ 优化后表现**
**解决**：只有真正持有账号凭证的人能完成迁移，且并发提交不会互相顶掉。
**验收**：两台浏览器同时提交不同用户名 → 只有一个成功、另一个返回 409；不带恢复码提交返回 400。

## R4-L03 · 低风险 · 三个旧登录接口继续对外开放，看不出何时下线

**① 问题描述**
**现状**：`/api/auth/register|recover|rotate` 保留给未升级客户端，注册成功即建号（每 IP 10 次/小时），令牌与恢复码长期有效，接口本身没有任何版本门槛或下线标记。
**用户影响**：攻击者可批量建空账号占配额；同时这三个接口正是 H04「旧凭据仍能进」的入口，很容易被误以为已经废弃。
**触发条件**：任何人直接请求这三个路径。
（证据：`functions/_lib/router.ts:64-66`、`functions/_lib/auth.ts:63-81`、`auth.ts:222-247`。）

**② 优化方案**

**③ 优化后表现**
**解决**：线上能看出还有多少旧客户端在用，下线有据可依，攻击面可控。
**验收**：`/api/stats` 或埋点里能按天看到旧接口调用次数。

## R4-U02 · 不确定 · 注销账号是否真的会解散自己创建的小组

**① 问题描述**
**现状**：`handleDeleteAccount` 只删快照/令牌/设备关联/账号，「你创建的小组会解散」完全依赖数据库外键 `ON DELETE CASCADE`，而仓库里没有任何 `PRAGMA foreign_keys` 设置文件，静态层面无法证明它在 D1 上生效。
**用户影响**：若级联未生效，用户点了注销后账号没了但小组还在，其他成员会看到一个没有组主、也无法被解散的小组。
**触发条件**：任何用户注销账号且该账号是某个小组的创建者。
（证据：批量删除 `functions/_lib/auth.ts:265-271`；组/成员外键 `functions/schema.sql:92`、`100-101`、`143`。）

**② 优化方案**
A：在本地或预发 D1 实测一次（建带组的测试账号 → 注销 → 查两张表），把结论写进验收清单；B：不依赖隐式级联，在注销的 batch 里显式删除该账号创建的组（改动约 5 行，行为可读、不依赖数据库配置）。
**置信度**：中（Cloudflare 文档称 D1 默认开启外键，但本仓库从未验证）。**需要谁确认**：跑一次验证的运维或后端负责人。

**③ 优化后表现**
**解决**：注销后不留无人管理的小组，界面上的承诺与实际一致。
**验收**：注销测试账号后 `SELECT * FROM mother_groups WHERE owner_account_id = '<id>'` 返回空。

## 最该先修的 3 条

### 1. R4-H03 · 只用恢复码的老用户换了手机后回不来
① 问题描述：网页删掉了恢复码登录入口，老账号又没有用户名密码，管理员脚本也按用户名找账号，这类用户没有任何一条可走的路。
② 优化方案：把现成的 `POST /api/auth/recover` 接回网页做一个入口（新增界面，先出 375/390 方案），登录后引导设置用户名密码；同时给重置脚本加 `--set-username` 兜底。
③ 优化后表现：老用户换设备能自助找回云端数据与小组；用一个 `username` 为空的测试账号走「恢复码登录 → 设凭据 → 另一浏览器登录」验收。

### 2. R4-H02 · 改密码输错原密码被强制登出
① 问题描述：服务端把「原密码不对」返回 401，前端把所有 401 当成登录失效并清掉会话。
② 优化方案：把该分支改成 400/403（一行），后续再统一鉴权失败的错误码。
③ 优化后表现：输错原密码只提示「原密码不对」，账号仍处于登录态；按「修改密码表单里故意输错」验收。

### 3. R4-H01 · 口令哈希迭代次数过低
① 问题描述：PBKDF2 只有 1 万次迭代，数据库一旦外泄，常见短密码很快被还原。
② 优化方案：先加与库分开保管的胡椒（约 15 行），再评估把迭代提到 10 万并做登录时静默升级（需运维确认 CPU 预算）。
③ 优化后表现：库被拿走也无法离线破解；本地 D1 登录一次记录接口耗时、跑 `npx vitest run src/api` 验收。
