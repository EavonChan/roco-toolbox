## 1. R4-H01 · PBKDF2 只有 1 万次迭代
- **原结论**：1 万次迭代太低，库外泄后弱口令可被快速还原；建议加 pepper、再评估提到 10 万并静默升级。
- **裁决：基本成立，但不是唯一的存储短板。**
  - 成立：`functions/_lib/util.ts:89` 的 1 万次是主要短板；10 万仍低于 OWASP 对 PBKDF2-HMAC-SHA256 的建议值（60 万），且破解耗时与 Pages CPU 开销无法从代码断定。
  - 反证（报告「盐与比较都正确」仍成立）：`util.ts:112` 盐随机，`:166` 比较不按字节提前退出；公开盐与参数不妨碍逐账号离线猜测，这不算另一处缺陷。
  - 第三种情况（报告漏项）：`util.ts:119` 未严格校验存储串的字段数、十六进制格式与迭代范围，损坏的存储值可能让校验抛错而不是返回失败。
- **对修复动作的影响**：pepper / 提高迭代的方向成立；修复时顺手给 `verifyPassword` 加格式与范围校验，避免脏数据导致 500。

## 2. R4-M03 · setup 没有所有权凭证，且 UPDATE 无条件
- **原结论**：`/api/auth/setup` 只校验令牌，`UPDATE` 无 `WHERE username IS NULL`，并发提交会静默覆盖。
- **裁决：成立，但覆盖有条件。**
  - 成立：`functions/_lib/auth.ts:176` 先读后判，`:183` 只按 ID 更新；两次都读到未绑定且写入均成功时后写覆盖，若第二次读到已绑定则 409。
  - 补充：`functions/schema.sql:27` 的唯一索引只防不同账号撞用户名，不防同一行被改写；`auth.ts:164` 只要求令牌有效。
  - 第三种情况：账号在读取后、写入前被注销时，更新可能影响 0 行，`auth.ts:189` 仍返回成功。
- **对修复动作的影响**：加 `AND username IS NULL`（B 方案）是必要修复，可直接做；是否再要求恢复码（A 方案）仍是产品决定。验收要覆盖「并发覆盖」与「0 行更新仍报成功」两种情形。

## 3. R4-U01 · 是否还有旧客户端在用 register/recover/rotate
- **原结论**：仓库看不到真实调用量，无法判断能否动这三个接口。
- **裁决：成立，仓库不能排除旧版调用。**
  - `functions/_lib/auth.ts:9` 说明保留目的；`functions/_lib/router.ts:64` 起三个路由没有版本门槛、UA 分流或按客户端版本的埋点。
  - `auth.ts:65`、`:224` 的限流计数只是 `register`/`recover` 的间接信号，分不清旧 APK 与测试，也不覆盖 `rotate`。
  - 第三种情况：即使没有旧 APK 活跃，仍可能有「只持恢复码、尚未设密码」的用户；调用量为零不等于可以停用恢复。
- **对修复动作的影响**：H03/H04 的顺序问题不能靠仓库证据拍板；但「有恢复码老用户」这一类风险独立存在，网页入口应优先补齐。

## 4. R4-U02 · 注销账号是否真的解散其创建的小组
- **原结论**：依赖 `ON DELETE CASCADE`，仓库无 `PRAGMA foreign_keys` 设置，静态无法证明生效。
- **裁决：级联判断成立，「仓库从未验证」不成立。**
  - 成立：按仓库建库，`functions/_lib/auth.ts:270` 删除账号时 `functions/schema.sql:92` 会级联删除其创建的小组；D1 不需要显式开启外键。
  - 推翻（报告原句「仓库从未验证」）：`tools/test/verify-mother-groups-schema.mjs:337-345` 已有本地 SQLite 的注销级联断言。**但需注意**：该脚本当前在 `:159` 就断言失败（见 R2b-H01），所以这条级联断言目前实际上跑不到。
  - 第三种情况：注销者若只是别组成员，组保留、成员关系删除；其在该组担任负责人的任务会清空负责人，而不是删任务（`functions/schema.sql:101`、`:174`）。
- **对修复动作的影响**：不需要额外加显式删除；应先修好 R2b-H01 让脚本恢复绿色，这条级联断言才会重新生效；线上 D1 的实际表结构仍需一次人工核对。
