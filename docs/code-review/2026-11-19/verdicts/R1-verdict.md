## 1. R1-M01 · 组状态只增不减最终撞 1.5MB 上限
- **原结论**：`transferred` 蛋与历史报价永久保留，撞 1.5MB 后任意操作返回 413；并附我的补充「取消也不会变小」。
- **裁决：部分成立。**
  - 成立：普通操作确实不清理已转交蛋或历史交易，容量检查在 `functions/_lib/eggMatching.ts:107`。
  - 推翻（我的补充，不是报告原文）：「取消也不能腾空间」。`src/shared/eggWorkflow.ts:386` 的取消与 `:221` 的完整库存同步都会删掉「已不在快照里的可用蛋」，因此存在缩容路径；413 拒绝的是**变更后的状态**，不是永久锁组。
  - 第三种情况：空产线同步可清自己的产线（`eggWorkflow.ts:169`）；成员移除还有绕过该容量检查的清理路径（`functions/_lib/collectionGroupsStore.ts:1014`）。
- **对修复动作的影响**：不必把「整组永久不可操作」当成既定事实；修复目标应是「常态增长需要主动瘦身」，同时保留「靠别的成员移除/重新采集偶然缩容」的兜底说明。优先级可从「阻断级」下调为「长期容量治理」。

## 2. R1-M02 · 一条脏 breeding_pairs 让整轮巡查抛错
- **原结论**：配窝解析抛错导致整轮巡查失败，用户完全无提示。
- **裁决：部分成立。**
  - 成立：`src/shared/eggPatrol.ts:149`、`:152` 的 `parent()` 抛错没有任何单条兜底，该 UID 本轮连已解析的 `eggs` 也不会写入观察；其他 UID 不受影响。
  - 推翻（报告原句）：「正式巡检不会把失败原因返回给用户 / 没有任何提示」。实际上该 UID 无旧观察时，任务卡会显示「巡查失败」（`functions/_lib/eggPatrolStore.ts:76`、`src/ui/plan/EggTasksPanel.tsx:79`）；强刷还会返回失败原因（`functions/_lib/eggPatrol.ts:152`）。
  - 第三种情况：有旧观察时读状态优先返回旧观察，失败被旧状态掩盖，因此「看起来一直停在某个状态」主要指这种情况。
- **对修复动作的影响**：修复方案（逐条容错 + 跳过计数）不变；但报告的「无提示」要改成「只有无旧观察时才显示失败，有旧观察时失败被掩盖」，验收时两种情况都要覆盖。

## 3. R1-M03 · 背包与家园共用时间水印，旧家园快照被静默丢弃
- **原结论**：先同步 12:00 背包、再同步 11:50 家园，整批家园蛋被丢弃且返回成功，客户端当作完成。
- **裁决：成立。**
  - `src/shared/eggWorkflow.ts:188` 在完整标记与蛋 ID 去重之前就 `return previous`；正常提交仍返回成功并递增版本，客户端 `src/ui/plan/EggMatchingHub.tsx:121` 会推进家园时间。
  - 第三种情况：后续更新的背包快照可能把本地已合并的家园蛋一起补传，但不会补传那次家园完整快照的**删除语义**（`EggMatchingHub.tsx:112`）；若家园时间先撞上客户端自己的水印，这些家园蛋也不会进入本地库存（`src/ui/plan/eggStockModel.ts:60`）。
- **对修复动作的影响**：方案（水印按 bag/home 拆分）成立；另外应在修复时一并考虑客户端 `eggStockModel` 的同一水印限制，否则只改服务端仍可能丢蛋。

## 4. R1-U01 · 接单前就在地上的蛋会被立刻判为「已产出」
- **原结论**：没有「任务创建时基线」，接单前就在地上的匹配蛋会在第一轮被判为 `produced` 并发群提醒。
- **裁决：成立，但「判产出」不等于「一定发提醒」。**
  - 成立：首次有效巡查不比较任务创建时间，唯一匹配一项活跃任务且只有一个候选父本的旧蛋直接判 `produced`（`functions/_lib/eggPatrolStore.ts:47`、`src/shared/eggPatrol.ts:251`）。
  - 第三种情况：多任务匹配或多候选父本会判 `ambiguous`，不排提醒；提醒去重发生在观察写入之后，只挡重复提醒，不挡首次产出判定（`functions/_lib/eggPatrol.ts:113`、`:117`）。
- **对修复动作的影响**：产品确认口径时，需要把「单父本 → produced 并提醒」和「多父本/多任务 → ambiguous 不提醒」分开描述；补用例时两种分支都要写。
