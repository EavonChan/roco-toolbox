## R8b1-L01 · 低风险 · 下载到的安装包只校验包名，不校验大小/哈希/版本号

**① 问题描述**
现状：下载完成后只检查文件非空，安装前用系统接口读出包名并比对，没有再校验文件大小、摘要或 `versionCode` 是否等于清单声明值。用户影响：下载到半包、错误页面或同包名的其它版本时，要到系统安装器才失败，用户看到的是系统报错而不是「更新包损坏，请重试」；同包名不同签名的包会被系统拒绝，不会真的装上。触发条件：下载链路中断、CDN 返回错误页（200）、清单配置错误。
（证据：`UpdateController.java:425-434` 只比对 `packageName`；`:470-513` 下载不校验字节数/摘要；清单里的 `versionCode` 未参与安装前校验 `UpdateManifest.java:38-46`。）

**② 优化方案**
清单增加可选 `sha256`（或 `sizeBytes`），下载完成后先比对摘要/大小，不一致直接提示重下并删除半包；安装前再比对 `getPackageArchiveInfo().versionCode` 与清单一致。改动约 30 行，不涉及表结构；旧清单没有 `sha256` 时跳过校验，保持兼容。

**③ 优化后表现**
解决：坏包在安装前就被拦住，提示可读。
验收：把下载地址临时指向一个 HTML 页面，点「立即更新」后出现「更新包损坏，已重新下载」而不是系统安装器报错。

## R8b1-L02 · 低风险 · 应用重启后，已下载好的安装包会被当成「还没下载」

**① 问题描述**
现状：「是否下载完成」只记在内存里，进程重启后即使安装包还在缓存目录，也返回「安装包还没准备好」，用户必须重新下载。用户影响：更新页提示安装后切到别的应用、系统把后台进程回收，回来再点安装会重新下载几十兆。触发条件：下载完成但未安装前进程被杀。
（证据：`UpdateManager.java:61`、`:131-152`、`:154-160`；`UpdateController.java:371-388`、`:425-434`。）

**② 优化方案**
安装前若内存标记为假但目标文件存在，则校验包名/摘要后允许安装；或把「已下载版本号」写进偏好。

**③ 优化后表现**
解决：重启后不必重复下载。
验收：下载完成后杀进程重开，点更新入口直接进入安装流程。

## R8b1-L03 · 低风险 · 清单允许 http 下载地址，但应用禁止明文，报错会让人看不懂

**① 问题描述**
现状：清单解析接受 `http://` 的安装包地址，而应用本身关闭了明文流量，真下载时会被系统拒绝，提示是网络层错误。用户影响：清单配置成 http 时，用户只会看到「下载失败/网络错误」，排查不到是地址不安全。触发条件：清单里写了 http 地址。
（证据：`UpdateManifest.java:41`；`AndroidManifest.xml:28` `usesCleartextTraffic="false"`；`UpdateController.java:506-509` 只把异常转文案。）

**② 优化方案**
清单解析只接受 `https://`（或解析后明确提示「下载地址必须为 https」），与明文策略保持一致。

**③ 优化后表现**
解决：地址不安全时在检查阶段就给出可读原因。
验收：把清单 `apkUrl` 改成 http，点检查更新出现「下载地址必须为 https」。

## R8b1-L04 · 低风险 · 「最低可用版本」高于清单版本时不会被拒绝，反而不会强更

**① 问题描述**
现状：清单只要 `versionCode > 当前` 才进入更新流程，`minSupportedVersionCode` 不与 `versionCode` 做一致性校验；若误配成「最低版本 45、清单版本 40」，当前 42 的用户会被判为「已是最新」，实际上低于最低可用版本。用户影响：清单配置错误时强更静默失效。触发条件：清单两个字段配反或漏改。
（证据：`UpdateManager.java:123-127` 先判新旧再判门槛；`UpdateManifest.java:38-46` 无交叉校验。）

**② 优化方案**
解析时要求 `minSupportedVersionCode <= versionCode`，否则视为坏清单；或在检查时若 `current < minSupported` 也进入强更分支（即使清单版本没有更高，也应提示不可用）。

**③ 优化后表现**
解决：错误配置会被识别，而不是静默放过。
验收：构造 `versionCode=40, minSupportedVersionCode=45`，当前 42 时应提示清单异常或要求更新。

## R8b1-L05 · 低风险 · Activity 销毁后在途下载仍会占着旧 Activity 直到网络超时

**① 问题描述**
现状：销毁时只关闭线程池，正在进行的 HTTP 读写不会立即中断，下载闭包仍持有 Activity 引用，最长可到读超时 30 秒。用户影响：频繁进出页面时短暂多占一点内存，无可见崩溃。触发条件：下载进行中 Activity 被销毁。
（证据：`UpdateController.java:154-160`；`:470-513` 的读超时 30 秒（`:477`）与 `cancelled` 仅在循环内检查（`:494`）。）

**② 优化方案**
销毁时把 `cancelled` 置真并主动 `disconnect()` 当前连接（保存连接字段），让下载线程尽快退出。

**③ 优化后表现**
解决：销毁后不再持有 Activity。
验收：下载中反复进出 Activity，LeakCanary 不再报告该引用。

## R8b1-U01 · 不确定 · 主清单拿不到时，低于最低版本的用户是否允许继续使用？

**① 问题描述**
现状：主清单（正式站 `version-18.json`）不可达时，会退回两份「只提示、不强更」的兜底清单；低于最低可用版本的用户在断网/主站故障期间可以一直用旧版本。用户影响：强更承诺只在主清单可达时生效，这是为了「不因一份旧缓存把人锁死」的有意取舍，但和「低于门槛必须阻断」的字面要求冲突。
置信度：中。**需要产品拍板**：离线/主站故障时是阻断（更严格）还是放行（更可用）。
（证据：`UpdateController.java:116-129`；`UpdateManager.java:93-107`、`:111-128`。）

**② 优化方案**
若必须阻断：兜底清单也读取 `minSupportedVersionCode`，只在「确实解析不到任何清单」时放行，并在强制页提示「无法确认版本，请联网后重试」。若保持现状：在发版规范里写明该例外。

**③ 优化后表现**
解决：强更策略在断网场景下有明确、可验收的口径。
验收：断网启动低版本客户端，行为符合拍板口径（进强制页或正常进入）。

## 复核结论（本次检查后未发现问题的点）

- **Activity 泄漏（e7422f0）**：控制器由 MainActivity 持有并在 `onDestroy` 调用 `destroy()`，强引用生命周期与 Activity 一致；检查/下载回调统一 `main.post`，不在后台线程碰 UI（`MainActivity.java:205`、`:524-538`；`UpdateController.java:154-160`、`:193-197`）。
- **强更门槛**：`current < minSupportedVersionCode` 才强制，且只有主清单能触发强更；断网/坏清单只回调失败，不会把用户锁在更新页（`UpdateManager.java:123-128`、`:93-107`）。
- **清单与通道**：清单地址来自 `BuildConfig`，正式包编译期断言不含测试站/内测清单；内测包只读内测清单。跨通道 APK 会被包名校验挡住（`build.gradle:217-247`；`UpdateController.java:425-434`）。
- **下载失败/重试/幂等**：下载前删除旧包、失败保留半包可重下、取消后不弹失败框、空文件视为失败；单测覆盖 `downloadFailureIsReported`、`emptyDownloadIsTreatedAsFailure`、`installWithoutPermissionIsBlocked`（`UpdateManager.java:131-152`；`UpdateManagerTest.java:133-201`）。
- **FileProvider**：安装包目录与备份/采集目录分别登记，authority 用 `${applicationId}.fileprovider`，与 `UpdateController` 的 `BuildConfig.APPLICATION_ID + ".fileprovider"` 一致（`file_paths.xml:4-7`；`AndroidManifest.xml:76-84`；`UpdateController.java:76`、`:403-423`）。
- **单测未改松**：清单解析的必需字段、http 拒绝、版本比较、门槛比较均有断言，且与实现一致（`UpdateManifestTest.java:16-77`）。
