## R1-M01 · 中风险 · 小组换蛋数据只增不减，用久了整组会突然什么操作都做不了

**① 问题描述**
**现状**：每次成交后，交出的两颗蛋被标成「已转出（`transferred`）」，加上所有报价记录（含被取消的），都永久留在小组的换蛋数据里，没有任何清理路径；只有「采集里已消失的现货蛋」会在分配 / 取消时被删。
**用户影响**：小组用到一定规模后，任意操作都会失败并提示「小组换蛋记录已达容量」，且旧数据不会自己变少——整组的换蛋功能等于关闭。
**触发条件**：同一小组累计约上千笔成交 / 报价（每条蛋记录还带父母信息，约 0.3~0.5KB），组状态序列化后撞上服务端 1.5MB 上限。
（技术证据：`src/shared/eggWorkflow.ts:218-223` 只对 `available && missingFromCapture` 做删除，`transferred` 无出口；`:303` 的报价永久入列、`:381-386` 取消只改状态不删记录；上限在 `functions/_lib/eggMatching.ts:107`。）

**② 优化方案**
在 `stock-sync` 成功落库后增加一次「历史瘦身」：`transferred` 蛋与 `done/cancelled` 超过 N 天（建议 30 天）的报价，只保留 `id / demandId / 双方账号 / 完成时间` 这类统计必需的字段，正文（`give` / `receive` / `line` / `parents`）清空。
代价：需要给 `WorkflowTrade` 增加一个「已归档」标记，前端历史列表对归档行只显示摘要（现在的历史列表已经按 `status` 过滤）。风险：归档行若仍被界面当作可点进详情会读到空字段，需同步改详情页的空态。
备选 B：只清蛋记录不清报价（改动最小，但省下的量不够，不推荐）。

**③ 优化后表现**
**解决**：小组用一年也不会因为数据变大而整组不可操作。
**验收**：造 2000 条已转出蛋 + 1000 条取消报价的组状态，跑一次 `stock-sync` 后 `state_json` 字节数明显下降，且 `applyEggAction` 的成交流程测试仍全绿（`npx vitest run src/shared/eggWorkflow.test.ts`）。

## R1-M02 · 中风险 · 家园数据里一条脏配对，会让这个账号的巡查提醒永久停摆且没有任何提示

**① 问题描述**
**现状**：解析家园场景时，蛋列表与住客列表遇到脏数据会跳过该行继续，但「配窝列表（`breeding_pairs`）」里只要有一条缺 `pet_gid` 之类的不良记录，就会直接抛错让整次巡查失败。
**用户影响**：这个账号之后每半小时重试一次、每次都同样失败，任务卡永远停在「待巡查」，对方永远收不到「已上窝 / 已产出」的消息，而正式巡检不会把失败原因返回给用户。
**触发条件**：上游 `scene-info` 的 `breeding_pairs` 中任一条女性缺失 `pet_gid`、父本条目格式异常，或 `male_partners` 不是数组且元素不合法。
（技术证据：`src/shared/eggPatrol.ts:144-158` 的 `parent(raw.female)` / `.map(parent)` 直接抛错，而同一文件 `:116-126` 的 `home_pets` 是 `continue` 跳过；失败后 `functions/_lib/eggPatrol.ts:150-154` 只把下次时间推后 30 分钟。）

**② 优化方案**
把 `breeding_pairs` 的解析改为「逐条容错」：单条配对解析失败就 `continue`（记录一条计数用于排查），只保留能完整解析的配对；`breeding_pairs` 整体缺失或不是数组时按「本次没有上窝证据」处理，不抛错。蛋列表（`eggs`）仍保持严格失败——那是判定必需数据。
代价：约 10 行；风险是脏配对被静默忽略后「已上窝」看起来一直没达成，所以建议把跳过条数放进巡检返回体（仅在强刷时返回），便于内测定位。

**③ 优化后表现**
**解决**：一条脏数据只影响它自己那一条配对，巡查照常进行，提醒不会无声中断。
**验收**：在 `src/shared/eggPatrol.test.ts` 增加「`breeding_pairs` 中混入缺 `pet_gid` 的条目时仍能解析出蛋与合法配对」用例并通过；线上强刷一次能在返回体里看到被跳过的条数。

## R1-M03 · 中风险 · 背包快照比家园快照新时，整批家园蛋会静默上传失败

**① 问题描述**
**现状**：库存同步用「一个时间戳水印（记录这批数据已经收过的时间点）」判断新旧，背包与家园共用这一份；客户端把两者合成一次请求，时间取两者较大的一个。
**用户影响**：用户后导入的是一份更早的家园截图时，这批家园蛋不会被服务端接收，但接口返回成功、本地也当成同步完成——蛋仓里看不到这些蛋，选蛋时「明明有却选不到」，只能再重新采集一次。
**触发条件**：某次同步的 `capturedAt` 不大于该账号该小号上次成功同步的时间戳（例如先同步了 12:00 的背包、再导入 11:50 导出的家园）。
（技术证据：`src/shared/eggWorkflow.ts:187-188` 水印键只有 `[账号, gameAccountKey]`、单值比较后 `return previous`；客户端 `src/ui/plan/EggMatchingHub.tsx:105-117` 用 `Math.max(bagTime, homeTime)` 作为唯一 `capturedAt`。）

**② 优化方案**
把水印拆成背包 / 家园两条（键改成 `[账号, gameAccountKey, 'bag'|'home']`），各自只和自己上一次比：背包旧了就只丢背包那部分、家园旧了只丢家园那部分；同一请求里两段独立生效，任何一段被丢弃时在响应里带一个「已忽略旧快照」的标记，客户端据此提示「请重新采集家园」。
代价：水印键结构变化，旧键需一次性兼容读取（缺键视为 -1，不会重复收）；服务端 `visibleState` 的水印过滤（`functions/_lib/eggMatching.ts:72-74`）同步改成按前缀匹配。

**③ 优化后表现**
**解决**：任一侧的旧快照都不会拖累另一侧，同步结果与用户看到的一致。
**验收**：先 `stock-sync` 一个 12:00 的背包，再 `stock-sync` 一个 11:50 的家园，蛋仓里仍能看到那批家园蛋（`npx vitest run src/shared/eggWorkflow.test.ts` 新增该用例）。

## R1-U01 · 不确定（置信度中） · 「接单前就已经在地上的蛋」算不算产出，需要产品拍板

**① 问题描述**
**现状**：现在每轮巡查都按「当前地上的蛋」判定，没有「接单时的首次基线」，因此一颗在接单之前就已经摆在对方家园里、且完全符合条件的蛋，会在接单后第一轮就被判为「已产出」并发群提醒。
**用户影响**：如果这是别人上一轮留下的蛋，收单人可能被提示「你的蛋孵好了」，而实际这颗蛋不是本次定制的产出。
**触发条件**：任务生效时，对方家园地上已经有一颗符合蛋种 / 性格 / 体型 / 声音的蛋。
（技术证据：`src/shared/eggPatrol.ts:242-256` 每轮全量匹配；用例 `eggPatrol.test.ts:39-44` 明确断言「不需要首次基线」。与此前计划书 `docs/superpowers/plans/2026-11-16-家园巡查与QQ提醒.md:121` 写的「不能把接单前见过的蛋算新产出」相反，属规则变更而非实现疏漏。）
**需要谁确认**：用户 / 产品 —— 是否接受「地上已有的蛋也算产出」（好处是只要有蛋就能提醒，坏处是可能提示一颗旧蛋）。

**② 优化方案**
A）维持现状，并在任务卡文案上写「地上已有符合目标的蛋」，把语义从「刚孵出」改成「现在有」；B）恢复基线：任务生效时先记一次「当时地上的蛋」，只有新出现（或旧蛋曾消失后再次出现）的蛋才提醒。推荐 A（改动小、且符合新口径「蛋收走即停」），但必须由产品确认。

**③ 优化后表现**
**解决**：提醒语义与实际一致，不再出现「以为是刚孵的」误解。
**验收**：按确认后的方案补一条用例：任务创建时地上已有匹配蛋 → 期望结果符合拍板口径。

## R1-U02 · 不确定（置信度中） · 绿窝（学院小窝）单的「已上窝」判定没校验性格来自学院那只

**① 问题描述**
**现状**：判定「已上窝」只要父母里至少一方带目标性格，不区分带性格的是不是学院小窝那一只。
**用户影响**：勾了「绿窝」的需求，即使对方把带目标性格的那只放在普通窝、绿窝里放的是另一只，任务卡也会显示「已上窝」，但实际孵不出保底性格的蛋。
**触发条件**：需求要求绿窝，且对方家园里带目标性格的亲本不在学院小窝。
（技术证据：`src/shared/eggPatrol.ts:202-214` 的性格判断不涉及小窝归属，`parsePatrolScene` 也没有解析学院小窝标记；领域口径见 `docs/换蛋撮合-落地方案-2026-11-15.md:29、31`——「绿窝 100% 等于学院小窝那只」「交接卡必须写明哪只进绿窝」。该文档不在本批规范白名单内，故只列为不确定。）
**需要谁确认**：产品 —— 巡查是否需要区分绿窝；若需要，`scene-info` 是否能给出学院小窝标识（目前代码未解析）。

**② 优化方案**
A）巡查在任务带绿窝要求时，额外校验「带目标性格的亲本在学院小窝」，需要先在 `parsePatrolScene` 里解析小窝类型；B）不改判定，在任务卡上把「已上窝」写成「已排窝（未校验绿窝）」。推荐 B（零风险），A 需要先确认上游字段。

**③ 优化后表现**
**解决**：用户不会因为一句「已上窝」而误以为保底性格已经就位。
**验收**：按拍板结果补用例或补文案断言。
