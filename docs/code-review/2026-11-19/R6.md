## R6a-H01 · 高风险 · 选了体型或声音档位后，性格 / 蛋组选项旁的命中数偏大，点进去却是空列表

① 问题描述：**现状** —— 背包的分面计数在传给 `computeFacetCounts` 之前，把「体型」「声音」两类已选条件**整类删掉**（不只是删对计数对象自己那一类），于是所有维度（性别 / 稀有 / 性格 / 蛋组）的数字都不再考虑用户已选的档位；而列表本身仍然叠加这一档。**用户影响** —— 例如背包里 10 只母、其中 4 只大块头，勾了「大块头」时「性格 · 开朗 (6)」仍写着 6，点下去列表却是 0 只，只剩「没有符合条件的精灵，试试取消部分标签」；性别 / 稀有 / 体型图标则会出现「没置灰但点出来是空」的死路。**触发条件** —— 先选体型或声音任一档位，再看其它筛选的数字或置灰状态（`MyPets.tsx:462-466` 把 `SINGLE_SELECT_KINDS` 从已选条件里剔除；而 `petFilters.ts:335-361` 的 `computeFacetCounts` 本来就按「不计被计数的那一类」处理，不需要再剔一次；对照 `779b08c` 版本同一处只剔 `account:`）。

② 优化方案：把传给 `computeFacetCounts` 的已选条件恢复成只剔 `account:`（即删掉 `SINGLE_SELECT_KINDS` 这段过滤）。「选了某档就看不到别的档还可选」的问题由 `computeFacetCounts` 自带的同类排除解决，不需要在页面层再剔。改动约 3 行，同时补一条断言：勾「大块头」后，性别 / 性格的计数应等于「再叠加该维度后列表的条数」。

③ 优化后表现：**解决** —— 每个筛选旁的命中数与它点下去得到的列表条数一致，不会再出现「写着 6 点开 0」。**验收** —— 造两只同性格、不同体型的精灵：只勾其中一档体型，打开性格面板，数字应为 1；点它，列表也是 1；再点另一档体型，同性格的数字仍应与列表一致。

## R6a-M01 · 中风险 · 双组模式下性格旁的命中数按「满足任一蛋组」统计，列表却只留「两个蛋组都满足」的精灵

① 问题描述：**现状** —— 「双组」模式下列表对两个蛋组取**交集**，但分面计数把两个蛋组当成同一类的普通多选，按**并集**算基础集合，于是性格 / 性别等选项的数字偏大。**用户影响** —— 用户按数字判断「这个性格还有 8 只符合两组的精灵」，点开只有 3 只，判断简历/挑母本时会误判；数字为 0 的项被置灰的情况也可能反过来（本可命中却显示 0）。**触发条件** —— 切到「双组」并选满两个蛋组后，查看任意其它维度的数字或置灰状态（`MyPets.tsx:443-450` 列表按 `eggGroupSets.every(...)` 取交集；`MyPets.tsx:459-469` 只把蛋组当普通一类传进 `computeFacetCounts`，其内部 `petFilters.ts:340-353` 按并集计算）。

② 优化方案：方案 A（推荐，改动小）——给 `computeFacetCounts` 增加一个「某类按交集」的选项（例如 `intersectingKinds: ['eggGroup']`），双组模式下传入；方案 B ——在页面层先用两组交集得到 `withinIndices` 再单独算一次蛋组自身以外的计数，需要额外维护两套结果，后续易漂。推荐 A，并加一条「双组 + 性格」的计数与列表一致性断言。

③ 优化后表现：**解决** —— 双组模式下每个数字都对应真实结果数。**验收** —— 用一只同时具备两组、一只只有第一组的精灵：双组勾两组后，两只共有性格的数字为 1，点开列表也是 1；切回多选时数字恢复为 2。

## R6a-M02 · 中风险 · 命中数为 0 的性格选项照样能点，点了只得到空列表（同面板的蛋组选项此时是灰的）

① 问题描述：**现状** —— 性格面板由页面自己渲染按钮（`renderNatureOption`），没有传 `disabled`，所以「(0)」的性格按钮仍可点击；同一面板里的蛋组选项走 `filterDimensions`，命中 0 且未选中时会被置灰。**用户影响** —— 同一块筛选面板里两套规则：性格可以点出空列表、蛋组点不动，用户会以为自己漏选了什么；选到 0 命中性格后列表变空，还得再点一次取消。**触发条件** —— 任意已有筛选使某性格命中为 0 时打开性格面板（`MyPets.tsx:545-565` 的 `renderNatureOption` 无 `disabled`；对照同文件 `:747` 蛋组选项 `disabled: ((facetCounts[tag.id] ?? 0) === 0 && !on) || limitReached`；`779b08c` 版本走 `FilterAccordion` 时也有同款置灰）。

② 优化方案：在 `renderNatureOption` 上补与蛋组一致的 `disabled = (count === 0 && !on)`，并在按钮上加 `disabled:opacity-40` 一类样式；「已选但命中 0」仍保持可点，避免删不掉。改动集中在 3 行属性。

③ 优化后表现：**解决** —— 性格与蛋组的可点规则一致，点不出空列表。**验收** —— 勾一个只命中 3 只精灵的稀有度，再打开性格面板：没命中的性格呈灰色不可点，已选的性格仍可点掉。

## R6a-L01 · 低风险 · 旧「极限」筛选升级后，体型 / 声音出现两个档位同时选中，与「单选」新规则对不上

① 问题描述：**现状** —— 旧存档里的 `body:极限` / `voice:极限` 被迁移成「满体重 + 零体重」「+100 + -100」两组，两个标签同时处于选中态；而新的交互规定体型 / 声音只能选一个，点其中任一个都会把两个一起清掉，所以这个状态只能从旧存档来、界面无法再复现。**用户影响** —— 用户看到一行里两个档位同时高亮，会怀疑「单选」是不是坏了；摘要里也会同时写两个档位。**触发条件** —— 在旧版本选过「极限」的用户首次升级后打开精灵背包（`myPetsFilterStore.ts:91-101` 迁移；`MyPets.tsx:488-499` 的单选逻辑；`myPetsFilterStore.test.ts:81-92` 明确断言两项同时存在）。

② 优化方案：方案 A（推荐，保语义）——保留两项（并集恰好等于旧「极限」的语义），只把摘要文案写成「极限」一个词，并在体型行加一行说明；方案 B（保一致）——迁移时只保留先出现的一项，另一项丢弃并提示用户重新选择。A 不改筛选结果，B 会让部分用户的条件变窄。需要产品确认取哪一种，不确认前不要动迁移。

③ 优化后表现：**解决** —— 用户不会看到自相矛盾的双高亮。**验收** —— 用旧存档（只含 `body:极限`）启动，体型行只呈现一个符合预期的状态（A：摘要写「极限」；B：只剩一个档位高亮）。

## R6a-L02 · 低风险 · 导入了 0 只精灵、或把账号全取消时，页面让用户「取消部分标签」——但标签不是原因

① 问题描述：**现状** —— 列表为空时兜底文案固定写「没有符合条件的精灵，试试取消部分标签」；真正没数据（例如重置后还没导入、或导入的账号里没有精灵）也走这条文案，页面没有「去导入数据」的出口。**用户影响** —— 用户照着提示去取消标签，取消完还是空的，最后只能自己去「我的 · 游戏数据」找入口。**触发条件** —— 已存在账号快照但精灵数为 0，或账号筛选把所有账号取消（`MyPets.tsx:520-526` 只在 `accounts.length === 0` 时给 `EmptyState`；`:902-905` 的空列表文案不区分「没数据 / 筛选后为空」）。**说明** —— 该逻辑在 `779b08c` 已存在，不是本次引入，但本次把该组件重写了一遍仍未修。

② 优化方案：把空列表兜底拆成两种——`owned.length === 0` 时复用 `EmptyState`（带 `onGoImport`）；只有「有数据但筛选后为空」才显示「试试取消部分标签」，并顺带给出「重置筛选」按钮（已有 `clearInventoryFilters`）。

③ 优化后表现：**解决** —— 没数据的用户被直接指向导入入口，有数据的用户才知道要取消的是标签。**验收** —— 清空本地数据后打开「收集 · 精灵背包」，看到「还没有数据 + 去游戏数据导入」；保留数据并勾一个命中 0 的标签，看到「取消标签 / 重置筛选」。

① 现状：分面计数把体型、声音整类剔出已选条件，数字不再考虑这一档；用户影响：性格写着 6 点开 0，性别 / 稀有出现点得动却为空的死路；触发：先选档位再看其它筛选。（`MyPets.tsx:462-466`）

③ 表现：解决——性格与蛋组可点规则一致；验收——命中 0 的性格变灰、点不动。

**3. R6a-M01（双组模式计数按并集）**
① 现状：列表对两个蛋组取交集，计数按并集；用户影响：数字偏大、挑母本误判；触发：双组 + 两个蛋组后再看其它维度。（`MyPets.tsx:443-450` 与 `:459-469`）
② 方案：给 `computeFacetCounts` 增加「蛋组按交集」的选项并在双组模式传入。
③ 表现：解决——双组下数字与列表一一对应；验收——两只精灵的样例里，共有性格数字为 1、点开也是 1。

## 高风险

### R6b-H01 · 高风险 · 种公阵列里「别的号能补这颗蛋」和「加入配窝建议」整块消失，只剩存量任务能删不能加

① **问题描述**
**现状**：覆盖度页不再把自己的蛋名单交给种公阵列，阵列里嵌口格右下角的淡蓝「补」标记、点格弹出「其他号能出的所有蛋」、每条蛋右侧「加入配窝建议」这三件事一起消失，看板「配窝建议」里的跨号分组从此没有新增入口。
**用户影响**：小号养大号的玩家再也看不到「这个缺口小号A能配出火花 60%」，也做不了跨号补种公的待办，只能自己回两个号里翻。
**触发条件**：进「收集 · 种公」覆盖度，或从看板看配窝建议的「跨号补种公」分组——只要不是看代码，就再也进不来。
（`src/ui/Coverage.tsx:44-52` 已删掉 `transferTarget`/`transferPets` 计算，`:191-206` 调 `StudMatrix` 不再传这两个 prop；`src/ui/StudMatrix.tsx:49-51,126-127,159-167,483-489` 逻辑与按钮仍在，但 `transferTarget` 为空时整段不渲染；`src/ui/useOwnedPets.ts:23,35` 仍保留「给种公阵列跨号补缺用」的 `all`；需求依据 `docs/产品交互规范.md:191-193`、`src/data/changelog.json:102-103`（2026-11-03 已上线）；删除来自 `de0b394`，该提交未改规范也未写 changelog 说明下线。）

② **优化方案**
方案 A（推荐）：在 `Coverage.tsx` 恢复「当前只勾了一个账号时，取该号以外的全部精灵」这段十来行计算，把 `transferTarget`/`transferPets` 传回 `StudMatrix`，其余组件不用动，风险低、回滚容易。
方案 B：若产品确认要下线跨号补缺，则把 `StudMatrix` 里相关分支、`useOwnedPets.all`、`studTransferTaskStore` 一并删除，并同步删掉交互规范两条与 changelog，别留「规范说有、界面上没有」的半套。
两种都要先跟产品确认是「回归」还是「有意下线」，不能凭现状默认。

③ **优化后表现**
**解决**：只勾一个号看覆盖度时，缺口格里又能看到哪个小号能补、点开能选蛋、能一键记进看板配窝建议。
**验收**：导入两个账号 → 收集 · 种公 → 账号只勾一个 → 打开一个缺口格，应能看到「其他号可出的蛋」列表且每条带「加入配窝建议」；操作后回看板「配窝建议」应出现「目标号 ← 源号」分组。

### R6b-H02 · 高风险 · 看板「母本全收集」和点进去的母本页给出两个不同数字（默认设置下就不一致）

① **问题描述**
**现状**：看板卡现在用覆盖度的单一奖牌档位自己算一遍母本缺口，母本页仍按「个人母本达标条件（可四档多选）」算，两处不再共用同一份计数。
**用户影响**：默认设置下（看板默认只追「大婉」、个人母本条件默认不限档位）卡上显示「大婉 3/142」，点进去却看到「已收集 12/142」，用户会以为工具算错——这正是 2026-10-06 修过的同一个问题。
**触发条件**：任何账号里有「非大婉档」的达标母本，或用户在母本页把达标条件改成了别的组合，看板卡都不会跟着变。
（`src/ui/Dashboard.tsx:53-61` 用 `selectedGrade` 覆盖 `motherCriteria.grades`，`:70-74` 自算 `missingMothers`，`:239-248` 用它当分子；`src/ui/MotherView.tsx:254-264` 仍用 `criteria.grades`；共享口径在 `src/ui/useCollectionSummary.ts:66-83`（`mother.collected`）已不再被看板使用；需求依据 `docs/产品交互规范.md:17`「个人母本条件只影响个人清单和看板母本进度」、`src/data/changelog.json:709`「看板卡与母本页同一口径」、`src/domain/motherCriteria.ts:16-18` 注释；既有 e2e `e2e/dashboard.spec.ts:70-85` 仍在断言两者数字一致。）

② **优化方案**
方案 A（推荐，与「目标奖牌组合（公母共用）」文案一致）：把档位统一到一处——母本页也读同一个单选档位（或在看板选档时同步写回个人母本条件），看板继续用 `useCollectionSummary().mother.collected`，两页天然同源，改动约 10 行 + 一处 store 写入。
方案 B：看板卡改回 `mother.collected` / `mother.total`，母本缺口列表也改回个人条件，代价是「公母共用」这句文案要改，且看板不能再靠选档位筛母本。
口径二选一需要产品拍板（规范 21 行说「公母共用」，17 行说「个人母本条件决定看板母本进度」，两条互相矛盾）；确认前不要自行统一。

③ **优化后表现**
**解决**：同一份母本数据，看板卡与母本页显示同一个「已收集 N / M」，用户点进去数字不跳变。
**验收**：导入含非大婉母本的账号 → 记下看板「母本全收集」分子 → 点卡进母本页 → 顶部的「已收集 N」应与之相同（即 `e2e/dashboard.spec.ts:70-85` 恢复通过）。

## 中风险

### R6b-M01 · 中风险 · 新用户（还没有账号）时，看板的「目标模式」开关和收集页三张入口卡会错位、右侧空出一列

① **问题描述**
**现状**：账号数为 0 时账号控件返回空，但父级网格仍按「账号列 + 3 列」预留位置，剩下三个元素挤在前三列，右边留一块空白；收集页三张入口卡宽度也会和平时不一样。
**用户影响**：第一次打开、还没导入数据的人（也是教程第一屏）看到的是排歪的顶栏，第一印象就是「这页坏了」。
**触发条件**：本机没有任何账号快照时进入看板或收集页。
（`src/ui/Collection.tsx:92-96` 固定 `grid-cols-[minmax(76px,0.8fr)_repeat(3,minmax(0,1fr))]`，账号槽在 `src/ui/AccountFilterBar.tsx:19` 无账号时 `return null`；看板 `src/ui/Dashboard.tsx:110-158` 同样固定三列，账号按钮在 `:115` 才有条件渲染。）

② **优化方案**
把「有没有账号」提到网格层：无账号时不渲染账号槽，收集页退回 `grid-cols-3`，看板退回两列（`auto + 1fr` 右对齐目标模式）；或给账号槽一个占位元素并保持列宽。各改两三行，不涉及数据。

③ **优化后表现**
**解决**：还没导入数据时，看板目标卡与收集页三张卡都是正常对齐的，不会出现空白列。
**验收**：清空浏览器数据后打开站点 → 看板目标卡里的「追满分 / 追双牌」贴右、收集页三张卡等宽三等分；375 与 390 宽各看一次。
