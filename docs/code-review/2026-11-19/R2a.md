## R2a-H01 · 高风险 · 打开「换蛋广场」时后端会把全站所有小组的换蛋数据整份读出来重算，小组越多页面越慢，机器人提醒也跟着变慢

**① 问题描述**
**现状**：取巡查状态的函数每次都先调 `activePatrolTasks`，后者一条 SQL 就把**所有**已接入机器人的小组的整份 `state_json` 取回来、在 JS 里逐个 `JSON.parse`，再按小组一条一条查成员；读状态的函数本身又被四个入口无条件调用。
**用户影响**：换蛋广场页开着时每 20 秒自动刷新一次，每次刷新都把全站小组数据扫一遍再重算，用户看到的是「越用越卡、偶尔转圈很久」，量大之后会撞 D1 单次请求的查询与 CPU 上限，表现为「换蛋服务暂不可用」以及群里提醒明显延迟。
**触发条件**：任意用户停留在换蛋广场，或 QQ 机器人按分钟级调用 tick / claim —— 只要站上有几十个接了机器人的小组就会触发。
（证据：`functions/_lib/eggPatrolStore.ts:36-46` 的 `SELECT` 取全表 `state_json` + 第 44-46 行逐组查成员；`eggPatrolStore.ts:66` 每次读取都先走这一步；调用点 `functions/_lib/eggMatching.ts:90`、`functions/_lib/eggBotBridge.ts:23/92/116/125`；前端刷新频率 `src/ui/plan/useEggMatching.ts:46`。）

**② 优化方案**
把「全站」收窄成「当前这个人关心的那一两个组」：给 `activePatrolTasks` 增加按小组过滤的参数（`WHERE e.group_id IN (…)`），成员查询改成一次 JOIN 或按 group_id 批量查，不再每组一条；广场读取只查当前小组，机器人领取/校验/回执只查该机器人绑定的组，tick 先算出本轮要巡的 uid 与所属组再按组查。
改动约 40~60 行、不涉及表结构；风险是过滤条件写错会漏提醒，必须用现有的 `tools/test/egg-patrol-api.test.mjs` 全量回归（尤其「同 UID 跨组只查一次」和「跨组重绑后旧租约失效」两条）。

**③ 优化后表现**
**解决**：打开和刷新换蛋广场的耗时不再随全站小组数量增长，机器人提醒延迟与站点规模解耦。
**验收**：`npx tsc -p functions/tsconfig.json` 通过；在测试里用现有那套「计数型假 DB」加一条用例：存在 A、B 两个组各一条任务时，读 A 组发出的 SQL 条数不随 B 组数据量变化。

## R2a-H02 · 高风险 · 蛋被收走之后，任务卡会从「发现产出 · 已提醒」退回「已上窝 · 等待产出」

**① 问题描述**
**现状**：写「已上窝」记录时只跳过**本轮还在地上的蛋**（用本轮观察结果拼出的集合判断），而「已上窝」和「已产出」是两行不同的记录（一个用空蛋实例号、一个用真实蛋实例号），读状态时按记录时间取最新的一行——蛋一收走，本轮就没有产出观察了，于是「已上窝」这行被刷新成最新。
**用户影响**：群里刚收到「XX 已产出，请收蛋后交给对方」，用户收完蛋回到任务卡，状态行已经变回「已上窝 · 等待产出」，看起来像那条提醒不作数、或者蛋还没收干净；「这颗蛋已经提醒过」的凭据也就没了。
**触发条件**：亲本还留在窝里、蛋已被收进背包——这正是上窝之后的正常状态（现有测试本身就按「只有配对、没有蛋」建模），下一次巡查（≤30 分钟）就会发生。
（证据：`functions/_lib/eggPatrol.ts:96-104` 的 `producedKeys` 只来自本轮 `observeSceneEggs` 结果，placed 用 `actor_id=''` 写独立行；`eggPatrol.ts:95` 注释与提交 `43f1639` 的说明都写「已经产出的同一任务不再回写『上窝』」，即意图本是不许回退；读取按 `observed_at` 取最新 `eggPatrolStore.ts:70`；卡片文案 `src/ui/plan/EggTasksPanel.tsx:76-77`；「配对在场、蛋不在场」的正常性见 `tools/test/egg-patrol-api.test.mjs:283-294`。）

**② 优化方案**
A（推荐）在写侧让「已产出」优先：写「已上窝」时若该任务已有产出记录就不覆盖（`ON CONFLICT` 分支按状态判断，或写入前加 `AND NOT EXISTS(同一 task_key、status='produced')`）。B 只在读取侧把「已产出」排在「已上窝」前面，改动更小，但表里仍留着一条与事实相反的状态，后续按状态做统计或对账仍会错。
两种方案都不影响「同一对亲本再产一颗蛋时重新提醒」——那是新的蛋实例、新的记录行。改动 5~10 行，不涉及表结构；需要产品先一句话确认口径：**同一任务提醒过产出后，是否允许状态退回上窝**（按现有注释的本意是不允许）。

**③ 优化后表现**
**解决**：收蛋后状态稳定停在「发现产出 · 已提醒」，直到换蛋完成或用户换配对。
**验收**：`node --test tools/test/egg-patrol-api.test.mjs`，并补一条用例：先「配对+蛋」得到产出，再把场景改成「只有配对」跑一轮，状态仍应为产出。

## R2a-M01 · 中风险 · 换蛋广场的巡查状态每个任务要发 3 条 SQL，其中一条要扫全表并解析 JSON，历史提醒越积越多越慢

**① 问题描述**
**现状**：读状态时对每个任务依次查巡查缓存、查观察记录、查通知记录，通知那条用 `json_extract(payload_json,'$.taskKey')` 做等值匹配、还用 `ORDER BY created_at` 排序，两者都没有可用索引；而通知表按「同一颗蛋 2 小时一次、每天最多 4 次」持续追加，无人清理。
**用户影响**：小组里任务和提醒历史越多，广场刷新越慢；长期看这张表只增不减，一年后每次刷新都要在几万行里做 JSON 解析和排序。
**触发条件**：任何有提醒历史的小组，任务越多、用得越久越明显。
（证据：`functions/_lib/eggPatrolStore.ts:68-76`（第 72-74 行 `json_extract` + `ORDER BY created_at`）；通知持续追加 `functions/_lib/eggPatrol.ts:128-138`；表结构无 task 列 `functions/schema.sql:560-568`。）

**② 优化方案**
给通知表加一列 `task_key`（写通知时一并落库）并建 `(group_id, task_key, created_at)` 索引，把 JSON 解析比对换成等值查询；顺手把「每任务 3 条 SQL」合并成本组一次批量查询再在内存里配对。
涉及加列 → 需要一条新的可重入迁移（`ALTER TABLE ... ADD COLUMN`），并同步 `functions/schema.sql`；代价是 R2b 的迁移一致性检查要一起过一遍。

**③ 优化后表现**
**解决**：广场刷新耗时不再随历史提醒条数增长。
**验收**：迁移执行后 `node --test tools/test/egg-patrol-api.test.mjs` 通过；并在假 DB 上断言一次状态读取只发出常数条 SQL。

**② 优化方案**

**③ 优化后表现**
**解决**：每轮巡查的读写量与账号数解耦，D1 写入量明显下降。
**验收**：`npx tsc -p functions/tsconfig.json` + `node --test tools/test/egg-patrol-api.test.mjs` 全绿（方案 A 不改测试）。

## R2a-M03 · 中风险 · 换蛋接口把内部异常原文直接当「操作失败」弹给用户，服务故障也被说成是用户操作不对

**① 问题描述**
**现状**：换蛋接口的兜底只识别两类异常（数据库约束冲突 → 409、表缺失/数据库错误 → 503），其余一律按「操作不合法」返回 400，并把原始异常文本原样回传；前端把这个文本直接当提示语显示。
**用户影响**：出现空指针、JSON 结构不符这类内部错误时，用户看到的是英文报错（例如 `Cannot read properties of undefined`），既看不懂也不知道该不该重试；而且这类异常没有写日志，线上排查看不到。
**触发条件**：任何非约束、非数据库类的异常——代码缺陷、上游字段变化、状态结构不符。
（证据：`functions/_lib/eggMatching.ts:146-153` 的兜底分支；前端原样展示 `src/api/eggMatching.ts:43`、`src/ui/plan/useEggMatching.ts:62`。）

**② 优化方案**
照同目录既有写法收口：未识别异常先打 `console.error`，再返回 500 `INTERNAL`「服务器出错了」；只有业务规则明确拒绝时才回 400 并带可读文案（可给业务错误加一个自定义错误类，与既有做法同构）。
依据：参照 `functions/_lib/collectionGroups.ts:211-212` 既有写法（未识别异常 → 打日志 + 500 `INTERNAL`「服务器出错了」）。改动约 10 行。

**③ 优化后表现**
**解决**：用户只会看到中文可操作提示，内部错误进日志可追。
**验收**：构造一条会抛非业务异常的输入（或用测试 mock 让动作处理函数抛出普通 `Error`），断言返回 500 + `INTERNAL`，而不是 400 + 英文原文。

## R2a-L01 · 低风险 · 一条删除语句没有租约守卫，极端情况下会删掉上一条「已产出」记录却没有补上新的

**① 问题描述**
**现状**：「任务重建时先让位」的那条删除语句不带租约条件，而同批次其它写入都要求「租约仍然属于本轮」；一旦租约在写批之前被别的巡查轮次接管，删除照旧执行、补写被跳过。
**用户影响**：极端情况下某颗蛋的产出记录会凭空消失一轮，任务卡短暂回落到「待巡查」，下一轮才会恢复。
**触发条件**：单轮处理（上游请求 + 写批）超过 60 秒租约、且恰好被另一轮接管。
（证据：`functions/_lib/eggPatrol.ts:109-112` 的 `DELETE` 无 `EXISTS(... lease_token=?)`，对比同函数 `:100-103`、`:113-116` 的写法。）

**② 优化方案**：给这条删除补上与其它写入相同的租约守卫（`AND EXISTS(SELECT 1 FROM egg_patrol_cache WHERE uid=? AND lease_token=?)`），一行条件、无表结构变更。

**③ 优化后表现**：**解决** —— 租约失效时不会再单方面删数据。**验收**：现有 `node --test tools/test/egg-patrol-api.test.mjs` 通过，并补一条「租约被接管时旧产出记录不被删除」的用例。

## 最该先修的 3 条

### 1. R2a-H02 · 收蛋后任务卡从「发现产出 · 已提醒」退回「已上窝 · 等待产出」
① 问题描述：产出记录被随后写入的「已上窝」记录顶掉，读取只认最新一条。
② 优化方案：写「已上窝」时若该任务已有产出记录就不覆盖（A 方案，5~10 行），并请产品确认「产出后是否允许回退」。
③ 优化后表现：收蛋后状态停在「发现产出 · 已提醒」，不会被误认为提醒作废；用 `node --test tools/test/egg-patrol-api.test.mjs` + 一条「蛋收走后仍为产出」用例验收。

### 2. R2a-H01 · 每次刷新换蛋广场都扫全站小组，越用越慢
① 问题描述：取巡查状态时先把所有小组的整份换蛋数据读出来并解析，而广场每 20 秒刷新一次。
② 优化方案：把读全站改成按小组过滤 + 成员一次批量查，只查当前小组/当前机器人绑定的组（40~60 行，配现有测试回归）。
③ 优化后表现：页面打开与刷新不再随全站小组数变慢；用 `npx tsc -p functions/tsconfig.json` 与「SQL 条数不随其它小组增长」的用例验收。

### 3. R2a-M03 · 内部异常原文被当成「操作失败」弹给用户
① 问题描述：换蛋接口兜底只分约束冲突与数据库错误两类，其余一律 400 并回传原始异常文本，且不打日志。
② 优化方案：照 `functions/_lib/collectionGroups.ts:211-212` 的既有写法，未识别异常打日志后返回 500 `INTERNAL`「服务器出错了」（约 10 行）。
③ 优化后表现：用户只看到中文可操作提示，内部错误进日志；用「抛普通 Error 时返回 500 + INTERNAL」的用例验收。
