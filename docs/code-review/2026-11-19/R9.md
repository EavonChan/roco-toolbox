## 高风险

### R9a-H01 · 高风险 · 走远或已经被抓走的精灵会一直留在地图和列表上

① 问题描述：
- **现状**：实时巡检每轮只刷新「本轮新增字节」里那句精灵的最后出现时间，随后把精灵表写回跨轮基线；但基线只保存精灵本身，不保存这份时间戳，下一轮从基线恢复出来的精灵没有出现时间，「9 秒没更新就释放」的判断被直接跳过，永不释放。
- **用户影响**：玩家走开、别人抓走、或精灵消散之后，附近页常驻列表与悬浮窗地图仍挂着它的点位（幽灵点），蹲守时会照着旧点位跑；只有等下一次「330 全量帧」或撞到 80 只容量上限才会消失。
- **触发条件**：真机实时采集连续跑超过 9 秒、且这期间没有新的 330 全量帧（悬浮窗/附近页的正常使用状态）。
- **技术证据**：（`core.js:1904-1908` 用 `wildSeenAt` 判过期；`core.js:2335/2387/2461/2533` 的 baseline 只保存 `pets` 与 `capturedWild`，`wildSeenAt` 不进基线；`core.js:2570` 导出前再跑一次 prune 也救不回来）

② 优化方案：
把 `wildSeenAt`（以及同根因的 `capturedWildAt`）一起放进 `nearbyBaseline` 与 `exportLiveDecodeState/importLiveDecodeState`，恢复时用「本轮 now」重新计时，而不是照搬旧时间戳——否则停一轮采集就会整批判过期。同一处顺带修墓碑：现在恢复后只剩 Set、没有时间，会落到「旧墓碑永不复活」分支，同一 `uniqueId` 重新刷出时永远不显示。改动约 20~30 行、只碰解码内部状态，不影响导入与协议解析。

③ 优化后表现：
**解决**：精灵离开视野或被别人抓走后约 9 秒自动从列表与地图消失；抓过的个体按 30 秒解禁，不会永久消失。
**验收**：真机开始采集，在野外走出一只精灵的视野后原地静止 10 秒以上，看悬浮窗列表与地图点位是否自动清掉；或连续采集时观察 `nearbyWildDiagnostics().evicted` 是否随走动增长（当前恒为 0）。

## 中风险

### R9a-M01 · 中风险 · 附近常驻列表会把只有体型牌 / 声音牌的普通精灵也留 10 分钟

① 问题描述：
- **现状**：常驻列表的「高价值」判定新增了「稀有」一项，而「稀有」在采集侧的定义是「有任何牌子就算」（体型、声音牌都算），于是单牌子普通精灵也被当作高价值，离开视野后继续保留 10 分钟；与其正下方「只有单一体型 / 声音牌的普通精灵不再进入常驻列表」的注释直接冲突。
- **用户影响**：常驻列表条目明显变多（上限 60 条），玩家翻列表找真正稀有的目标时被一堆普通精灵淹没，且这些条目已不在视野，容易误判成「还在附近」。
- **触发条件**：附近出现带任意牌子的普通精灵并让它离开视野；「稀有」这一档筛选与列表口径也会跟着放大。
- **技术证据**：（`nearbyRetain.ts:43-48` 新增 `pet.rare ||`，`wildNearby.ts:130` 里 `rare: kinds.length > 0`；`nearbyRetain.ts:40-41` 的注释仍写着单牌子不常驻；配套测试 `nearbyRetain.test.ts:79-84` 把这类用例改成 `rare: false`，而真实数据里 `kinds` 非空必然 `rare: true`，该断言永远跑不到）

② 优化方案：
二选一，需要产品拍板：A（推荐）把「稀有」收窄成真正的稀有标记（炫彩 / 异色 / 污染或主动提醒），体型牌、声音牌不算；B 保留当前口径但删掉注释里的排除条款，并把测试改成真实可达的数据组合（`kinds: ['big'], rare: true` 断言为「常驻」）。选 A 时同步检查附近页「稀有」档位是否也要收窄，避免页面与悬浮窗两套口径。

③ 优化后表现：
**解决**：常驻列表只留下真正值得回头找的精灵，条目数量回到可用范围。
**验收**：打开附近页，制造一只只有声音牌的普通精灵并离开视野，10 分钟内它不应留在常驻列表；带炫彩 / 异色的精灵离开后仍应保留。

### R9a-M02 · 中风险 · 背包里算「大块头」的精灵不会命中「大块头」需求

① 问题描述：
- **现状**：需求中心与悬浮窗的体型匹配改成「体重 ≥98% 且身高 ≥98%」才算大块头，而工具箱其它地方（奖牌 / 展示 / 需求口径）用的是「有奖牌按奖牌；没奖牌时身高正好 100% 且体重 ≥95%」；两套阈值并存，同一只精灵会给出不同答案。图鉴没有收录身高区间的精灵（约 29 个 cfg 编号对不上主图鉴）根本没有身高百分位，这类精灵的任何体型需求都永远不命中。
- **用户影响**：玩家按背包/蛋仓里看到的「大块头」发布需求，附近真的出现这只精灵时却不提醒、不进列表，等于需求中心对体型条件失效。
- **触发条件**：发布带「大块头 / 小不点」条件的需求，命中精灵的体重与身高落在两套阈值之间（如身高 100%、体重 96%），或该精灵图鉴缺身高区间。
- **技术证据**：（`demandMatch.ts:42,44` 的 98/98 双阈值；`src/shared/bodySize.d.ts:16` 明确 `bodyGradeOf` 是「奖牌 / 展示 / 需求口径」，实现见 `bodySize.js:73-83`）

② 优化方案：
把 `demandMatch` 的体型判定改成调用 `bodyGradeOf({ medalBody, heightPercent, weightPercent })`（或把两处阈值抽成同一个函数），保证「需求命中」与背包里看到的体型标签同源；图鉴缺身高时不命中属于合理退化，但需要在需求卡上写清「该精灵缺身高数据，体型条件不参与判定」，避免用户以为需求坏了。改动 10~20 行，会改变现有需求的命中结果，需要与产品确认统一后一次落地。

③ 优化后表现：
**解决**：背包里显示「大块头」的精灵，只要出现在附近就会命中「大块头」需求并进列表 / 发提醒。
**验收**：用一只已知身高 100%、体重 96% 的精灵跑 `npx vitest run src/pcap/demandMatch.test.ts`（补一条对应断言），或真机发布「大块头」需求后靠近它，确认列表与提醒都命中。

## 低风险

### R9a-L01 · 低风险 · 悬浮窗推送的节流说明与实际不符
① 问题描述：桥接文件顶部写着「节流 800ms」，实际推送窗口是 250ms，维护者按注释调参会得到错误结论。技术证据：（`overlayBridge.ts:10` 与 `useNearbyOverlayPush.ts:24`）
② 优化方案：把注释改成 250ms，或直接写「见 `useNearbyOverlayPush` 的 `PUSH_INTERVAL_MS`」，避免两处数字各自漂移。
③ 优化后表现：**解决**：查节流时只认一个数字。**验收**：搜「800ms」不再命中悬浮窗节流说明。

### R9a-L02 · 低风险 · `readScene` 是没有任何调用方的死导出
① 问题描述：`wildNearby.readScene` 已无调用方（场景解析改由 `core.js` 内部按 opcode 区分 338/348），留着会让人以为 348 也走它。技术证据：（`wildNearby.ts:142-144`，全仓仅测试文件引用过 `wildNearby` 的其它导出）
② 优化方案：删除该导出；若担心外部脚本使用，改为在注释里标注「仅供诊断，勿用」。
③ 优化后表现：**解决**：少一个误用入口。**验收**：`npx vitest run src/pcap` 仍全绿。

### R9a-L03 · 低风险 · 导出附近列表时用逗号运算符夹带清理，靠执行顺序生效
① 问题描述：`nearbyPets: (pruneWildPets(capture), Array.from(...))` 把「先清理再导出」藏在表达式里，读代码时看不出清理是导出的一部分，重构时容易丢。技术证据：（`core.js:2570`）
② 优化方案：在构造返回对象前先单独调一次 `pruneWildPets(capture)`，返回里只写 `Array.from(...)`。
③ 优化后表现：**解决**：导出语义可读。**验收**：`npx vitest run src/pcap/wildNearby.test.ts` 全绿。

### R9a-L04 · 低风险 · 每个上行帧都做 41 次偏移探测，且有一处永远走不到的分支
① 问题描述：为了不依赖固定前缀长度，自身坐标解析从 0 到 40 逐字节尝试解析，且上行帧不再只挑 307 类型，所有非握手帧都先解密再跑这轮探测；探测里的「解析失败就跳过」分支实际不会触发（解析函数不抛错、也不返回空），等于每帧固定跑满 41 次。目前帧小、成本低，但属于随帧量线性放大的热点。技术证据：（`core.js:59-79` 的偏移循环与 `if (!fields) continue`，`parseLooseProto` 见 `core.js:190-225`；`core.js:1411` 放开上行帧筛选）
② 优化方案：先按帧长与前几字节做一次廉价预筛（例如只有解密结果长度落在典型移动帧区间才进入偏移循环），并把死分支改成真正的失败判断；是否值得做以真机 `__rocoPerf.capture()` 的 `decodeAvg/decodeMax` 为准，不达标再优化。
③ 优化后表现：**解决**：解码耗时不随花屏/心跳帧增长。**验收**：真机采集后看 `__rocoPerf.capture()`，`decodeMax` 与改动前同量级（当前若已 <5ms 可不改）。

### R9a-L05 · 低风险 · 连点两次「检查更新」时，第一次的 10 秒兜底会把第二次打回未检查
① 问题描述：每次触发检查都排一个 10 秒定时器，定时器到点只要状态还是「检查中」就改回「待检查」；如果用户 10 秒内点了第二次且壳还在请求，第一个定时器会把第二次的「检查中」提前清掉，按钮闪回可点状态。技术证据：（`appUpdate.ts:72-74`）
② 优化方案：定时器里加一次序号比对（只让最后一次检查的定时器生效），或触发新检查前先清掉上一个定时器。
③ 优化后表现：**解决**：连点只按最后一次检查结算。**验收**：真机连点两次「检查更新」，按钮不会在中途闪回；壳 10 秒无响应时仍能恢复可点。

### R9a-U01 · 不确定 · 「大块头 / 小不点」到底该按体重还是按体重+身高双维度
① 问题描述：附近牌子与稀有判定这次改成「体重与身高同时到顶/到底」，注释说是「游戏真实奖牌口径（2026-11-10）」；但同仓另一套奖牌实现仍按体重 2%/98% 单维度，`docs/domain/` 里也没有这条规则的明文。两套实现会让同一只精灵在「附近牌子」与「背包奖牌」上给出相反结论。技术证据：（`rareRules.ts:58-63` 注释与 `bodySize.js:21-27` 的 `bodyMedalOf` 单维度阈值）

③ 优化后表现：**解决**：同一只精灵在背包、附近、悬浮窗看到的体型结论一致。**验收**：`npx vitest run src/pcap/rareRules.test.ts src/pcap/bodySize.test.ts` 中补一条「同一输入两处结果相同」的对照断言。

## R9b-H01 · 高风险 · 正式包里「服务器地址」面板会把正式站写成「测试服（默认）」，兜底默认站还写死了测试站

**① 问题描述**
- 现状：面板的当前/默认两行不读壳返回的通道，而是拿 `defaultUrl` 当「测试服」并硬编码文案；网页侧缺字段时的兜底常量也直接写死测试站。
- 用户影响：正式包用户在「我的」连点版本号 5 次打开面板，看到的是「当前：测试服（默认）https://roco-toolbox.pages.dev / 默认：测试服 https://roco-toolbox.pages.dev / 正式：正式服 https://roco-toolbox.pages.dev」——三行地址同一个、通道标错，用户会以为自己正在内测站上操作。
- 触发条件：正式通道 APK（`build.gradle` 里 `DEFAULT_SERVER_URL` = 正式站、`TEST_SERVER_URL` 为空）→ 我的 → 连点版本号 5 次（快切失败也会自动打开本面板）。

**② 优化方案**

- **用户影响**：在功能分支上 `npm run build` 之后直接执行发版命令，脚本会一路绿灯把正式站顶到没被核对过的代码上——`docs/发版与更新规范.md` §4.2（「先提交、再构建」「工作区干净」）与 2026-11-10 事故就是这一类；一旦发出去，回滚与复盘都找不到对应提交。
- **触发条件**：非 release 分支构建 → `node scripts/deploy-web.mjs --branch main --approve-production`（不带/带 `--dist` 都行）。
- **证据**：`scripts/deploy-web.mjs:34,48-51,138-157` 与 `docs/发版与更新规范.md:188-198` 对照；脚本里没有任何 `git` 调用。

② **优化方案**
A) 部署前读 `git rev-parse --abbrev-ref HEAD` 与 `git status --porcelain`：分支不是 `release`（或指定的正式分支）或工作区有改动就中止，并打印本次 HEAD 提交；需要临时验证包时显式加 `--allow-dirty`。约 15 行，风险是 worktree / 直接拷仓库的用法要补参数；
B) 只做告知：打印 HEAD 提交并要求 `--expect-hash` 必填。
推荐 A（真正挡住越界），B 只降低误发概率。

③ **优化后表现**
- **解决**：发版人不会再在「绿灯」下把功能分支的产物推上正式站。
- **验收**：在非 release 分支上跑 `node scripts/deploy-web.mjs --branch main --approve-production --dry-run`，脚本非 0 退出并指出当前分支；在 release 且工作区干净时仍能正常打印 bundle 与 SHA-256。
