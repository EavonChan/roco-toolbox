## R5-H01 · 高风险 · 以前勾过多档或清空过档位的用户，母本「已收集」会变成 0 或把没显示的档位也算进去

**① 问题描述**
**现状**：本地存的「档位组合（选中哪几个奖牌档，如大婉/小婉）」是数组，读取时原样保留；判定时对数组里**每一个**档位做「或」匹配，但界面上单选只显示数组第一个（数组为空时强行显示「大婉」）。
**用户影响**：以前多选勾过两个档的用户，页面显示「大婉」却把小婉/小粗的母本也计入「母本全收集」；以前把档位全部取消的用户，界面仍显示「大婉」但收集数是 0，看起来像数据丢了。
**触发条件**：升级前在旧的多选界面里勾过 2 个以上档位，或把唯一档位点掉（本地存储里是 `{"grades":["大婉","小婉"]}` 或 `{"grades":[]}`）。
（证据：`src/domain/motherCriteria.ts:88-90` 用 `criteria.grades.includes(grade)` 对全数组取或；`src/ui/motherCriteriaStore.ts:46` 迁移时只过滤不归一；`src/ui/MotherCriteriaMedals.tsx:81-84` 只取 `grades[0] ?? '大婉'` 展示；同口径被 `src/ui/useCollectionSummary.ts:74`、`src/ui/MotherView.tsx:257` 直接使用；旧版多选可清空见 `git show 3dacef9:src/ui/MotherCriteriaMedals.tsx` 的 `toggleGrade`。）

**② 优化方案**
把三处口径收成一处：A 方案在本地存储迁移时把档位数组归一成单个（保留第一个合法值），空数组按「未选档位」处理并在界面上如实显示未选，不再伪显示「大婉」；B 方案不动存储，判定时只认 `grades[0]`，与界面展示保持一致。推荐 A（存量一次性修正、语义清楚），代价约 10~20 行并需给旧数据补一条迁移用例；B 改动更小但「空数组 = 没有组合」这条注释语义要同步改写。

**③ 优化后表现**
**解决**：母本页和看板显示的档位与「已收集 / 共 N」的数字永远对得上，不再出现「显示大婉却算出 0」。
**验收**：预置 `roco.motherCriteria` 为 `{"grades":[]}` 与 `{"grades":["大婉","小婉"]}` 后打开收集页，数字与所选档位一致；`npx vitest run src/domain/motherCriteria.test.ts` 增加这两个存量用例。

## R5-M01 · 中风险 · 家园地上的蛋明明按新口径能判定体型，却显示「体型待确认」

**① 问题描述**
**现状**：家园蛋按父母推算体型时，仍用「奖牌，或身高 100% **且**体重 ≥95%」的旧口径；而母本/种公/档位已经改成「身高 100% 单独等效大块头」的孵蛋口径。
**用户影响**：一对身高到顶、体重只是中等（没有奖牌）的父母，在母本页/档位里算「大块头/大婉」，但在家园蛋卡片上被算成体型未知，用户会以为这颗蛋不是满体型蛋，可能因此不接单、不换。
**触发条件**：家园住户里的父母没有体型奖牌、身高百分位为 100%（或 0%），且体重百分位不在 98% / 2% 档内。
（证据：`src/ui/plan/homeEggAdapter.ts:159-167` 用 `bodyGradeOf` 推蛋的体型，`src/ui/plan/homeEggAdapter.ts:5` 引入的正是旧口径函数；对立面为 `src/domain/petFilters.ts:156`、`src/domain/motherCriteria.ts:77` 已改用 `breedingBodyGradeOf`；口径来源 `src/data/changelog.json`「2026-11-17a」第 1 条。）

**② 优化方案**
把「蛋的体型推算」改用孵蛋口径（身高 100% / 0% 等效）。父母卡片上的体型标签属于奖牌展示，可保持现状不动，避免把没奖牌的精灵展示成「大块头」；只需替换 `homeEggAdapter` 里推导 `body` 的那两三行，改动小、无表结构影响。

**③ 优化后表现**
**解决**：家园蛋的体型与母本/档位判断一致，满身高父母配出的蛋直接显示「大块头」，不再是无意义的「待确认」。
**验收**：造一母一父「无奖牌 + 身高 100% + 体重 50%」的家园快照，蛋卡片显示「大块头」；`npx vitest run src/ui/plan/homeEggAdapter.test.ts` 增加该用例。

**① 问题描述**
**现状**：体型筛选声明了「身高 / 体重两个维度」的类型和两套默认区间，但没有任何调用方；真正参与筛选的只有身高范围。

**触发条件**：只有读代码/接新功能时才会踩到。
（证据：`src/domain/petFilters.ts:29-41` 的 `WeightRange` / `DEFAULT_WEIGHT_RANGE` / `SizeField` / `DEFAULT_SIZE_VALUE_RANGES` 在生产代码中零引用；实际筛选入口只有 `src/ui/MyPets.tsx:425` 的 `matchesHeightRange(pet.heightPercent, …)`。）

**② 优化方案**
删掉未被使用的类型与常量（或把体重筛选真正接上再保留注释）；若只是留作扩展，把注释改成「暂未接入体重筛选」，避免误导。

**③ 优化后表现**
**解决**：代码里不再存在「声明了但没实现」的筛选维度，读者不会再据此误判。
**验收**：`npx tsc -b` 通过（删除导出后无引用报错），全仓检索 `DEFAULT_SIZE_VALUE_RANGES` 无结果。

## R5-U01 · 不确定 · 「需求匹配 / 有现货」到底该按奖牌算还是按身高算，代码和它自己的说明相反

**① 问题描述**
**现状**：体型工具的说明里把「奖牌 + 身高 + 体重」写为需求口径、把「只看身高」写为孵蛋口径；但需求匹配模块（判断「我有没有现货」「谁能接单」）用的却是后者。
**用户影响**：若需求口径本应是奖牌，则没有奖牌、只是身高到顶的个体会被当成「已有现货」，用户以为能交单、实际交付可能不被认可；反之若按身高算，则当前行为正确、只是说明文字过期。
**触发条件**：需求写的体型是「大块头/小不点」，而本地个体的奖牌与身高结论不一致（身高 100% 但体重只有 50%）。
（证据：`src/shared/bodySize.d.ts:15` 注释把 `bodyGradeOf` 定义为「奖牌 / 展示 / 需求口径」，`:21` 把 `breedingBodyGradeOf` 定义为「母本 / 种公 / 档位」；`src/domain/demandCriteria.ts:44` 的需求匹配与 `:51-60` 的现货/满体重判定都用了 `breedingBodyGradeOf`。置信度：中。）
**需要谁确认**：产品/用户拍板「需求匹配与现货校验」用哪套体型口径；确认前不要改这两行，否则会同时影响接单判断与结单校验。

**② 优化方案**
若确认为需求用奖牌口径：把 `demandCriteria.ts` 的 `bodyOfPet` 与满体重/零体重分支改用 `bodyGradeOf`，并补一条「身高 100% + 体重 50% 不算现货」的用例；若确认按身高口径：只改 `bodySize.d.ts` 的注释与本条结论。两种都只动 1~2 处，无表结构影响。

**③ 优化后表现**
**解决**：需求能不能接、有没有现货，与用户理解的奖牌/身高定义一致，不再出现「工具说能交、对方说不对」。
**验收**：口径定下后，`npx vitest run src/domain/demandCriteria.test.ts` 增加「身高 100% + 体重 50%」的正/反用例并稳定通过。

## R5-U02 · 不确定 · 蛋「能不能拿去换」依赖的「特殊/异色」标记，领域文档里没有定义

**① 问题描述**
**现状**：蛋仓把抓包字段直接翻译成「普通 / 异色 / 特殊」，其中「特殊」由「不是普通蛋」「珍贵蛋类型非 0」「特殊蛋配置号 >0」等多项推断；不可流通的蛋会被挡在换蛋之外。
**用户影响**：如果这些字段的真实含义与推断不符（例如某个「特殊」只是活动来源、仍可赠送），用户会发现自己明明能送的蛋在工具里选不了；反过来也可能把不可送的蛋列进换蛋。
**触发条件**：抓包里的蛋带 `isOrdinary=false`、`preciousEggType≠0`、`specialEggConfId>0`、`appearanceType>0` 或 `extensionType>0` 中任意一项。
（证据：`src/domain/eggInventory.ts:15-21` 的 `capturedEggKind` 与 `src/shared/eggMatching.ts:107-109` 的 `canCirculateEgg`；`docs/domain/数据字段说明.md` 只写了蛋仓有 `weightGrams` / `petName`，未定义上述字段语义。置信度：低。）
**需要谁确认**：采集/运维侧（谁负责抓包字段字典）确认 `isOrdinary`、`preciousEggType`、`specialEggConfId`、`appearanceType`、`extensionType` 的真实含义；确认前不要把这条当缺陷改代码。

**② 优化方案**
确认后把字段语义补进 `docs/domain/数据字段说明.md`，再按语义收紧 `capturedEggKind`；若暂时无法确认，改为「只把确定不可送的标记算特殊，其余先在界面上标『待确认』而不是直接禁止流通」。

**③ 优化后表现**
**解决**：换蛋广场里的可选蛋与游戏内实际可赠送范围一致，不会出现「能送却选不了」或「选了送不出去」。
**验收**：用一份含上述各字段的真实蛋仓备份导入，蛋仓卡片上的「普通/异色/特殊」与游戏内一致；`npx vitest run src/domain/eggInventory.test.ts` 用例随口径更新。
