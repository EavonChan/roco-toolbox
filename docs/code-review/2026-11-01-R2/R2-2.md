## 高

### R2-2-H01 撤回重发的单会继承旧的「已上窝」勾选

- **问题描述**：现状是「已上窝」的本机记忆键末尾带需求版本号，注释声称「撤回重发会变成新的一行，不该继承旧的勾选」；但服务端撤回是整行 DELETE、重发是 INSERT version=0、再被接单 version=1，键和旧勾选完全一样。用户影响：别人把同款需求撤回重发、你重新接单后，这条新单上一来就打着旧的「已上窝」勾，你可能漏上窝。触发条件：需求方撤回→重发同内容需求→你再次接单。（证据：demandPlacementStore.ts:6-8 注释与 25-34 键含 `version`；functions/_lib/collectionGroupsStore.ts HEAD 版 withdrawCollectionDemand 走 `DELETE FROM collection_group_demands`、publish 走 `INSERT ... version, ... VALUES (..., 0, ...)`、claim 走 `version = version + 1`）
- **优化方案**：把键里的「版本号」换成「接单时间」（`claimedAt`，即该单被我接下时的 updatedAt）——它在持有期间不变、每次重接都刷新，正好满足「重发不继承」。`PlacementRow.version` 改为 `claimedAt`，HomeDemandPlacements 的 rowKeyOf 传 `placement.demand.claimedAt`。代价：升级后已存在的旧勾选键失配，用户现有「已上窝」勾选全部失效一次（键格式变了，旧键自然作废，不需迁移）。
- **优化后表现**：撤回重发→重新接单的单不再带旧勾；同一条单在持有期间勾选稳定。验收：`npx vitest run src/ui/HomeDemandPlacements.test.tsx`（新增「撤回重发不继承勾选」用例）。

## 中

### R2-2-M01 切换云账号的瞬间，接单列表还显示旧账号的单

- **问题描述**：现状是身份变化时 effect 只在「模块缓存正好命中新身份」时更新列表，缓存不匹配时旧列表原样留着等新请求回来。用户影响：换身份的几秒里，家园「接单上窝」显示的是上一个账号接的单，此时勾选「已上窝」会写进新账号的存储键（错写）。触发条件：组件保持挂载的状态下发生账号切换（目前切号流程会先离开家园页，窗口很小，属埋雷）。（证据：useClaimedDemands.ts:52-60，`if (cache && cache.accountId === accountId) setItems(cache.items)` 之后没有 else 清空；勾选写入走 demandPlacementStore.ts:47-59 以当前 accountId 为键）
- **优化方案**：effect 开头统一 `setItems(cache && cache.accountId === accountId ? cache.items : [])`——命中缓存照旧秒开，不命中先清空再等请求，与「无账号」分支口径一致。代价：无（换身份时本就该重新加载）。
- **优化后表现**：换身份瞬间列表立即清空并显示「正在读取接单…」，不会把旧账号的单错写进新账号。验收：`npx vitest run src/ui/HomeDemandPlacements.test.tsx src/ui/Home.test.tsx`（该 hook 现有测试不变即可证明无回归）。

### R2-2-M02 三个本机记忆写存储没兜底，隐私模式点一下直接抛错

- **问题描述**：现状是「已上窝」勾选、「账号收起」、结单「知道了」、家园分页切换这四处的 localStorage 写入都没有 try/catch；而同模块的 lastTab.ts 与 demandPickStore.ts 写入都兜底了。用户影响：隐私模式 / 存储被禁用 / 配额满时，点一下勾选或切分页就抛未捕获异常，事件中断。触发条件：存储不可写的浏览器环境。（证据：demandPlacementStore.ts:56 与 77、demandCompletionReadStore.ts:36、Home.tsx:279 均无 try/catch；依据：参照 src/ui/lastTab.ts 第 34-41 行与 src/ui/demandPickStore.ts 第 31-38 行的既有写法「存不下不影响本次操作」）
- **优化方案**：给这四处 `localStorage.setItem` 包 try/catch，失败只影响「下次打开记不住」，本次界面状态照样更新（marks 的 setState 本来就独立于写盘成功）。代价：每处 3 行，无行为变化。
- **优化后表现**：存储不可写环境下勾选、收起、切分页都正常，只是不持久化。验收：`npx vitest run src/ui/HomeDemandPlacements.test.tsx src/ui/Home.test.tsx`。

### R2-2-M03 「用哪颗蛋接单」的记忆键不带小组，同内容需求跨组互串

- **问题描述**：现状是种公需求的选蛋记忆以「需求方 + 需求内容」为键，不带小组 id；同一需求方把同一条种公需求发到两个组时，在 A 组选的蛋会直接显示为 B 组那张卡的代表蛋。用户影响：跨组看到错误的选择回显，极端情况下按 A 组的选择在 B 组接单。触发条件：同一需求方在多个小组发布内容完全相同的种公需求。（证据：demandPickStore.ts:7 全局单键 `roco.demandPick`；HEAD 版 MotherGroupResources.tsx 键为 `${demanderAccountId}:${demandKeyOf(demand)}` 无 groupId；依据：参照 demandPlacementStore.ts:33 与 demandCompletionReadStore.ts:15，同类键都带 groupId）
- **优化方案**：键改为 `groupId|demanderAccountId|demandKeyOf(demand)`，与另两个 store 对齐。**修复点在 MotherGroupResources.tsx——该文件当前是另一会话的未提交 WIP，本批不动，移交该会话或下批处理。**代价：旧选择失效一次。
- **优化后表现**：两个组的同名需求各自记忆选蛋。验收：本批不可执行（WIP 重叠），移交时在 MotherGroupResources.test.tsx 补「同内容需求跨组不互串」用例。
