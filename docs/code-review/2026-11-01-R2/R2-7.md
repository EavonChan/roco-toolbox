## 中风险

### R2-7-M01 · 中风险 · 两个人同时发需求时，小组的需求额度会被突破

**① 问题描述**
- **现状**：发布需求时先查「本组已用多少条、本人已用多少条」，再逐条插入，两次操作之间没有任何保护。
- **用户影响**：同一账号在两台设备（或连点重试）同时发布时，两边都算到「还没超」，最终本组/本人的实际条数超过额度，别人更难发需求；界面不会报错。
- **触发条件**：并发发布或一次重试与首次请求交错；单设备正常操作不会触发。
- （证据：`publishCollectionDemand` 的额度判定在 collectionGroupsStore.ts:1793-1817，插入在 1819-1833，中间无原子约束；额度为软约束 `DEMAND_LIMIT_PER_GROUP = 200`）

**② 优化方案**
把「先 COUNT 再 N 条 INSERT」改成「带额度条件的单条 INSERT」：所有性格用一条 `INSERT … SELECT … WHERE (当前总数 + 新增数) ≤ 上限 AND (本人总数 + 新增数) ≤ 额度` 的语句写入，由 SQLite 单语句保证不超额；保留原有 COUNT 作为「友好文案」的快速路径。
代价：发布语句变成动态拼装的多行 `SELECT … UNION ALL`，可读性下降；D1 往返从 N+2 降到 3 次。风险集中在 SQL 本身，靠现有 `test:mother-groups:api` 覆盖。

**③ 优化后表现**
解决：并发发布也不会突破小组/个人额度（额度语义从「事后可能超」变成「语句级保证」）。
验收：`npm run test:mother-groups:api` 通过；手写两条并发发布同组需求，`SELECT COUNT(*)` 不超过 200。

### R2-7-M02 · 中风险 · 小组用久了，需求中心一次拉回全部历史

**① 问题描述**
- **现状**：需求列表一次返回「未完成 + 全部已归档完成行」，没有上限也没有分页；已完成行只增不减。
- **用户影响**：活跃小组用上一年后，每次打开小组/每次轮询都可能拉回几百 KB 到 1 MB 的历史需求，手机端明显变慢、流量变大。
- **触发条件**：组内累计完成的单数达到数百条以上；新组短期无感。
- （证据：`listCollectionDemands` 无 LIMIT，collectionGroupsStore.ts:1600-1619；2026-10-31 新增的版本号轮询只在「版本没变」时省掉整包，变一次仍全量）

**② 优化方案**
A：服务端给「已完成」加 `LIMIT`（例如最近 300 条）+ 游标，前端只展示最近 N 条，已结单计数改用单独聚合——需要改响应契约与前端计数口径；
B：把「已完成」换成独立的计数字段（`demand_done_count` 已有版本号接口，但没有按成员计数），列表只回未完成——改动面最大。
推荐 A 的最小版：只限制返回条数、计数仍由服务端给出（`readCollectionGroupVersion` 已算 `demand_done_count`，可按成员扩展）。**两条都需要你拍板**，本批不改。

**③ 优化后表现**
解决：长期小组的响应体不再随历史线性增长。
验收：构造 1,000 条已完成数据，`GET /demands` 响应 < 100 KB；「已结 N 单」数字不变。

### R2-7-M03 · 中风险 · 两个接口文件各抄一份限流与错误码表，新增错误码容易只改一处

**① 问题描述**
- **现状**：`/api/collection-groups` 与旧 `/api/mother-groups` 逐字复制了限流常量、24 项状态码表与 4 个响应辅助函数（约 70 行）。
- **用户影响**：本次新增的两个错误码必须同时改两处；漏一处就会出现「同一个错误，两个入口返回不同状态甚至没有状态」，前端文案与重试判断随之漂移。
- **触发条件**：任何一次只在单个 handler 里加错误码/改限流的改动。
- （证据：collectionGroups.ts:65-131 与 motherGroups.ts:40-111 逐字相同；`Record<MotherStoreErrorCode, number>` 只能保证「每份完整」，不能保证「两份一致」）

**② 优化方案**
把常量与 `failCode / okJson / limited / newInviteCode / GROUP_ID_MAX / STORE_STATUS` 抽到新文件 `functions/_lib/collectionGroupsHttp.ts`，两个 handler 只 import。纯搬移、不改行为。
代价：新增 1 个内部模块（以下划线开头，Pages 不当作路由），导入路径多一层。

**③ 优化后表现**
用户无感知；验收看：`npx tsc -p functions/tsconfig.json` 通过、`npm run test:mother-groups:api` 通过，且两个入口的限流与状态码只有一处定义。

### R2-7-M04 · 中风险 · 「他不在小组了」和「你不是组员」共用一个错误码，但一个 404 一个 403

**① 问题描述**
- **现状**：组长移除一个已经离开的成员时，接口返回的 code 是 `NOT_MEMBER`（本意是「你不是该组成员」），HTTP 状态却是 404；「这个组不是母本组」也复用了「小组不存在」这个码。
- **用户影响**：目前 UI 按状态码分流、没按错误码分支，所以还没有可见错误；但任何以后按错误码做的判断（例如「我被踢了 → 清掉本地小组记忆」）都会在「成员已不在」这个 404 上误判成「你不是成员」。
- **触发条件**：组长重复移除同一成员，或往遗留的非母本组发布母本摘要。
- （证据：collectionGroups.ts:773、collectionGroupsStore.ts:631/1040；`STORE_STATUS` 两张表同名同值，无法区分主语）

**② 优化方案**
新增两个错误码：`MEMBER_NOT_FOUND`（404，「他不在小组了」）与 `GROUP_TYPE_MISMATCH`（409，「这个小组不是母本组」），替换上述两处借用；同步 `MotherStoreErrorCode` 与前端 `MOTHER_API_ERROR_CODES`。
代价：接口契约新增两个码；旧客户端把它们当未知码 → 落到 `HTTP_ERROR`，行为与现在按状态码分流一致，无回归。

**③ 优化后表现**
用户无感知；验收看：移除一个已离开的成员返回 `404 MEMBER_NOT_FOUND`，两处 `NOT_MEMBER` 只剩「你不是成员」一种语义；`npx vitest run src/api` 通过。

### R2-7-M05 · 中风险 · 需求方被移出小组后，接单的人只会看到任务凭空消失

**① 问题描述**
- **现状**：组长移除成员时，会顺带删掉该成员所有**未完成**需求（open / claimed）；已完成的单在归档表里不受影响。
- **用户影响**：正在帮忙的承接人下次刷新时，那条「我接的单」直接从列表消失，没有任何说明；用户会以为是自己点错了或需求被撤回，也可能白孵一颗蛋。
- **触发条件**：需求方被移出小组（或需求方主动退出）且其需求已被别人接单、尚未完成。
- （证据：`removeMemberCleanup` 删 `status != 'done'` 的行（collectionGroupsStore.ts:978-989），承接人没有收到任何通知；plan.md §7 已确认归档表与成员行解耦，这条不是数据丢失，而是提示缺失）

**② 优化方案**
A（推荐，不改表）：承接人本机记住「我接过哪些单」，每次需求列表刷新时对比——某条 `claimed` 且 `claimer = 我` 的单消失、归档表也没有它，就在小组页顶部提示一次「你接的 1 条需求已被取消（需求方已离开小组）」；复用现有 `demandCompletionNotice` 的展示位置与本机已读水位。
B：服务端记录取消原因（需新增字段/表），换设备也能看到——按纪律本批不能动 schema。
推荐 A：零 schema 改动、与现有「已完成提示」同构；代价是只在操作过的那台设备可见。

**③ 优化后表现**
解决：承接人知道任务为什么消失，不会误以为是自己的操作。
验收：A 设备接单 → 组长把需求方移出 → A 设备下一次刷新弹出「已被取消」提示；`npx vitest run src/ui/demandCancelledNotice.test.ts`（新增）通过。

> **需要你拍板**：这条是否要做、以及选 A 还是 B。

### R2-7-L01 · 低风险 · 带空格的需求性格会存成另一条，永远接不上

**① 问题描述**
- **现状**：性格校验时先 trim 判空，但通过后原样入库；同蛋同条件的两条需求只有尾随空格之差时，会被存成两条并各占一个额度。
- **用户影响**：正常界面不会发出这种值；一旦出现（旧客户端/手写请求），需求中心会凭空多一条同性格的单，客户端拿正常性格去接单永远匹配不上。
- **触发条件**：请求体里的性格带首尾空格。
- （证据：校验 `nature.trim().length > 0`（shared/collectionGroups.ts:368-376），入库 `new Set(input.natures)` 不 trim（collectionGroupsStore.ts:1780）；handler 原样传（collectionGroups.ts:582-596）。同根因：B3-L01 + B4-L03）

**② 优化方案**
在 store 入口统一规范化：`natures.map(n => n.trim())` 后再去重；接单/撤回的 `nature` 同样 trim。只改规范化，不改长度限制。
代价：无；异常请求会被归并成同一条，不再产生幽灵行。

**③ 优化后表现**
解决：同性格带空格不会重复占额度，接单能命中。
验收：`npx vitest run` 相关用例通过；集成里发 `['胆小',' 胆小']` 只落一行。

### R2-7-L05 · 低风险 · 蛋 id 用宽松数字解析，还留着已下线种公的负数语义

**① 问题描述**
- **现状**：`Number()` 接受 `'0x10'`、`'1e3'`、`' 12 '` 这类写法，正数分支也没有上限；负数分支注释说「负数 = 种公需求」，而种公组与种公需求已经下线。
- **用户影响**：无注入、无越权；最坏是写进一条永远匹配不上的需求并占额度，或给异常输入返回语义模糊的 400。
- **触发条件**：URL 或请求体里的蛋 id 不是十进制整数。
- （证据：collectionGroups.ts:493-506；同文件 `parseOptionalVersion` / `parseTaskKey` 都是严格校验，可作参照）

**② 优化方案**
改成「先用 `/^-?[1-9]\d{0,9}$/` 严格格式校验，再 `Number()`」；**负数分支保留**——集成用例
「种公需求：负数蛋组 id 可发布、可读回」明确覆盖它，说明旧轮「没有写入方」的结论已不成立
（只收紧解析格式，不改语义）。
代价：手写传 `'0x10'` 的调用会从「能用」变成 400，属预期。

**③ 优化后表现**
解决：蛋 id 只接受规范十进制整数，异常写法不再静默落库。
验收：`npm run test:mother-groups:api` 通过（含负数用例）；传 `'0x10'` 返回 400。
