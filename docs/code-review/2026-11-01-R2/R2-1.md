### R2-1-M01 跨账号放置只按账号顺序，不看配对概率

- **等级**：中
- **文件:行号**：[demandPlacement.ts:471-489](file:///d:/desk/洛克工具箱/src/domain/demandPlacement.ts#L471-L489)
- **标题**：`buildDemandPlacements` 两轮放置都以「第一个能配上的账号」为准，丢掉了候选里的 `natureChance`
- **描述**：

  ```ts
  // 第一轮：严格 1:1
  for (const state of states) {
    const pick = pickPair(target, demand, state, nestCount, false);
    if (!pick) continue;
    commit(state, demand, pick);   // pick.best 的 natureChance 只用于「账号内部」排序
    placed = true;
    break;
  }
  ```

  `pickPair` 内部已按 `natureChance` 降序挑出 `best`（:314-322），但**只在一个账号内比较**；
  外层 `for (const state of states)` 命中即 `break`，**没有跨账号比较** `pick.best.natureChance`。
  只要排在前面的账号能凑出 30% 的一对，就把这条单钉在 30%，哪怕第二个账号能用学院小窝给到 100%。

  典型触发：账号 A 有「目标蛋母本 + 同蛋组种公，但只有一方带目标性格」（0.3）；
  账号 B 有「自带目标性格的一对」（学院 1.0）。当前实现选 A。

- **影响面**：接单上窝的核心产出是「该把哪只挪到哪个窝」，并逐条写在卡片上的概率（`home-demand-chance`，
  50% 绿 / 30% 黄 / 15% 红）。同一笔接单本可以 50%（学院）却被排成 15%，用户按名单上窝后实际命中率更低；
  同一产品内两条口径互相矛盾——changelog `2026-10-30d` 明确「多个账号时取概率最高的那一对」，
  需求的详情页（`studHatchOptions`）也是按概率选，而接单上窝页是按账号顺序选。
- **修复建议**：两轮放置都改成「先收集各账号的 `pickPair` 结果，取 `best.natureChance` 最大者再 `commit`」，
  同级再按 `newNests` 少、账号序稳定；`diagnose` 诊断逻辑不动。行为变化需补一条用例：
  账号 A 0.3 / 账号 B 1.0 → 应落在 B。
- **置信度**：高（代码行为确定）；「是否算 bug」置信度中——需要产品确认「跨账号也按概率优先」是否就是期望（见 §4）。

### R2-1-M05 `lines === null` 把「旧摘要没产线」和「成员数据不可比」混成同一种降级，与页面其它判定口径冲突

- **等级**：中
- **文件:行号**：[studDemandCandidates.ts:59-61](file:///d:/desk/洛克工具箱/src/domain/studDemandCandidates.ts#L59-L61)；来源 [MotherGroupResources.tsx:313-329](file:///d:/desk/洛克工具箱/src/ui/MotherGroupResources.tsx#L313-L329)、传参 [:1190-1196](file:///d:/desk/洛克工具箱/src/ui/MotherGroupResources.tsx#L1190-L1196)
- **标题**：「有这枚蛋」兜底会把不可比 / 过期成员算成能补，而页面其它地方把它们当「未知」
- **描述**：`linesByMember` 在**两种情况**下都写 `null`：

  ```ts
  if (!isMotherResourceComparable(member.resource, catalogVersion, criteriaId)) { map.set(id, null); continue; }
  ... accounts.some((account) => account.lines === undefined) ? null : ...
  ```

  前者是「数据不可比（口径/图鉴版本不匹配）」，后者才是「旧摘要没带产线」。`findStudDemandCandidates`
  把 `null` 一律当成旧摘要：

  ```ts
  if (member.lines == null) {
    if (member.eggGameIds.has(entry.gameId)) supplierIds.push(member.accountId);
    continue;
  }
  ```

  于是「不可比」成员按**有没有这枚蛋**计入 `supplierIds`，角标人数与代表头像会被撑大；
  而同一页面 `targetRows` / `comparableIds` 用 `isMotherResourceComparable` 把这类成员排除，
  `memberSupplies` 对 `null` 返回 `null`（=未知）。结果：卡片说「N 人能补」，详情按产线判定说「没人/未知」。
- **影响面**：种公需求卡的「N 人能补」角标、代表蛋排序（`supplierIds.length` 是第二排序键），
  以及需求方据此决定是否发单；跨口径显示的差异会让用户怀疑数据。
- **修复建议**：给 `StudCandidateMember` 增加第三种状态（例如 `lines: null` 仅表示旧摘要，
  不可比成员由调用方直接过滤掉不传，或传 `lines: null + comparable: false`），
  调用方按 `comparableIds` 过滤成员；`findStudDemandCandidates` 保持纯函数只吃规范化后的输入。
- **置信度**：中高（`null` 的双语义是确定事实；「该不该计入」需产品确认，见 §4）。
