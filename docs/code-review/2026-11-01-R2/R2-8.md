### 2.1 读取限流集成用例「约 1805 次请求未触发 429」——既有不稳定，不是断言/实现错误

实现与用例（本轮复读确认）：`mg-read:<accountId>` 桶、`READ_LIMIT = 1800`、固定 1 小时窗口，一条 `INSERT … ON CONFLICT DO UPDATE … RETURNING count` 原子计数（[util.ts:130-153](file:///d:/desk/洛克工具箱/functions/_lib/util.ts#L130-L153)），**异常时 `catch { return true }` 静默放行**；用例串行 GET 最多 1805 次，断言出现 429（[mother-groups-api.test.mjs:664-684](file:///d:/desk/洛克工具箱/tools/test/mother-groups-api.test.mjs#L664-L684)）。

**本轮 3 次运行结果（每次服务只监听 127.0.0.1，临时库用完即删）：**

| 轮次 | 环境 | 结果 | 结束后 `rate_limits` 里该桶 `count` |
| --- | --- | --- | --- |
| ① 全套件内 | 干净库（随 34 条用例一起跑） | **PASS**（26.3s） | —（套件内未单独查表） |
| ② 单独跑·干净库 | 新临时库 + 新服务 | **PASS**（26.5s） | **1801**（触发身份）/ **1**（同 IP 另一身份） |
| ③ 单独跑·干净库 | 又一个新临时库 + 新服务 | **PASS**（26.5s） | **1801** / **1** |

上一次会话的同项复核记录过：Run A **FAIL**（1805 次全 200，结束后计数仅 **419**，即约 1386 次计数没落库 → 永远到不了 1800）、Run B PASS（1801）。

**结论**：断言口径正确、限流逻辑正确；失败模式是「本地 wrangler/miniflare 高频写入下 D1 计数偶发丢失 + `rateLimit` fail-open 放行」的**既有环境不稳定**。本轮 3/3 通过、计数精确落库 1801，未复现失败；上轮 1/2 失败且失败时计数确实丢失，两边证据合起来指向同一根因。风险不在用例，而在 **fail-open 无任何日志/打点**（写失败=限流整体失效且不可观测），建议后续把「表缺失」与「写失败」区分并打点（属产品改动，需拍板，见 §6.3）。另注：该集成套件在同一库上**不可重复运行**（register/创建限流是按小时窗口的），每次验证必须换新临时库。

### 3.1 迁移执行顺序（必须先于 Functions 部署）

### 3.3 校验脚本缺口（命令 5 门禁红的根因，只报告不修）

`verify-mother-groups-schema.mjs` 的机制是「剥掉 schema.sql 里带 `>>> / <<<` 标记的新区块 → 按清单重放迁移 → 逐列对比」。要覆盖新迁移需要同时做两件事：

1. 把 `2026-11-01-collection-demand-green-nest.sql` 登记进 `MIGRATIONS`（`repeat: 1`，因它不可重复执行）；
2. 处理基线问题：现版 schema.sql 已含该列，直接登记会撞 `duplicate column`——需把「加列前」的 schema 作为旧库基线（如取 `HEAD~1` 的 schema，或在剥离时同时删掉这两列定义）。

这是**测试脚手架缺口**，不是产品缺陷；但不修它，`npm run test:mother-groups:api` 永远红在第一步，发包验证命令不可用。
