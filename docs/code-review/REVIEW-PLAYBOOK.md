# 代码审查流程（Playbook）

> 触发：用户说「整体审代码」「全量 review」「按流程审一遍」时，直接按本文执行，不再重新讨论流程。
> 每次审查的实例产物放 `docs/code-review/<日期>-...`，本文只写**流程与模板**，不写具体结论。
> 实例参考：`2026-10-29-审查计划与批次.md`、`2026-10-29/briefs.md`、`2026-10-29/B*.md`。

---

## 0. 一句话流程

**对基线 → 定范围 → 固化基线 → 跑基线验证 → 按目录切批 → 每批自包含简报分发 → 只读审查出报告 → 按批复核并修 → 全量收尾验收 → 合并报告归档。**

审查与修复**分两阶段**：第一阶段只读，禁止改任何代码；报告出来后再进第二阶段。

---

## 1. 开工前必须先确认的 5 个参数

不允许猜。给出默认建议，让用户一次拍板：

| 参数 | 说明 | 默认建议 |
| --- | --- | --- |
| base_ref → head_ref | 范围边界；工作区脏时 head 用「工作区」 | 上一个发布点 → 当前 HEAD（含工作区） |
| 范围清单 | 纳入/排除的目录与文件类型 | 纳入 `src/** functions/** tools/** e2e/**`；排除 `dist node_modules .wrangler *.apk *.tsbuildinfo lockfile 生成物 截图/` |
| 规范来源 | 中风险判定的唯一依据 | 见 §4 白名单；**先确认仓库有没有 eslint/editorconfig** |
| 报告路径 | 放哪里、叫什么 | `docs/code-review/<日期>-report.md`，分批放 `<日期>/B{n}.md` |
| 批量与并行度 | 每批问题数与同时会话数 | 每批 ≤3 问题 / 3 文件；并行会话 ≤3（本机终端上限 5） |

**工作区是脏的，必须先问一句**：要不要把当前改动原样提交成一个「审查前基线快照」？
理由：不固化的话，第二阶段的 `git rev-parse HEAD` 回滚点会被未提交改动污染，每个问题的独立提交也切不干净。

---

## 2. 阶段一：基线固化与验证

1. 记录事实：`git log --oneline -5`、`git status --short`、`git diff --stat <base>`
2. 固化：`git add -A && git commit -m "chore: 代码审查前基线快照（内容未改动，仅固化工作区）"` → 记下 `rev-parse HEAD` 作为**总回滚点**
3. 跑基线（**只跑这一遍**，收尾再跑一遍）：
   ```powershell
   npx tsc -b
   npx tsc -p functions/tsconfig.json
   npx vitest run
   npm run test:data-pipeline
   ```
4. 把「文件数 / 用例数 / 通过 / 既有失败」写成表格放进计划文档。
   **基线全绿的美德**：之后任何新增失败都能直接归因于修复。若基线有既有失败，逐条列出，后续对比时排除。

---

## 3. 阶段二：批次划分

划分原则（照做即可）：

1. **按目录/层次切，不按人切**：域模型 → 后端 → 契约 → UI → 集成测试，保证批次间文件不重叠。
2. **单批 ≤ 1,300 行变更**（含测试）。超了就拆，但见第 4 条。
3. **单个巨型文件（> 2,000 行）单独一批**，且**不按行拆会话**——它是单组件，拆会话只会在接缝重复审查。改为「一个会话、分两轮读、两轮汇报」。
4. **测试文件跟被测代码同批**，不单独成批（e2e/集成测试除外，它们自成一批）。
5. **域模型先审**：口径错了，UI 批会跟着误判，且域模型的修复会改 UI 测试预期。
6. **集成/e2e 永远最后一批**：它要跑在「所有修复都提交完」的 HEAD 上，否则结论立刻过期。
7. 每批在表里写清：主题 / 规模（+增 −删）/ 文件清单 / 审查重点 / 验证命令。

排期建议：`域模型 → 后端 → 契约 → UI（≤3 并行）→ 巨型组件 → 集成收尾`。

---

## 4. 规范依据白名单（中风险只能引这些）

先实测仓库有没有 `.eslintrc*`、`.editorconfig`。没有就只用下面这些，并写清引用位置：

| 来源 | 可判什么 |
| --- | --- |
| `tsconfig*.json`（`strict` / `noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` / `isolatedModules`） | 类型、未使用变量、switch 穿透 |
| `AGENTS.md` | 工作约定 |
| `docs/产品交互规范.md` | 交互与文案口径 |
| `docs/domain/**` | 领域规则（蛋组、体型、性格、覆盖度、排序） |
| `src/data/changelog.json` 对应条目 | **需求口径**，用于判「实现与需求不符」 |
| 同模块既有写法 | 须写「依据：参照 `xxx` 第 N 行既有写法」 |

**降级规则**：指不出依据的一律记为「建议」，不计入中风险。禁止把个人偏好当规范。

---

## 5. 分级与产出格式（全批统一）

- **高**：逻辑错误、与需求不符、并发/边界/异常处理缺陷、明显性能问题（N+1、循环内 IO、复杂度失控）、数据正确性（精度、时区、编码、事务、幂等）、安全（注入、越权、敏感信息）
- **中**：违反 §4 明确规范、明显过度复杂、职责耦合、重复逻辑、错误处理不一致、可测试性差
- **低**：死代码、无用导入、命名/注释瑕疵、格式
- **不确定**：证据不足或需业务语义，标置信度 + 需要谁确认，禁止自行假设

编号：`B{批次}-{H|M|L|U}{两位}`，例如 `B3-H01`。合并报告时**编号不再改**，修复提交直接引用。

### 每条问题的固定三段式（面向上线影响，不面向代码）

**第一行（一句话标题）**：`H01 · 高风险 · 删掉组员会连带删掉他已结单的记录`
标题必须是**人能看懂的现象**，不能是「XxxStore 缺少校验」这类代码名词。

**① 问题描述**（三句话，按顺序回答）
- **现状**：现在代码实际做了什么，用业务语言。「组里移除一个成员时，他发过的已完成需求会跟着一起被删。」
- **用户影响**：谁、在什么操作下、会看到什么异常或丢什么数据。「楼主清理成员后，小组首页『已结单』从 12 掉到 9，且无法恢复。」
- **触发条件**：偶发还是必然、影响哪些人。「任何移除成员/删组操作都会触发，必然复现。」
- 技术证据压成**一行括号附录**，不占正文：`（functions/schema.sql:188 ON DELETE CASCADE；demand_completions.demand_id 无独立快照）`

**② 优化方案**（2~3 句）
- 用「把 X 改成 Y」的句式，**不贴代码**。
- 改动超过 30 行、涉及表结构、或会影响其它功能时，必须写清**代价与风险**，并给 A/B 一句话对比 + 推荐。
- 有多个修法时说明「为什么选这个」。

**③ 优化后表现**（解决了什么 + 怎么验收）
- **解决**：用户能感受到的变化，一句。
- **验收**：给一条**可点的操作路径**（「小组管理 → 移除成员 → 回首页，已结单数仍为 12」）或一条**可执行命令**（`npx vitest run xxx` 期望通过）。
- 用户无感知的内部改进，写「用户无感知；验收看：xxx 用例转绿 / 类型检查通过」。

**术语规则**：技术词首次出现写成「通俗说法（术语）」，例如「数据丢失（级联删除）」；能不用缩写就不用；必须用时第一次解释。
**禁止**写「优化了代码结构」「提升了健壮性」这类没有信息量的表述。

### 批间汇报模板（会话里直接给用户）

1. **一句话结论**：本批审出 N 条，最该先修的是 H01（一句话说清后果）。
2. **速览表**：`编号 | 风险 | 一句话问题 | 影响谁`
3. **需要你拍板**：最多 2 条，写成「A 和 B 你选哪个，差别是什么」；没有就写「无」。

每份报告末尾必备：三段式清单统计、最该先修的 1~3 条（同样三段式，各一句话）、范围外备注（只记录不展开）。

---

## 6. 阶段三：分发

- **每批一份自包含简报**（`<日期>/briefs.md`，用四反引号包起来，整段可复制粘贴）。简报必须自带：范围文件清单、审查重点、已知线索、规范白名单、分级、输出路径与编号、验证命令、纪律与禁止项、必须停下问的情形。
- 新会话不共享上下文，简报里**不能出现「如上所述」「刚才那个」**。
- 并行度 ≤3；同一文件不允许两个会话同时改（批次按目录不重叠就是为此）。
- **不要在同一会话里同时「改代码」和「跑集成/e2e」**：构建产物与端口会被污染，结论无法归因。真集成放最后一批。

---

## 7. 阶段四：修复

顺序 高 → 中 → 低；每批 ≤3 问题 / 3 文件，批间汇报。

每个问题：
1. 记 `git rev-parse HEAD` 作回滚点
2. 独立提交，message 形如 `fix(cr-B3-01): 完成需求未校验更新行数`
3. 跑**相关**测试 + `npx tsc -b`（遵循 AGENTS.md：不要每改一点就跑全量）
4. 与基线对比：**出现新增失败立即回滚该提交**并标「修复失败待议」
5. 写进报告「处理记录」：编号 / 提交 / 前置 HEAD / 改动文件 / 验证 / 回滚命令

低风险：只有「全局检索无引用（含路由、配置、动态 import、序列化入口）+ 构建通过」才删，否则只记录。

**硬性禁止**：删文件/目录（除明确要求）、重命名公共接口、改 `migrations/**` 与 `schema.sql`、改 CI/CD 与部署配置、改 lockfile、`reset --hard`/`rebase`/force push/改历史、顺带重构或格式化、升级依赖、**为让测试通过而改断言**（认为断言错就先报告）。

**必须停下问**：需要业务口径二选一、涉及线上数据、影响面无法静态确认、需要改表结构、需要放宽 e2e 超时。

---

## 8. 阶段五：收尾验收（只跑一次）

```powershell
npx vitest run                       # 全量，对比基线
npx tsc -b
npx tsc -p functions/tsconfig.json
npm run test:data-pipeline
npm run test:mother-groups:api       # 本地 wrangler + 临时 D1，只监听 127.0.0.1
npx playwright test --list
npx playwright test <与本次改动最相关的 2~3 个 spec>
```

另查：数据库迁移的**执行顺序**（迁移先于 Functions 部署）、changelog 是否需要补用户可见说明、报告是否覆盖了所有批次编号。

---

## 9. 合并报告

`docs/code-review/<日期>-report.md` 按批次顺序拼接 `B{n}.md`，给出：

1. 一句结论（哪些做完了、哪些没做）
2. 问题统计表（按批 × 等级）
3. 修复记录汇总（编号 → commit → 验证结果）
4. 未修 / 降级 / 待议清单（含原因与建议后续动作）
5. 剩余风险与建议下一步
6. **一页速览（给非技术读者）**：只列高中风险，每条一行 = 「现象 → 影响 → 一句话修法 → 怎么验收」，不出现文件名与行号

## 10. 常见坑（都踩过）

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 工作区脏 | 修复提交混进别人的改动，回滚点不可靠 | 先固化基线快照；并行会话只 `git add` 自己的文件 |
| 行号漂移 | 报告写 `:2424`，代码已是 `:2448` | 报告注明「行号以 <commit> 为基准」，并给映射表 |
| 大提交插队 | 新功能提交改写了正在审查的文件，结论过期 | 见 §11 的「旧项作废判定」 |
| 测试被改松 | 断言迁就实现，回归被固化 | 审查阶段逐条对比 `<base>` 版本断言；发现即报告，不改 |
| 巨型组件 | 2,000+ 行单组件，拆会话重复审查 | 单会话两轮读、两轮汇报，不按行拆 |
| 并行构建 | 一个会话改代码、另一个跑 e2e/集成 | 串行；或只并行「静态部分」（引用核对、`--list`） |
| 集成用例不稳定 | 高频写导致限流用例偶发失败 | 记为既有不稳定，交收尾批复核，不要为了过而改断言 |
| 只修高不修中 | 中风险堆到下一轮变成债 | 每轮给「剩余清单」并明确下一轮承接 |

---

## 11. 增量审查：中途来了新提交怎么办

**不要重审全文，只审差异面。**

1. **先让工作区落地**（提交或冻结），否则审一半代码又在变。
2. 以「新提交是否改到该文件」判定旧结论是否还有效：
   - **文件被改过** → 旧问题作废/降级为「需复核」，进新一批重看（新提交往往已经顺手修了）
   - **文件没被改过** → 旧问题仍然有效，原样承接
   - **文件被删除** → 旧问题直接关闭
3. 新提交本身按 §3 重新切批（只看它新增/改动/删除的文件）。
4. 收尾验收仍只做一次，对着最终 HEAD。
5. 在计划文档里留一张「旧项作废判定表」，逐条写清 有效 / 作废 / 已顺手修掉，避免下一轮重复劳动。

## 12. 简报骨架（复制后填）

````text
你是资深代码审查工程师。项目：<路径与一句话架构>。领域规则见 <docs 路径>。
【任务】只读审查（先不改代码），范围：git <base>..<head> 中下列文件的变更，及其直接调用方。
- <文件清单，带增删行数；重点文件标 ★>
【审查重点】
1. <具体到函数/口径，不要写「检查代码质量」>
2. …
【已知线索（未复核，必须重读当前代码确认后再定级）】
- <疑似高/中/低 + 位置 + 一句话>
【规范依据白名单】<按 §4 填>
【分级】<按 §5 填>
【输出】写文件 <报告路径>。编号 B{n}-H01…。**每条严格按 §5 三段式**：
① 问题描述（现状 / 用户影响 / 触发条件，各一句；技术证据压成一行括号附录）
② 优化方案（把 X 改成 Y，2~3 句，不贴代码；有代价或 A/B 方案要写明）
③ 优化后表现（解决了什么 + 怎么验收：可点路径或可执行命令）
标题一句话说清现象，禁止用代码名词。末尾给：统计、最该先修的 1~3 条（同样三段式）、范围外备注。
【纪律】审查阶段禁止改代码、禁止 git 写操作。修完一批最多 3 问题/3 文件，独立提交 fix(cr-B{n}-01): …，提交前记 HEAD 写入处理记录。
【验证】<本批测试命令 + tsc>；基线 <文件数/用例数>。
【硬性禁止】<按 §7 填>
【遇以下立即停下问我】需要业务口径二选一、涉及线上数据、影响面无法静态确认。
````
