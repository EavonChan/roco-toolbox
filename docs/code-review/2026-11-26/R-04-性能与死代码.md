## 0. 结论

三条性能改动的方向都对：`fitCardName` 把「逐卡改样式→量→写」改成「集中读 → canvas 量 → 集中写」，母本推荐性格改成一次建表，首屏只挂 2 组再靠空闲片补齐。**任务书里列的四个怀疑点全部不成立**，可以销案：render 阶段做 DOM 测量（没有，都在 layout effect / 调度里）、批内读写交替（没有，读集中在 `flushCardNameFit`）、二分死循环（没有，有明确收敛条件）、隐藏克隆节点污染（没有，量的是真卡 `clientWidth`）。

真正剩下的一个 P1 是**渐进渲染的切换路径**：换筛选 / 打字时，重置写在 `useEffect` 里，切换后的**第一次提交仍按旧组数整屏渲染**，然后才塌回 2 组 + 骨架再长回来 —— 和这次优化的目标正好相反，而且触发面就是目标设备（宽横屏）。其余是「分片收益被打折」的 P2。

新文件一侧：**聚合三件套（`eggStockGroups` / `EggGroupCard` / `EggGroupLevel2`）确实是死代码**，生产零调用（只有自己的测试和 `tools/preview/u3` 预览器），面板没接线。好消息是 `src/data/changelog.json` **没有**向用户宣布聚合功能，所以不构成"假已上线"；坏消息是它有 27 条绿测试 + 方案文档 + 截图，下一个接手的人很容易当成已生效。

## 1. PERF-01 · P1 · 搜索 / 换筛选后先按旧组数整屏渲染，再塌回 2 组 + 骨架

**位置**：`src/ui/MotherView.tsx:448-458`（`requestedSections` / `mountedSections` 两个 state + 重置 effect）、`:478`（`chainSections.slice(0, mountedSections)`）、`:480`（骨架切片）、`:754-764`（骨架渲染）

### ① 问题描述

- **现状**：首帧只挂 `FIRST_PAINT_SECTIONS`（2）组，然后靠空闲片长到 10（横屏）/ 6 / 2。但「换筛选 / 搜索 / 断点就从头来」的重置写在 `useEffect` 里（`:455-458`），它在 React 提交并绘制**之后**才跑；而 `visibleChainSections = chainSections.slice(0, mountedSections)`（`:478`）用的是**上一次提交的** `mountedSections`。
- **用户影响**：宽横屏下每敲一个字，都会先按旧值（最多 10 组）把新结果整屏渲染一次，然后 effect 把它塌回 2 组、露出 8 个骨架，再用 3~4 个空闲片长回 10。用户看到的是：① 列表「收回去」再「长出来」；② 骨架每次输入都重现；③ 已经下滚时文档高度先缩后长，浏览器可能夹紧滚动位置。同时**每次输入都白付了一遍"一次挂 10 组"的成本**，与这次改动"首帧只挂 2 组"的目的直接矛盾。
- **触发条件**：**必然**，只要在宽横屏（10 组 / 6 组档）下换筛选、改搜索词、或触发断点变化；竖屏（2 组档）不受影响。
- （技术证据：`MotherView.tsx:455-458` 是 effect 而非渲染期重置；`:478` 用 state 切片；`MotherViewProgressive.test.tsx` 只覆盖"首挂 2 组"和"补齐到 10 组"，**没有覆盖换筛选**）

### ② 优化方案

把「重置」从 effect 挪到渲染期，二选一：

- **A（推荐）**：把 `{ key, requested, mounted }` 合成一个 state，当 `key`（= 筛选签名）与当前不一致时，在 render 里直接按 `{ target, 2 }` 取值，effect 只负责空闲增长。这样切换后的**第一次提交**就只有 2 组。
- **B**：给列表主体加 `key={filterKey}`，让它以 2 组重新挂载。代价：整块 DOM 重建，滚动位置与 `content-visibility` 的缓存都会丢，比 A 粗暴。

选 A：只改取数时机，不动 DOM 生命周期。

### ③ 优化后表现

- **解决**：敲字/换筛选时不再出现"先整屏再收回"的跳动，每次输入只挂 2 组。
- **验收**：`npx vitest run src/ui/MotherViewProgressive.test.tsx`，新增用例——宽横屏补齐到 10 组后 `fireEvent.change` 搜索框，断言**同一 tick** 内 `mother-chain-group-*` 数量 ≤ 3，随后空闲片补齐回 10。

## 2. PERF-02 · P2 · 空闲回调不看「还剩多少时间」，一片固定 2 组 / 20 张卡

**位置**：`src/ui/MotherView.tsx:122-133`（`scheduleIdleTask` 的 callback 无参）、`:464-474`（`nextMounted` 按组数/卡数切片）

### ① 问题描述

- **现状**：`requestIdleCallback(run, { timeout: 300 })` 的 `run` 不接收 `IdleDeadline`，一次固定追加 ≤2 组 / ≤20 张卡，不看这一帧还剩多少空闲；`timeout` 只保证"最晚 300ms 执行"，不限制单次工作量。
- **用户影响**：20 张卡 + 一次 React 提交在低端平板容易超过一帧；仓库自己的分析文档（`docs/分析-收集页卡顿-2026-11-25.md` §11.4）就记录了 1024×768 有约 1/6 轮出现正好 50ms 的一帧。分片粒度是"张数 / 组数"，不是"毫秒"。
- **触发条件**：**必然**（每次进入母本页都会走这条路径），是否掉帧取决于设备。
- （技术证据：`scheduleIdleTask` 的签名与调用；[推测] 具体帧耗时需真机 Performance 面板确认）

### ② 优化方案

`run(deadline)`：每次只加**一组**，用 `deadline.timeRemaining() > 8` 决定继续还是留给下一片；或把 `IDLE_SLICE_MAX_CARDS` 从 20 降到 8~10，用更多片换更小的单帧。代价：补齐稍微慢一点（多几个空闲片）。

### ③ 优化后表现

- **解决**：单帧工作量有上界，不再出现偶发 50ms 长帧。
- **验收**：`npx vitest run src/ui/MotherViewProgressive.test.tsx`（jsdom 走 `setTimeout` 分支，行为应不变）；真机 Performance 面板确认 Long Task 消失。

## 3. PERF-03 · P2 · 取消只走 `cancelIdleCallback?.()`，旧闭包可能把「显示更多」的组数改回去

**位置**：`src/ui/MotherView.tsx:129`（`return () => scope.cancelIdleCallback?.(handle)`）、`:464-474`（`nextMounted` 读闭包里的 `requestedSections`）、`:473`（`Math.min(requestedSections, count)`）

### ① 问题描述

- **现状**：有 `requestIdleCallback` 但没有 `cancelIdleCallback` 的环境（自写 shim、部分 WebView）里 cleanup 是空操作，待执行的旧回调会用旧闭包的 `requestedSections`（例如 10）与新的 `current`（用户点「显示更多」后 15）算出 `Math.min(10, 15) = 10`。
- **用户影响**：用户刚点「显示更多蛋组」多出 5 组，几百毫秒后自己又消失（还顺带把 DOM 卸掉重挂）。
- **触发条件**：**窄竞态**，需要"rIC 存在但 cancel 不存在"的环境 + 恰好点了显示更多。**[推测]**（代码路径确定，环境是否存在需确认）。

### ② 优化方案

`setMountedSections(c => Math.max(c, nextMounted(c)))` 防倒退；并把 `requestedSections` / `chainSections` 放进 ref 让回调读最新值，或自己包一层带 `cancelled` 标志的调度。代价：几行。

### ③ 优化后表现

- **解决**：点「显示更多」后组数不会被旧回调吃掉。
- **验收**：`npx vitest run src/ui/MotherView.test.tsx`（"大列表首屏只渲染部分蛋组"用例）+ 新增"`cancelIdleCallback` 为 undefined"的用例。

## 4. PERF-04 · P2 · 骨架是写死的 180px 白块，落在视口里时会被用户看见

**位置**：`src/ui/MotherView.tsx:116`（`SECTION_SKELETON_HEIGHT_PX = 180`）、`:754-764`（骨架 div 定高）、`:706`（真分区 `containIntrinsicSize: 'auto 180px'`）；配合 `src/index.css:418-423`（两列 grid）

### ① 问题描述

- **现状**：骨架是纯白圆角 `div`、写死 `height: 180px`，和真分区同在两列 grid 里；真分区高度 = 表头 + 行数 × 卡片高（4 张卡一组 ≈136px，13 行一组 ≈1430px）。
- **用户影响**：① 搜索/筛选后只剩几个短分区时，首帧 2 个真分区只有 ~270px，剩下的骨架落在 768 高视口内 —— 用户会看到 4~5 个**空白圆角块**，几十到几百毫秒后才长出内容；② 骨架在视口内被真分区替换时，同一 grid 行高度从 180 变成 136 或 1430，同行另一个骨架和下方内容会跟着跳。注释里"骨架→真分区屏外高度不变"只在分区**仍在屏外**（`content-visibility:auto` 保持 180 占位）时成立。
- **触发条件**：**必然**（只要骨架落在视口内），短列表最明显。**[推测]**（按 CSS 规则 + DOM 顺序推的，未录屏；CLS 具体数值需真机量）

### ② 优化方案

骨架改成不显眼的占位（`min-height` 而非定高，或 `visibility:hidden` 的等高占位），并且只给"首屏可能可见"的骨架（例如 `min(pending, 2)`），其余等滚动/空闲再补。实在保证不了一致性就不渲染骨架直接分批插入（作者实测锚点位移本来就是 0px）。代价：`mother-chain-skeleton` 的数量断言要跟着改。

### ③ 优化后表现

- **解决**：首屏不再出现空白圆角块，替换真分区时不再抖。
- **验收**：新增用例断言搜索后 `mother-chain-skeleton` 数量上限；真机 1024×768 与 375 录屏看 Layout Shift。

## 5. PERF-05 · P2 · 三列判定只量到前 2 个已挂分区，之后不再重算

**位置**：`src/ui/MotherView.tsx:495-542`（`useLayoutEffect`，测量在 `:521-527`，依赖数组在 `:542`，**不含** `mountedSections`）

### ① 问题描述

- **现状**：这个 layout effect 在首帧量 `list.children`（此时只有 2 个真分区，其余是骨架），把 2 个高度交给 `shouldUseThreeColumns({ totalSections: 全部 })`；空闲片把已挂组数加到 6/10 时**不会重跑**。
- **用户影响**：改造前首帧就挂满 6/10 组、用真实高度判定；现在只有 2 个样本外推（`motherColumnLayout.ts` 用平均值兜底），分区高度差异大时会两列/三列选错，而且这个错误会一直留在页面上，直到下次筛选。只影响 ≥1200px 横屏 + 收起筛选的情景。
- **触发条件**：**条件必然**（横屏 + 收起筛选 + 分区高度差异大时选错）**[实测]（代码级）**；"是否真的选错"需真机确认。
- （技术证据：`:542` 的依赖列表；`:521-527` 只筛 `mother-chain-group-*`，即已挂分区）

### ② 优化方案

### ③ 优化后表现

- **解决**：三列/两列判定基于全部已挂分区的真实高度。
- **验收**：`npx vitest run src/ui/motherColumnLayout.test.ts`（纯函数）+ 新增"补齐后重算"用例。

## 6. PERF-06 · P2 · 每个空闲片都全量重渲染已挂分区，越往后越贵

**位置**：`src/ui/MotherView.tsx:702-747`（分区直接在 render 里 map）、`:812`（`MotherEggRow` 未 memo）

### ① 问题描述

- **现状**：`mountedSections` 是 MotherView 自己的 state，每次空闲片都重跑整个 render：已挂的 ~191 行 `MotherEggRow` 全部重新执行（`mothersOf()` 新建数组、`new Set`、`PetCardLayout` 子树 diff），再叠加新挂的 20 张卡。
- **用户影响**：分片的初衷是"每片工作量恒定"，但第 4~5 片要重算 150+ 行，单帧成本随进度上升 —— 和 PERF-02 一起解释了"最后仍有一帧 50ms"。**行为上没有错误**，只是优化效果被打折。
- **触发条件**：**必然**（每次补齐）。
- （技术证据：`mountedSections` 提升在 MotherView；分区与行组件均无 `memo`；`mothersOf()` 在 render 内调用）

### ② 优化方案

把分区抽成 `React.memo(ChainSection)`（props 只有 section + 稳定回调），或至少给 `MotherEggRow` 包 `memo`，并用 `useMemo` 稳定 `mothers={mothersOf(group)}` / `onTogglePlan` / `jumpBase`；`mountedSections` 变化只应影响新增的那一片。代价：要保证回调引用稳定（`useCallback`），否则 memo 失效。

### ③ 优化后表现

- **解决**：第 N 片只渲染第 N 片。
- **验收**：`npx vitest run src/ui/MotherViewProgressive.test.tsx`；可加"`PetCardLayout` 渲染次数"计数断言，确认第 2 片不再重渲染第 1 片的行。

## 7. PERF-07 · P2 · 共享 ResizeObserver + 全局 flush：一张卡变宽就重测全部

**位置**：`src/ui/fitCardName.ts:145-162`（observer 回调在 `:158` 调 `scheduleFlush()`）、`:119-133`（flush 读所有 task 的 `clientWidth`）

### ① 问题描述

- **现状**：RO 回调只要**一张**卡宽度变了就 `scheduleFlush()`，而 flush 把 `tasks` 里所有卡的 `clientWidth` 全读一遍再逐个写。母本分区带 `content-visibility:auto`，滚动进出视口时卡内元素宽度会在 0 ↔ 真实之间反复变。
- **用户影响**：单张卡 resize 的代价从 O(1) 变成 O(N)（191 张读 + 191 次写；写基本被 `!==` 挡掉，但读会强制一次布局）。滚动跨分区时每个边界可能触发一次全量重测 —— 省掉 165 个观察器实例是对的，但换来的是做功放大。
- **触发条件**：**必然**（滚动时）。具体耗时 **[推测]**，需真机确认。
- （技术证据：`fitCardName.ts:145-162`；`flushCardNameFit` 遍历全部 task）

### ② 优化方案

RO 回调只把变化的目标收进 dirty 集合，flush 只处理这些 task（`flushCardNameFit(dirtyTasks?)`）；或把 flush 合批到一次 `requestAnimationFrame`，同一帧最多一次。代价：多一个集合。

### ③ 优化后表现

- **解决**：滚动进出视口时不再每次全量重测。
- **验收**：`npx vitest run src/ui/fitCardName.test.tsx`，补一条"只有 1 张卡回调时 `clientWidth` 只读 1 次"的计数用例。

## 8. PERF-08 · P2 · 字体族/字重按"第一张被量到的卡"全局缓存，且没有失效入口

**位置**：`src/ui/fitCardName.ts:45-47`（模块级 `fontFamily/fontWeight`）、`:81-92`（`fontOf`）、`:49-50`、`:110`（`widthCache` 只在满 2000 条时清）

### ① 问题描述

- **现状**：`fontOf()` 用**第一次**被量到的元素的 computed font，之后全模块永久复用；`widthCache` 没有失效入口（只有测试 reset）。
- **用户影响**：现在所有卡都是 `font-bold` + 同一套字体，所以暂时等价；一旦有人给某张卡换字重/字族，或将来加 `@font-face`（字体加载完成前量到的宽度会被缓存住），canvas 量出来的自然宽度就不是那张卡的真实宽度 → 字号算错。目前因为 base == min 不会缩字号（PERF-11），问题被掩盖。
- **触发条件**：**潜伏**，等真的启用"长名字缩字号"或引入自定义字体时才暴露。
- （技术证据：`fitCardName.ts:45-47/81-92` 的短路返回；无 `document.fonts.ready` 处理）

### ② 优化方案

把 family/weight 放进 `CardNameFitTask`（登记时读一次）并进入 cache key；`document.fonts.ready` 之后清一次 `widthCache` 并重排。代价：每个 task 多两个字符串。

### ③ 优化后表现

- **解决**：不同字重/字体下的字号测量不会互相污染。
- **验收**：`npx vitest run src/ui/fitCardName.test.tsx`（用 `setTextMeasurerForTest` 构造两种字重验算）。

## 10. PERF-10 · P2 · `useMotherCollectionData` 的 memo 永不命中

**位置**：`src/ui/useMotherCollectionData.ts:110-124`；调用点 `src/ui/plan/MotherCollectingView.tsx:160-174`、`:232-249`

### ① 问题描述

- **现状**：memo 依赖 `motherGroups / demands / trades / members` 等，但两处调用都在 render 里现造数组（`motherGroups.map(...)`、`members.map(...)`、`demands: state?.demands ?? []` —— 空数组字面量每次也是新引用），所以每次渲染 `buildCollectionPlanCards` 都重跑。
- **用户影响**：看起来是"收口 + memo"，命中率是 0；「收集中」点一下状态筛选就全量重建卡片（209 组规模）。不会出错，但**这次性能改造在这个文件上没有收益**，还多了一层间接。
- **触发条件**：**必然**（每次渲染）。
