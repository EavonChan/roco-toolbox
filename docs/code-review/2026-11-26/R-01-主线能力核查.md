# R-01 · 主线能力核查（蛋仓入库 / 合并 / 服务端同步）

> 审查者：R4（只读）。**没有改 `src/`、没有 commit、没有 push、没有打包/发版、没有跑全量测试。**
> 行号基准：`d1a4f1c`（当前 HEAD）。引用前请先 `git show d1a4f1c:<file>` 复核。
> 分级口径：**P1** = 用户能感知的错误 / 丢数据 / 用户意愿被覆盖；**P2** = 潜在风险、口径不一致、边界、需确认。
> 标注规则：**[实测]** = 读代码或跑命令核对过（给命令）；**[推测]** = 有机制但没复现；**需确认** = 卡在业务口径。

## 0. 结论

**四项主线字段（`obtainedAt` / `parents` / `greenNest` / `provenance`）没有被任何路径清空**（见 §4 逐字段核查），服务端改成「读最新 → 合并 → CAS 重试」也确实**不会丢别人的写**（CAS 在 `version` 上，重读后再合并，`eggMatching.ts:117-141`）。真正的问题集中在**「谁有权替用户做主」**和**「没人处理的状态」**两处：

1. **自动挂出会把升级前用户手动下架过的蛋重新挂到组内广场**（R4-01，P1）—— 这是本轮最该先修的一条：用户没做任何操作，私藏蛋/满重蛋会变成别人可申请换的库存。
2. **家园里消失的蛋只标「待认领」、永不清理，而唯一能显示「待认领」的组件还没接线**（R4-02，P1）—— 蛋仓会永久残留幽灵家蛋，用户看不见也删不掉。
3. 合并键的错配风险（R4-03，P2）和重试窗口里的一侧静默丢弃（R4-06，P2）属于「机制成立、触发条件窄」，列出来是为了别在下轮被当成"已保证幂等"。

## 1. R4-01 · P1 · 用户手动下架过的蛋，升级后会被自动重新挂出去

**位置**：`src/shared/eggWorkflow.ts:159-171`（`autoListStock`）、`:163`（唯一的豁免条件 `listingOptOut`）、`:327`（每次 `stock-sync` 结尾都会调用）、`:336-337`（`listingOptOut` 只有手动下架才写）

### ① 问题描述

- **现状**：每次蛋仓同步结束后，服务端会把该账号该角色的**所有**背包蛋重新评估一遍：只要「获得时间 / 蛋重 / 蛋高 / 声音 / 性格」五项齐全，就把 `listed` 置成 `true`（对组内其他成员可见、可申请换）。唯一能拦住它的是 `listingOptOut`，而这个字段**只有本次改动之后**点过「取消挂出」的蛋才会有；代码注释也明说「旧数据没有该字段 = 未下架」。
- **用户影响**：升级前就手动下架过的蛋（按仓库自己的口径，典型是满重蛋和要收藏的绿窝蛋）在升级后第一次同步时被重新挂出。用户什么都没点，自己的蛋却出现在组内广场，别人可以直接发起交换；如果对方接单，这颗蛋会被占成 `reserved`。
- **触发条件**：**必然**，不是偶发。任何在本次版本之前手动下架过完整蛋的账号，升级后第一次蛋仓同步就会触发；有多个角色的账号每个角色都会触发。
- （技术证据：`autoListStock` 是本次新增函数，`eggWorkflow.ts:165-166` 是五项齐全判定，`:163` 只认 `listingOptOut`；`git grep -n 'listingOptOut' d1a4f1c -- src functions` 只有 `eggWorkflow.ts` 与测试命中，**没有任何迁移 / 回填**）

### ② 优化方案

把「升级前就存在且 `listed=false`」的蛋在第一次同步时按「已下架」处理，两条路选一条：

- **A（推荐，改动只在共享状态机）**：在 `EggWorkflowState` 里加一个一次性标记（例如 `autoListSince: number`），同步时只在 `egg.lastConfirmedAt >= autoListSince` 的蛋上自动挂出；标记缺失时先写一次当前时间，早于它的旧蛋一次都不挂。代价：状态多一个字段，旧客户端读到会忽略（不破坏兼容）。
- **B（改动在客户端）**：升级后第一次同步前，把本机已知的 `listed=false` 且字段齐全的蛋在 payload 里带上 `listingOptOut: true`。代价：只能覆盖"这台设备参与过同步的蛋"，换设备的用户漏掉。

选 A 的理由：判定发生在服务端，与设备无关，且不依赖客户端版本。

### ③ 优化后表现

- **解决**：用户升级后不会看到自己的私藏蛋凭空出现在组内广场；之后手动下架的行为照旧生效。
- **验收**：`npx vitest run src/shared/eggWorkflow.test.ts`，新增用例「升级前 `listed=false` 的完整蛋，第一次同步后仍为 `listed=false`」；反例用例「新入包的完整蛋仍然会被自动挂出」保留。

## 2. R4-02 · P1 · 家园里消失的蛋只标记不清理，而「待认领」在线上界面没有出口

**位置**：`src/ui/plan/eggStockModel.ts:152-158`（消失即标 `claimPending`、不删）、`src/ui/plan/EggStockPanel.tsx:137`（家园蛋 `status()` 返回空串）、`src/ui/plan/EggGroupCard.tsx:66-67`（唯一显示「N 待认领」的地方）、`src/ui/plan/EggGroupCard.tsx` 未被任何生产代码引用

### ① 问题描述

- **现状**：家园完整快照里少了一颗蛋时，客户端不再删这一行，而是保留原行并打上 `claimPending: true`（为的是不丢父母 / 自产 / 绿窝）。但线上唯一在用的面板 `EggStockPanel` 对家园蛋的状态返回空串，`claimPending` 一个像素都不显示；唯一会显示「N 待认领」的 `EggGroupCard` / `EggGroupLevel2` 只被自己的测试引用（见 R-03 接线表），面板还没接。服务端也没有任何「认领」动作能把标记清掉。
- **用户影响**：用户在蛋仓里会看到一颗**已经不存在**的家园蛋：没有状态标签、时间和自产标记看着都正常，但永远不会消失。如果这颗蛋其实已经收进背包但没对上（同物种有多颗时按口径"宁可并存"），用户会同时看到家蛋和背包蛋，**同一颗蛋算两次**；他想手工改正也找不到入口。
- **触发条件**：**必然**，只要家蛋离开家园（收进背包、换出、放生）。同物种只有一颗时会被下一次背包快照合并掉（自愈）；**同物种两颗以上时不会自愈**，永久残留。
- （技术证据：`eggStockModel.ts:155-157` 只 `set(claimPending)` 不 `delete`；`eggWorkflow.ts:480/506` 的失效蛋清理只认 `missingFromCapture`，`claimPending` 永远不在清理名单里；`git grep -n 'claimPending' d1a4f1c -- src functions` 在生产代码里只出现在 `eggStockModel` 与未接线的 `EggGroupCard`/`EggGroupLevel2`/`eggStockGroups`；服务端 `applyEggAction` 无 claim / 认领分支）

### ② 优化方案

两件事都要做，顺序建议先 A 后 B：

- **A（先给出口，2~3 屏内可做）**：在 `EggStockPanel` 的家园蛋卡片上直接显示「待认领」徽标 + 一个「认领为背包这颗 / 忽略」的入口，走一条新的 `claim` / `dismiss-claim` 动作（或复用 `label` 动作带上 `capturedEggId`）。
- **B（再给兜底）**：给 `claimPending` 加时效，例如超过 N 次完整家园快照仍未出现、且用户一次都没处理，就只在「清理家园残留」里列出、不进正常库存计数。代价：涉及一条新的清理动作，建议单独一批。

选的顺序理由：A 是用户可感知的修复，B 需要新的删除动作（本轮硬规则禁止删数据），所以 B 只做"不计数"不做"删除"。

### ③ 优化后表现

- **解决**：家园里已经没了的蛋，用户能一眼看到「待认领」并决定怎么处理，不会在库存里无限期冒充一颗真蛋。
- **验收**：`npx vitest run src/ui/plan/EggStockPanel.test.tsx`，新增用例「`claimPending` 的家园蛋卡片带 `待认领` 徽标与处理入口」；再跑 `npx vitest run src/ui/plan/eggStockModel.test.ts` 确认既有「不写 `missingFromCapture`」的用例仍绿。

## 3. R4-03 · P2 · 新买的同种蛋会被并进家园那顆蛋，父母和绿窝跟着错位

**位置**：`src/ui/plan/eggStockModel.ts:138-141`（候选筛选）、`:131-136`（`capturedEggId` 精确链接）、`:104-127`（`mergeCaptured` 的字段继承）

### ① 问题描述

- **现状**：合并分两级。第一级是精确链接（`capturedEggId` 等于背包观测 id），这一级是安全的。第二级是**兜底猜**：只要家园里恰好有 1 颗「同游戏账号 + 同物种 + 没有 `obtainedAt` + 没有 `capturedEggId`」的家蛋，就把这颗背包蛋并进去，不再比对任何其他身份字段。家蛋天然没有 `obtainedAt`，所以这个条件几乎总是成立。
- **用户影响**：用户从别人那里换到 / 买到一颗同种蛋时，蛋仓会**少一颗家蛋、多一颗"带着别人家父母"的蛋**：`parents`、`greenNest`、`provenance: self-bred` 都从家蛋继承过来（`mergeCaptured` 里 `parents: home.parents ?? observation.parents`，而背包观测本身不带父母），蛋重 / 蛋高 / 获得时间来自新蛋。结果是一颗外来蛋被标成自产、还挂着别人的父母，挂出去时按"自产"对待。
- **触发条件**：背包快照里出现同物种的蛋 + 家园里恰好有 1 颗同物种无主家蛋。**偶发但必然会发生**（同物种是最常见的组合：同一个母本连续下蛋）。多颗家蛋时反而安全（`candidates.length !== 1` 就不并）。
- （技术证据：`eggStockModel.ts:138-139` 候选只按 `sameGame + location==='home' + eggGameId 相同 + !obtainedAt + !capturedEggId` 过滤；`homeEggAdapter.ts:170-185` 产出的家蛋观测**从不带 `obtainedAt`**；`src/domain/eggInventory.ts` 的背包观测**从不带 `parents`**）

### ② 优化方案

把「恰好 1 颗同种家蛋」从"可以并"降级成"并了要能反悔"，两个层次一起加：

- **A（判定收紧）**：只在下面两种情况下才允许兜底合并——① 这颗家蛋已经被标成 `claimPending`（上一轮完整家园快照里它就消失了）；② 背包观测的 `obtainedAt` 不早于这颗家蛋第一次被看到的时间。两者都不满足就并存，等用户认领（配合 R4-02 的认领入口）。
- **B（留痕）**：合并时把来源写进行里（例如 `mergedFrom: 'home'` + 原家蛋 id），这样认领 / 撤销时有据可查。

推荐 A+B：A 直接消掉错配，B 让以后出问题能修。代价：A 会让"刚收进背包、还没经过一轮家园快照"的蛋短暂并存两颗（可接受，比错配好）。

### ③ 优化后表现

- **解决**：外来同种蛋不会再顶着别人的父母和自产标记进蛋仓；用户能看出"这两颗要认领一下"。
- **验收**：`npx vitest run src/ui/plan/eggStockModel.test.ts`，新增用例「家园有 1 颗无主家蛋时，新来的同种外来蛋不合并、两颗并存」；保留既有「收进背包能并上」的用例（那条用例的输入应显式带上 `claimPending` 或靠 `obtainedAt` 通过）。

## 4. 字段丢失核查（回答任务书的「有没有路径被清空」）

> 说明：原本单列的「R4-04 · `greenNest` 的显式 false 上行后被丢成未知」**已并入本节**（见表格后的补充说明），所以编号里没有 R4-04 —— 不是漏了。

结论：**`obtainedAt` / `parents` / `greenNest` / `provenance` 都没有被清空的路径。** 但有两个口径细节值得记住：

| 字段 | 客户端合并（`eggStockModel.ts`） | 服务端合并（`eggWorkflow.ts` stock-sync） | 判定 |
| --- | --- | --- | --- |
| `obtainedAt` | `observation.obtainedAt ?? home.obtainedAt`（`:116`）只在新值非空时覆盖 | `normalizeEgg` 解析；`:294` `if (!egg.obtainedAt) egg.obtainedAt = before.obtainedAt`；新行 `:202` 回退 `old?.obtainedAt` | **不会丢** |
| `parents` | `home.parents ?? observation.parents`（`:114`）；背包观测本身不带父母，所以等价于"保留家蛋父母" | `normalizeEgg(capture=true)` 解析 `raw.parents`；`:296` 缺失才继承 `before.parents`；`label` 分支不碰父母 | **不会丢**；但**也永远不会被背包采集补全/更新**（口径事实，非缺陷） |
| `greenNest` | `mergeCaptured` **没有**写 `greenNest`，靠 `...home` 保留；普通小窝的显式 `false` 不会丢 | `normalizeEgg` 只保留 `true`（`:113`），`false` 变 `undefined` → `:291` 从 `before` 继承 → `:309` 按父母回填 `true` | **不会清空**；但"显式普通小窝"上行后与"未知"无法区分（见下） |
| `provenance` | `provenanceOf(...)`（`:66-67`）external > self-bred > unknown，unknown 不能清掉已有标记（`:110`） | `:277` 只有 `unknown` 才会被 `before` 覆盖 | **不会丢**；但历史表见 R4-05 |

**`greenNest` 的补充说明**：用户**手动**标过的 `false` 是安全的（`label` 动作直接写状态，下一次同步走 `:291` 从 `before` 继承）。只有「采集推导出来的显式 `false`」在上行时退化成 `undefined`；界面目前对 `false` 和 `undefined` 都不显示徽标（`EggStockPanel.tsx:137` 一带的绿窝徽标只认 `true`），所以**当前不影响显示**，只影响数据口径与将来的分组统计。要修的话是 `normalizeEgg` 区分「字段缺失」与「显式 false」：`raw.greenNest === true ? true : raw.greenNest === false ? false : undefined`，同时 `mergeCaptured` 补 `greenNest: observation.greenNest ?? home.greenNest`。**建议与 R4-02 的认领入口同批做，不要单独发一版。**

## 5. R4-05 · P2 · 「换来的蛋重复导入不会变自产」的保护，只在这一次页面会话内有效

**位置**：`src/ui/plan/useEggStockSync.ts:75`（水合时把 `provenanceHistory` 清空）、`src/ui/plan/eggStockModel.ts:59`、`:162-171`（历史只在本机内存里参与判定）

### ① 问题描述

- **现状**：`provenanceHistory` 的注释写明「历史不可见库存也要保留，避免收到的蛋重复导入后变成自产」。但它只存在于客户端内存：页面一刷新 / 重开 App，`useEggStockSync` 水合时直接置成 `{}`；服务端状态里没有这个字段，同步也不上行（payload 只有 `eggs`）。
- **用户影响**：用户刷新页面或换设备后，再导入一份旧备份（备份里的 `sourceType` 不是"交换/赠送"，`provenance` 是 `unknown`），那颗**早就换出去的外来蛋**会以 `self-bred` 身份重新出现在蛋仓里。之后它会被当成自产蛋挂出、也可能被当成"自产父母"参与推算。
- **触发条件**：先换出过外来蛋 → 刷新页面（历史清空）→ 导入包含该蛋的旧备份。**必然**，只要同时满足这三步。
- （技术证据：`git grep -n 'provenanceHistory' d1a4f1c -- src functions` 只有 `eggStockModel.ts` 三处与 `useEggStockSync.ts:75` 一处，**服务端零引用**；`useEggStockSync.ts:109-111` 的 payload 只发 `eggs`）

### ② 优化方案

把这份历史变成"和数据一样活的东西"：在服务端 `EggWorkflowState` 里加 `provenanceHistory`（`Record<instanceKey, provenance>`），随 stock-sync 上行合并（口径：只有 `external` 能覆盖，`unknown` 永不覆盖，与 `provenanceOf` 一致）。代价：每个已换出的蛋多一条记录，状态体积增加；需要一次性的字段兼容（缺字段按 `{}` 处理，`eggStockModel` 的兜底已经在）。

### ③ 优化后表现

- **解决**：刷新 / 换设备后重新导入旧备份，换出去的外来蛋不会再变回自产。
- **验收**：`npx vitest run src/ui/plan/eggStockModel.test.ts`（新增「上一轮已记 external，清空内存后重新 reconcile 仍为 external」）+ `npx vitest run src/shared/eggWorkflow.test.ts`（新增「stock-sync 携带 provenanceHistory 且 unknown 不覆盖 external」）。

## 6. R4-06 · P2 · 合并写重试期间某一侧被别的写入顶掉时，客户端仍把这批采集记成已同步

**位置**：`functions/_lib/eggMatching.ts:117-141`（4 次重试，每次重读 `latest` 再 `applyEggAction`）、`src/ui/plan/useEggStockSync.ts:112-116`（只要 2xx 就推进所有侧的采集时间）、`src/shared/eggWorkflow.ts:266-268`（按侧水印决定这一侧写不写）

### ① 问题描述

- **现状**：CAS 失败后重读最新状态再合并。重读后的状态可能已经被**同一账号的机器人入库**（`recordIngestedHomeEggs`）推进了家园侧水印，于是第二次合并会把家园侧判成"没推进"、只写背包侧，但整条请求仍返回 200。客户端拿到 200 后无差别推进 `bag` 和 `home` 两条采集时间，这批数据以后不会再重发。
- **用户影响**：一次采集里"家园那一侧的新蛋"没有被写进服务端，而界面显示同步成功；用户只有在下一次抓包时才会莫名其妙地"少了几颗蛋"，且没有任何错误提示可以追。
- **触发条件**：**偶发**，窗口在毫秒级——第一次 CAS 失败到第二次读之间，恰好有机器人入库同一个账号。**[推测]**：机制从代码可读出来，但我没有复现（要求并发写同一账号，单测需要模拟两次写）。
- （技术证据：`eggMatching.ts:117-141`；`eggWorkflow.ts:266-267` 每侧重算 `applied*`；`useEggStockSync.ts:115` 成功后无条件 `partTimes.current[key] = {...}`）

### ② 优化方案

不要让"重试"改变幂等的前提。两个修法：

- **A（推荐，改动小）**：在响应里回带这次**实际写入了哪几侧**（例如 `synced: { bag: boolean, home: boolean }`），客户端只推进被确认的侧；没写的那一侧保留旧时间，下次同步会自动重发。
- **B**：重试时固定第一次读到的水印基线（把"是否推进"的判定冻结在第 1 次），只有 CAS 成功才按冻结的判定写水印。代价：如果真被别人写走了，会覆盖对方刚写的水印（但蛋行是按 id 合并的，不会丢别人的蛋），需要仔细论证。

推荐 A：客户端本来就持有每侧时间，回带一个布尔数组即可，且不需要动合并语义。

### ③ 优化后表现

- **解决**：偶发的"一侧没写但显示成功"变成"下次自动重发"，用户不再丢采集。
- **验收**：`node --test tools/test/egg-matching-api.test.mjs`（新增「第一次 CAS 失败、第二次家园侧已被别人推进 → 响应 `synced.home=false`」）；阈值确认后再补一条 vitest 覆盖 `useEggStockSync` 只推进确认过的侧。

## 7. R4-07 · P2 · 重复标注同一批蛋仍会把小组版本号 +1，别人手里的版本白作废

**位置**：`src/shared/eggWorkflow.ts:341-358`（`label` / `label-many` 无条件写入）、`functions/_lib/eggMatching.ts:187-191`（空操作判定）

### ① 问题描述

- **现状**：本轮给服务端加了"空操作不写库、不推进版本"的判定，但判定方式是**对象引用相等**（`next === current.state`），而 `label` / `label-many` 无论值有没有变化都会 `Object.assign` 进克隆体，所以永远判定为"有变化"。
- **用户影响**：用户重复点一次「标注同类蛋」（值一点没变），小组版本号仍然 +1；此时别的成员正在提交需求 / 接单，就会看到「小组数据已变化，请刷新后重试」——这正是本轮想消掉的那类假冲突。
- **触发条件**：**必然**，只要重复提交同一组标注值。频次取决于 UI 是否防重复点击。
- （技术证据：`eggWorkflow.ts:349-356` 无"值相同就跳过"的比较；`eggMatching.ts:187` 只判引用）

### ② 优化方案

在 `label` / `label-many` 里先比较再赋值：逐颗判断 `nature` / `body` / `voice` / `greenNest` / `labelSource` 是否都已经是目标值，全都没变就 `return previous`。代价：多一次字段比较，忽略不计。

### ③ 优化后表现

- **解决**：重复标注不再制造版本冲突；"空操作不 +1"这条规则对所有幂等动作都成立。
- **验收**：`npx vitest run src/shared/eggWorkflow.test.ts`，新增用例「同一组标注重复提交返回同一个 state 对象」。

## 8. R4-08 · P2 · 被移出小组后，蛋仓同步要重试 4 次才报「正在被其他人更新」

**位置**：`functions/_lib/eggMatching.ts:132-134`（`UPDATE ... AND EXISTS (成员存在)`）、`:141-143`（重试耗尽统一返回 `SYNC_BUSY`）

### ① 问题描述

- **现状**：写语句里带了「当前账号仍是组成员」的条件。账号被移出（或自己退组）后，4 次 CAS 全部落空，最后统一返回 409 `SYNC_BUSY`「蛋仓正在被其他人更新，请稍后再试」。
- **用户影响**：用户被移出小组后，蛋仓每次打开都要等 4 轮往返，然后看到一句"稍后再试"——他会一直重试，而真实原因是没权限。客户端也不会因此去刷新组列表，界面停留在过期的小组上。
- **触发条件**：**必然**，被移出 / 自己退组后打开蛋仓或换蛋广场。
- （技术证据：`eggMatching.ts:132-134` 的 `EXISTS (SELECT 1 FROM mother_group_members ...)`；`:143` 用 `SYNC_BUSY` 覆盖了所有耗尽情形）

### ② 优化方案

重试耗尽后先判一次原因，再决定错误码：成员行不存在就返回 `403 NOT_MEMBER`（并让客户端在收到 `NOT_MEMBER` 时清掉当前组、刷新组列表），只有成员仍在才返回 `SYNC_BUSY`。代价：多一条查询，只在失败路径上。

### ③ 优化后表现

- **解决**：退组 / 被移出后用户看到「你已经不在这个小组」，而不是"稍后再试"的死循环。
- **验收**：`node --test tools/test/egg-matching-api.test.mjs`（新增「成员被移除 → stock-sync 返回 `NOT_MEMBER`」）。

## 9. R4-09 · P2 · 机器人上报没有限流；4 次冲突用尽后抛异常变 500

**位置**：`functions/_lib/eggBotBridge.ts:72-101`（`ingest` 分支，**没有** `rateLimit`；对比同文件 `:32` 的设置接口有 30 次/时限流）、`functions/_lib/eggPatrolStock.ts:74-87`（4 次 CAS 重试，最后 `throw new Error('INGEST_STATE_CONFLICT')`，`:82` 还会抛 `STATE_CAPACITY`）

### ① 问题描述

- **现状**：机器人上报这条路的合并逻辑本身是对的（读最新 → 合并 → `WHERE version=?` CAS → 空操作直接返回不写库），**没有重复写**。但两处兜底缺失：① `ingest` 没有任何限流，持有 binding token 的调用方可以按请求体上限反复触发「读 1.5MB state → 改 → 写」，直接烧 D1；② 4 次冲突都失败（或多组同时写导致连续被抢）时抛错，`handleEggBotBridge` 没有捕获 → Functions 直接 500，机器人这一批上报既没落库、也拿不到可重试的 JSON。
- **用户影响**：并发高峰（用户同时改蛋仓 + 巡查 + 多次上报）时机器人的一批家园蛋可能丢，用户在蛋仓里看不到刚下的蛋；token 泄漏时是无上限的写入成本。机器人是否对 500 重试是**外部行为，静态确认不了**。
- **触发条件**：**偶发**（需要 4 次连续被抢）。**[推测]** 冲突路径没有用例覆盖（`eggBotBridge.ingest.test.ts` 5 条只覆盖成功 / 幂等 / 未绑定）。
- （技术证据：`:72-101` 无 `rateLimit`；`eggPatrolStock.ts:87` 的 throw 与调用方无 try/catch）

### ② 优化方案

① `ingest` 加 `rateLimit`（按 `groupId` + `botId`，例如 30 次/分钟）；② 把 `STATE_CAPACITY` / `INGEST_STATE_CONFLICT` 捕获成 `409`/`503` 的 JSON（`{ ok:false, retryable:true }`），或失败入队交给 `tick` 重试；③ 重试之间加短退避（现在 4 次是背靠背）。代价：①②各几行，③需要一次 sleep（Workers 里可用 `scheduler.wait` 或干脆不做）。

### ③ 优化后表现

- **解决**：机器人拿得到"可重试"的明确答复，不会再因为一次冲突丢一批蛋；token 泄漏的爆炸半径受限。
- **验收**：`npx vitest run --config vitest.functions.config.ts functions/_lib/eggBotBridge.ingest.test.ts`，新增"version 每次都变 → 返回可重试错误且不丢数据"用例 + 限流用例。

## 10. 服务端同步的两个明确结论（先说清楚，免得下轮重审）

1. **CAS 重试不会丢别人的写 [实测]**。写语句是 `UPDATE ... WHERE group_id=? AND version=?`（`eggMatching.ts:132-134`），重试前 `readState` 重读（`:140`），所以后写者一定基于最新版本合并；失败只回滚自己的这一次。第 4 次仍冲突就明确报 `SYNC_BUSY`（`:143`），不静默丢这批蛋。
2. **放宽 stock-sync 没有连带削弱其它 action 的版本锁 [实测]**。`stock-sync` 在 `:171-173` 提前返回，其它 action 仍在 `:174-175` 校验 `baseVersion`，`:206-208` 的 CAS 也没改；`:187-191` 的空操作判定对其它 action 只是"少推进一次版本"，不放大写入权限。**唯一的连带影响**是 R4-07（`label` 系仍会推进版本）。
