## 0. 结论

本轮把不少东西"收口"了（占窝勾选统一进 `nestPicksStore`、蛋仓同步抽成 `useEggStockSync`、蛋仓屏搬进家园页），但**「同类蛋」这个最常被用户念出来的词，现在有三套意思**：

- 面板/聚合：同类 = 同物种蛋，**在当前角色、当前筛选下能看见的那些**（`eggStockGroups.ts:104-107`）；
- 批量标注动作：同类 = **该账号下全部同物种蛋**，跨游戏角色、含换蛋中、含异色/特殊（`eggWorkflow.ts:345`）;
- 用户理解：卡片上写着 `×5`，以为点下去就改这 5 颗。

这三套意思在**线上已经能出事**（不只是接线后的隐患）：批量标注会把这一颗的绿窝标记刷给每一颗同种蛋，而且只要同种蛋里有一颗正在换蛋中，整批标注直接报错、一颗都不写。这是本册的 P1 之一。

另一个 P1 是同一份数据两个范围：账号筛选后 `plans` / `coverageByAccount` 只按选中号算，但配窝卡会为"出蛋源号"生成页签 —— 那个页签拿到的是空方案（看不到该号种公配窝、窝数也对不上）。

## 1. R4-10 · P1 · 「标注所有同类蛋」改的是账号下全部同种蛋，还会把绿窝标记刷给每一颗

**位置**：`src/ui/plan/EggStockPanel.tsx:246`（按钮，传 `labelValues(egg)`）、`:173-180`（`labelValues` 里带 `greenNest: isGreenNestEgg(target)`）、`:140`（列表按角色/搜索/筛选过滤）；`src/shared/eggWorkflow.ts:345`（`label-many` 的目标集合）、`:349-356`（逐颗 `Object.assign`，含 `greenNest`）、`:350` + `:178-180`（任一颗不可流通就抛错）

### ① 问题描述

- **现状**：用户在蛋详情里点「标注所有同类蛋」，前端把**当前这一颗**的性格 / 体型 / 声音 / **绿窝**一起打包发上去；服务端按 `accountId + eggGameId` 取出**所有**同物种蛋（不区分游戏角色、不排除换蛋中 `reserved`、不排除异色/特殊），逐颗 `available()` 检查后把这四个值**无条件覆盖**上去。
- **用户影响**：三个具体后果——① 同账号有多个游戏角色且都有同种蛋时，改的是**看不见的那个角色**的蛋（changelog 明明已经宣布「蛋仓按角色查看：一次只看一个角色」）；② **绿窝标记被批量刷成这一颗的值**：一颗绿窝 + 一颗普通窝的同种蛋，点一次就把普通那颗标成绿窝（绿窝是用户很在意、且会参与需求匹配的标记）；③ 同种蛋里只要有**一颗**在换蛋中或不可交换，`available()` 抛错，整批标注失败、一颗都不写，用户看到「蛋已占用或为不可交换的异色/特殊蛋」，以为是这颗蛋的问题。
- **触发条件**：②③ **必然**（3 颗同种蛋里有 1 颗换蛋中就是常见情形）；① 需要多角色 + 同物种。注意：`label-many` 的动作实现与按钮在基线 `f952a93` 就存在，**不是本轮引入**；但本轮新写的聚合模块把"同类 = 当前屏可见的同物种蛋"固化成另一套口径，接线后卡片上的 `×N` 天然会被读成"要点下去改的颗数"，冲突会立刻显形。
- （技术证据：`eggWorkflow.ts:345` 的过滤只有 `accountId + eggGameId`；`:353` 的 `greenNest` 与 `:351-355` 的 `Object.assign`；`:178-180` 的 `available` 直接 throw；`EggStockPanel.tsx:173-180` 把 `greenNest` 一起打包；`git grep -n 'label-many' d1a4f1c -- src` 只有面板与 `eggWorkflow` 两处）

### ② 优化方案

三层一起改，按代价从低到高：

- **A（修错配，必须先做）**：`label-many` 增加可选 `gameAccountKey`，只标该角色；`targets` 里跳过 `canCirculateEgg` 为假的蛋，把"跳过 N 颗"回传给前端提示「已标注 X 颗，跳过 Y 颗（换蛋中 / 不可交换）」，而不是整批抛错。
- **B（修误覆盖）**：`greenNest` 这类"逐颗事实"不随批量动作写入，或只对"该值为空"的蛋补写（现在是无条件覆盖）。性格 / 体型 / 声音同理，建议只在空值时补。
- **C（对齐口径）**：给面板加一层 `groupEggStock(visible, facts)`，让卡片数字与批量动作的作用集合用**同一个**集合（见 R4-15 / R-04 的 NEW-02）。

选 A+B 作为第一批：A 消除"改到看不见的蛋 / 整批失败"，B 消除"绿窝错标"；C 与聚合接线同批做。

### ③ 优化后表现

- **解决**：批量标注只影响当前角色、只影响能改的蛋，绿窝不会被顺手刷错；有跳过时用户能看到提示。
- **验收**：`npx vitest run src/shared/eggWorkflow.test.ts src/ui/plan/EggStockPanel.test.tsx`，新增两条用例——① 同种蛋含一颗 `reserved` 时批量标注成功且跳过它；② 两个 `gameAccountKey` 同物种时只改选中的那个。

## 2. R4-11 · P1 · 账号筛选下，出蛋号页签拿到空配窝方案（看不到该号种公配窝，窝数少算）

**位置**：`src/ui/useCollectionSummary.ts:51`（`owned` 来自 `useOwnedPets()`，是**按账号筛选后**的集合，`all` 才是全量）、`:97-100`（`coverageByAccount` 用 `owned`）、`:105-108`（`plans` 用 `owned`）；`src/ui/Dashboard.tsx:288-297`（把这份 `plans` 传给配窝卡）；`src/ui/NestPlanCard.tsx:1314-1332`（账号全集 = `plans` 的号 + 母本建议里的源号，缺方案时 `plan ?? emptyNestPlan(account)`）

### ① 问题描述

- **现状**：账号筛选只选一个号时，母本建议里其他号会作为 `sourceAccount`（出蛋源）出现，于是配窝卡会为源号生成页签；但 `plans` 只含**当前选中账号**，源号落到 `emptyNestPlan(account)` —— `nestsTotal = 0`、`views = []`。
- **用户影响**：用户按界面提示「到出蛋号页签勾选占窝」切过去，看到的是**一半空的计划**：该号的种公配窝看不到；`pickedNestsOf` 只认 `selectableCardsOf`，之前勾过的种公卡也统计不到，标题只写「用 2 个窝」而不是「2/11」——用户会按错误的空位数继续配窝。同一处还会让**跨号建议**退化（`coverageByAccount` / `plans` 缺失时，"该号已有同种种公 / 已占窝 / 未覆盖格"这些判断全部取空）。
- **触发条件**：**必然**，只要"账号筛选选单个号 + 该号在母本建议里出现别的号作为源"（2026-11-24 新交互的主要场景）。
- （技术证据：`useCollectionSummary.ts:51` 的 `owned` 与 `allOwned` 两个来源；`:105-108` 用 `owned`；`NestPlanCard.tsx:1326-1332` 的 `plan ?? emptyNestPlan`。测试盲区：`NestPlanCard.test.tsx:1378-1396` 手工给源号传了 `planB` 并断言 `2/11`，生产路径没有传，所以测不出来）

### ② 优化方案

让"账号全集"的数据与"精灵全集"配套：`useCollectionSummary` 再暴露一份 `allPlans` / `allCoverageByAccount`（用 `allOwned` 算），`Dashboard` 传给 `NestPlanCard` 与 `useMotherSuggestions`；或者把 `plans` 改成按 `allOwned` 算、由使用方自己按选中号过滤。**注意**：`plans` 里"本号缺口"这类数字仍应只用选中号，别一起换口径。

代价：多算一份（全量）方案，需要 memo；口径要写进注释，否则下一个人会把它当成重复计算删掉。

### ③ 优化后表现

- **解决**：切到出蛋号页签能看到该号完整的种公配窝与正确窝数，跨号建议也不会因为缺数据退化。
- **验收**：新增 `NestPlanCard` 用例——只传目标号的 plan、`motherSuggestions` 含源号 task，断言源号页签显示其 `nestsTotal` 与种公卡；再跑 `npx vitest run src/ui/NestPlanCard.test.tsx src/ui/Dashboard.test.tsx src/ui/useMotherSuggestions.test.tsx`。

## 4. R4-13 · P2 · 声音平均与体型档位各写了两份，体型还少了两档

**位置**：`src/shared/eggLabels.ts:19-21`（`averageVoice`）与 `src/domain/nestPlan.ts:58-60`（同名同实现，逐字相同）；`src/shared/eggLabels.ts:24-29`（`bodyMedalOfWeight` 只返回 `'' | 大块头 | 小不点`）与 `src/domain/eggInventory.ts:53`（返回 `满体重 | 零体重 | 大块头 | 小不点 | unknown | ''`）

### ① 问题描述

- **现状**：`averageVoice`（(父+母)/2 向零取整）在两处各写一份、各有一套测试；体型档位两套口径——**背包抓包**会用克数判断"正好等于物种最大/最小体重"→ `满体重`/`零体重`，而**家园抓包**（`bodyGradeOf`）与**机器人入库**（`bodyMedalOfWeight`）只到 `大块头`/`小不点`。
- **用户影响**：同一颗"满体重"的蛋，从背包进库显示「满体重」，从家园/机器人进库只能显示「大块头」；`canMatchDemand` 专门为这个差异写了兼容（`eggMatching.ts:123-125`），说明这是**已知差异**，但"满分档"在家园蛋上永远取不到，用户会看到同物种的蛋标签不一致。
- **触发条件**：**必然**，只要用户同时有背包蛋和家园蛋（很常见）。
- （技术证据：三处函数逐行比对；`eggLabels.ts:4-8` 的注释自己写着"避免两条入口对同一颗蛋标出不同的声音"，说明作者在意这件事，但只搬了声音、没搬体型）

### ② 优化方案

① `nestPlan.ts` 的 `averageVoice` 改成从 `shared/eggLabels` 再导出（保留一份实现 + 一处测试）；② 体型统一：`eggLabels` 增 `bodyLabelOfWeight(size, grams)`，把 `eggInventory.ts:53` 的满/零体重判定搬进来复用，`homeEggAdapter` 与 `eggPatrolStock` 都走它（家园蛋没有 `weightGrams` 时仍回 `unknown`）。代价：一次跨 3 个文件的重构，建议单独一批。

### ③ 优化后表现

- **解决**：同一颗蛋不管从哪条入口进来，声音/体型档位一致。
- **验收**：`npx vitest run src/domain/nestPlan.test.ts src/ui/plan/homeEggAdapter.test.ts src/shared/eggPatrolStock.test.ts src/domain/eggInventory.test.ts`，新增"背包蛋与家园蛋同体重得到同一 body 档"。

## 5. R4-14 · P2 · 绿窝的"显式 false"存在两套口径：一边认真写 false，另一边丢弃 false

**位置**：`src/ui/plan/homeEggAdapter.ts:179`（`greenNest: academyParents.length > 0`，注释明写"普通小窝 → false（不是缺失）"）；`src/shared/eggWorkflow.ts:113`（`normalizeEgg` 只保留 `true`，`false` 变 `undefined`）、`:291`（undefined 才从 `before` 继承）、`:309`（按父母回填 `true`）

### ① 问题描述

- **现状**：抓包入口把「普通小窝」表达成显式 `false`，并把"false 和 undefined 不是一回事"写进注释；但服务端 `normalizeEgg` 只认 `true`，`false` 一到服务端就变成 `undefined`，随后要么从上一行继承、要么按父母回填。也就是说：**客户端认为 false 有意义，服务端不认**。
- **用户影响**：当前**不影响显示**（面板绿窝徽标只认 `true`），所以不列 P1。但它让"这颗蛋明确不是绿窝"这个事实在服务端无法表达：将来任何按 `greenNest === false` 统计/筛选的功能都会漏；一旦某次采集没采到亲本的学院窝信息，也只能表现为"未知"而不是"否"。
- **触发条件**：所有从抓包进来的普通小窝蛋。
- （技术证据：`normalizeEgg` 的 `...(raw.greenNest === true ? { greenNest: true } : {})`；对照用户**手动**标的 `false` 是安全的——`label` 动作直接写状态，下一次同步走 `:291` 从 `before` 继承。**注意**：子代理曾推测"抓包 false 会覆盖机器人写的 true"，**这条不成立**，因为 false 在 `normalizeEgg` 就被丢了，详见 §6）

### ② 优化方案

`normalizeEgg` 区分「字段缺失」与「显式 false」：`raw.greenNest === true ? true : raw.greenNest === false ? false : undefined`；继承逻辑保持 `=== undefined` 才继承；`mergeCaptured`（客户端 `eggStockModel.ts:104-127`）补 `greenNest: observation.greenNest ?? home.greenNest`。代价：一处共享状态机 + 一处客户端合并，需补 2 条用例。

### ③ 优化后表现

- **解决**：普通小窝在服务端能表达成"否"，不再是"未知"。
- **验收**：`npx vitest run src/shared/eggWorkflow.test.ts src/ui/plan/eggStockModel.test.ts`，新增"显式 false 能上行且不会被父母回填改成 true"。

## 6. 关于「抓包 false 会不会覆盖机器人 true」的更正（避免下轮重复排查）

有同学推测：某次抓包没采到亲本的学院窝信息 → `homeEggAdapter` 写 `greenNest: false` → 会把机器人入库的 `greenNest: true` 覆盖掉。**这条不成立 [实测]**：`normalizeEgg` 在 `eggWorkflow.ts:113` 就把 `false` 丢成 `undefined`，随后 `:291` 从 `before` 继承 `true`，`:284` 的 manual 分支也会保住 `before.greenNest`。所以"抓包丢信息 → 绿窝变灰"这个担心在当前代码下不会发生；真正的问题只有 §5 的"false 无法表达"。

## 14. R4-22 · P2 · 三维字段沿用有两套身份键：老数据退回「槽位 + 名字」，可能安到另一只精灵头上

**位置**：`src/domain/backup.ts:249-253`（`petIdentityOf`：有 `captureId` 用 `id:`，否则退 `slot:物种|名字|盒组|盒号|槽位`）、`:256-258`（同一身份重复时整组丢弃）、`:301-319`（`mergePetBonusFields` 只补字段、不增删宠物）

### ① 问题描述

- **现状**：本轮新增的"三维字段级沿用"用两套身份：抓包给了唯一编号 `captureId` 就用它；老数据没有时退回**物种 + 名字 + 盒子位置**。同一身份在当前快照里出现两次会整组跳过（这层保护是对的）。
- **用户影响**：老采集器/老备份没有 `captureId` 时，用户换盒、挪位、放生后又抓到一只**同物种、同名字、同一个槽位**的精灵，它会继承旧快照的三维数值。用户看到的是错误的三维，而且**无法察觉、也清不掉**（它是"沿用"而不是"导入"）。风险不在"丢"而在"安错"。
- **触发条件**：**窄**——需要无 `captureId` 的旧数据 + 槽位被同种同名精灵复用。**[推测]**，需构造两份无 `captureId` 且槽位复用的快照才能复现。
- （技术证据：`backup.ts:249-253` 的两级身份；`:315` 只在"当前快照里该身份不唯一"时跳过，**不校验旧快照侧的槽位是否被换过**。`backup.test.ts` 27 条多用 `captureId`，没有覆盖槽位复用）

### ② 优化方案

保守方案（推荐）：**只对 `captureId` 做沿用**，无 id 不补 —— 少补一点三维，但不会安错。次选：加"两份快照采集时刻相差不超过 N 小时"的限制；或在界面上给沿用的三维标一个"沿用旧快照"的角标，让用户能看见。

### ③ 优化后表现

- **解决**：不会把旧精灵的三维装到新精灵身上。
- **验收**：`npx vitest run src/domain/backup.test.ts`，新增"无 `captureId`、同槽同名不同宠物 → 不继承"（按采纳方案）。
