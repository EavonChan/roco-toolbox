## 结论摘要（先看这八条）

1. **「获得时间」不是入库时丢的，是在浏览器端 `reconcileEggStock` 就被丢掉的**：它按固定字段重建每一颗蛋，`obtainedAt` 既不在 `EggObservation` 类型里，也没有被复制进新对象；发给服务端的 payload 从来就没带过这个字段。
2. **「自产」丢是因为背包蛋和家园蛋是两套 id，采集时没有做身份合并**：家园蛋 id 是 `[uid,"home",actorId]`，收进背包后变成 `[uid,externalEggId]`，旧行被 complete 快照清掉、新行来源只能是 `unknown`，自产信息没有载体。
3. **「整份覆盖」是 `complete` 语义的必然结果**：客户端在部位 `complete=true` 时删掉不在本次快照里的蛋，服务端再把该「账号 + 游戏账号」的整批蛋替换成 payload 里的集合。只要这次抓包被判为完整快照，就是整份覆盖；判为不完整（`complete=false`）才表现为「只增不删」。
4. **用户记忆里的修复确实存在，但从未进主线**：`c268d6b`（2026-11-21，分支 `codex/test-personal-stock-20261121`）实现了 `mergeCaptured` / `capturedEggId`，能把背包观测合并到唯一的自家家园蛋上并保留获得时间、体重、身高、自产；仓库里所有分支只有那一条包含它。
5. **正式版「不覆盖但也没数据」不是版本更好**：实测正式站与测试站这段写入代码逐字相同（见 §5），所以正式版同样写不进获得时间与自产；它「不覆盖」只能说明那次同步没以 `complete=true` 执行（或没触发），不是代码差异。
6. **两份对照 pcap 证明「采集没丢、写入才丢」**：`capture-内测.pcap` / `capture-正式.pcap` 各解出 **117 颗蛋**，`obtainedAt / weightGrams / heightCm / itemConfId` 全部 **117/117**，两份逐字段 **0 差异**；`reconcileEggStock` 是唯一丢获得时间的环节。**原始报文里没有「自产」布尔字段**，只有 `sourceType`（活动 34 / 巢穴 79 / 普通 4），自产只能由本地规则推断或从家园蛋身份继承（见 §7）。
7. **家园三维「时有时无」不是采集问题**：两份 pcap 的 **610/610** 只精灵都带 `individualBonuses`，家园 11 个住户 **11/11** 匹配到带三维的背包精灵；正式站 bundle 里连 `individualBonuses` 字段名都没有（功能只在 test），再叠加云同步/导入的**整份快照替换**，才会出现「有时有、同步后又没了」（见 §8）。

## 三、根因（函数 + 行号 + 代码）

### 3.1 获得时间：`reconcileEggStock` 重建对象时丢字段（确认）

`src/ui/plan/eggStockModel.ts:4-8` —— 观测类型里根本没有 `obtainedAt`：

```ts
export type EggObservation = Pick<EggRecord, 'id' | 'eggGameId' | 'nature' | 'body' | 'voice'> &
  Partial<Pick<EggRecord, 'provenance' | 'confidence' | 'kind' | 'labelSource' | 'parents' |
    'specialCategory' | 'greenNest' | 'heightCm' | 'weightGrams' | 'itemConfId' | 'location'>> & {
    gameAccountKey?: string;
  };
```

`src/ui/plan/eggStockModel.ts:104-117` —— 新行是逐字段拼出来的，没有 `obtainedAt`（对比：`heightCm` / `weightGrams` / `itemConfId` 有，所以「蛋重/蛋高有」）：

```ts
const egg: StockEgg = { id: observation.id, accountId: snapshot.accountId, eggGameId: observation.eggGameId,
  nature: observation.nature, body: observation.body, voice: observation.voice,
  provenance, confidence: observation.confidence ?? 'unknown',
  ...
  heightCm: observation.heightCm ?? old?.heightCm,
  weightGrams: observation.weightGrams ?? old?.weightGrams,
  itemConfId: observation.itemConfId ?? old?.itemConfId,
  ... };
```

而输入侧明明有值（`src/domain/eggInventory.ts:60`）：

```ts
heightCm: raw.heightCm, weightGrams: raw.weightGrams, obtainedAt: raw.obtainedAt, itemConfId: raw.itemConfId });
```

`src/ui/plan/useEggStockSync.ts:84-89` 直接把重建后的 `nextStock.eggs` 发出去，所以服务端 `eggWorkflow.ts:233-234` 的「缺时间时保留旧获得时间」永远没有可保留的输入：

```ts
// 新抓包偶尔缺时间时，保留已经记录过的获得时间。
if (!egg.obtainedAt) egg.obtainedAt = before.obtainedAt;
```

**结论：首次同步就没有 `obtainedAt`，服务端也没有历史值，UI 只能显示「采集数据里没有获得时间」。**

> 对照实验佐证（§7）：两份真实 pcap 解出的 117 颗蛋全部带 `obtainedAt`，说明抓包与解码都没丢，丢点就在 `reconcileEggStock` 这一步。

### 3.2 自产：家园蛋与背包蛋 id 不贯通，没有合并（确认）

- 背包蛋 id：`JSON.stringify([gameAccountKey, instance])`（`src/domain/eggInventory.ts:54`）
- 家园蛋 id：`JSON.stringify([accountKeyOf(snapshot), 'home', egg.actorId])`（`src/ui/plan/homeEggAdapter.ts:164`；来源 `self-bred` 在 `:170`。协议与已知限制见 `docs/换蛋-家蛋进蛋仓-方案-2026-11-17.md` §6「身份不贯通」）
- 背包蛋的来源只有两种（`eggInventory.ts:56`）：

```ts
provenance: raw.sourceType === '交换' || raw.sourceType === '赠送' ? 'external' : 'unknown',
```

抓包里没有「这蛋是我自己孵的」信号，所以背包蛋天然是 `unknown`。自产信息唯一来源是**家园蛋行**（`homeEggAdapter` 写 `provenance:'self-bred'`）。蛋收进背包后：

1. 下一次完整家园快照里没有这颗蛋 → `reconcileEggStock:68-74` 把家园行删掉；
2. 背包里出现新 id 的蛋 → 新建一行 `unknown`；
3. 两行不是同一身份，`provenance` 无法继承。

当前 reconcile 只在 **同 id** 时继承来源（L82-84）：

```ts
const known = [observation.provenance, history[key], old?.provenance];
const provenance: EggRecord['provenance'] = known.includes('external') ? 'external'
  : known.includes('self-bred') ? 'self-bred' : 'unknown';
```

id 一变，`old` / `history` 都命中不了。于是「自产」标记随旧行一起被删。

### 3.3 「整份覆盖」：complete 语义 + 服务端整批替换（确认）

客户端（`eggStockModel.ts:68-74`）：

```ts
for (const location of ['bag', 'home'] as const) {
  const part = snapshot[location];
  if (part?.complete) {
    const currentIds = new Set(part.eggs.map(e => e.id));
    for (const [id, egg] of next) if (sameGame(egg) && egg.location === location && !currentIds.has(id)) next.delete(id);
  }
}
```

服务端（`eggWorkflow.ts:244-251`）：

```ts
for (const egg of old) { ... egg.missingFromCapture = true; egg.listed = false; }
state.eggs = state.eggs.filter(e => !(e.accountId === actor && e.gameAccountKey === key) || !sideApplied(e) ||
  (!accepted.some(n => n.id === e.id) && (!sideComplete(e) || e.status === 'reserved' || e.status === 'transferred')));
state.eggs.push(...accepted);
```

也就是说：**payload 里没有的旧蛋，只要本次部位 complete，就会从服务端删掉。** 客户端删除 + 服务端替换是同一件事的两端，不存在「服务端替客户端兜底」。

`complete` 怎么来的（`eggInventory.ts:62-63`）：

```ts
return { ..., complete: snapshot.eggInventoryComplete === true && unresolvedCount === 0, eggs, unresolvedCount };
```

→ 抓包里只要有一颗没解析出来的蛋，`complete=false`，这次就变成「只增不删」；全部解析成功则是「整份替换」。**这解释了为什么同一个人在两个账号/两次采集上看到的覆盖行为不同，但不是代码版本不同。**

### 5.2 那为什么一个覆盖、一个不覆盖？（推断，高置信）

唯一能造成差异的开关是 `complete`（`eggInventory.ts:62-63`）+ 服务端整批替换（`eggWorkflow.ts:249-251`），而 `complete` 取决于**这次抓包本身**：

- `eggInventoryComplete === true` 且 `unresolvedCount === 0` → `complete=true` → 客户端删旧蛋、服务端整批替换 → 「整份覆盖」；
- 只要有一颗蛋没解析出来（或抓包声明不完整）→ `complete=false` → 只增不删 → 看起来「不覆盖」。

所以最可能的解释是：**测试账号那次是完整快照，正式账号那次不是（或正式站那次同步根本没触发：未入组 / 水位没前进 / 接口报错被 `syncError` 吃掉）**，而不是正式版代码更正确。同一份正式版代码，只要拿到一次 `complete=true` 的抓包，一样会整份覆盖。

### 5.3 为什么正式版「拿不到获得时间 / 自产」（确认）

不是正式版少功能，而是这条管道在两端都没接上：

### 8.1 字段、改名与兼容性

### 8.3 为什么「有时有、有时空」（按可能性排序）

1. **正式版根本没有三维功能（确认）**：线上正式 bundle `index-CsU6PiGS.js` 里 `individualBonuses` / `rawFields` 出现次数都是 **0**，测试站 `index-Dhf8s1i0.js` 是 **6 / 1**；`a19fbd1` 的 `NestPlanCard` 里也没有 `individual` 相关代码。1.6.0 App 只是加载正式站，所以正式版永远空白，切到内测/测试站就有——这是「时有时无」最直接的解释。
2. **整份快照覆盖（确认机制）**：`mergeSnapshots` 按「数据时刻」整份取较新（`backup.ts:253-305`），云同步平局取云端（`sync.ts:191`），`mergeImportedSnapshot` 只在 incoming 没带家园时保留本地家园（`backup.ts:228-234`），**不按字段合并 pets**。只要有一份更新的、但不含三维的快照（例如正式版导入/上传，或旧备份 JSON），带三维的 `pets` 会被整份换掉：表现为「同步一次后空白，重新导入新抓包又出现」。
3. **旧备份 / 旧采集器 JSON（确认）**：1.6.0 导出的**备份 JSON** 里既没有 `individualBonuses` 也没有 `rawFields`（`sanitizePet` 显式字段列表）→ 解不出三维；旧**采集器 JSON** 只有 `individualStats` 名字，但通常带 `rawFields.bytes["14"]`，新版能兜底解出数值。这是唯一与「改名」相关的兼容问题，而 `individualStats` 本身无法恢复数值。
4. **住户↔背包匹配失败（本次数据已排除）**：`petsByInstance` 用 `captureId` 最后一段匹配住户 `instanceId`；两份 pcap 的 11 个住户 **11/11 匹配成功、11/11 有三维**，所以这两份数据不是匹配问题。匹配失败时会整张卡没有 pet（性格/声音也一起空），可作为其他样本的排查点。
5. **渲染无兜底（确认）**：`NestPlanCard` 缺字段直接 `?? []`，不提示「未采集」，用户无法区分「没采到」和「丢了」。

### 8.4 三维的修复建议（只列方案）

1. **先发版**：把 `46bf7f9`（PR #15）随 `test → release` 发正式站。这是当前「正式版没有三维」的根治项，成本最低、收益最大。
2. **合并时做字段级保护**：`mergeImportedSnapshot` / 云同步合并 pets 时，若 incoming 的同一 `captureId` 缺 `individualBonuses` 而本地有，保留本地值；或给快照带一个「客户端能力版本」，低于支持三维的版本不允许覆盖该字段。**不要整份回退**。
3. **旧 `individualStats` 兼容**：只用于「知道有三维但数值缺失」，不要伪造数值；在详情里写「该快照为旧版本采集，未记录三维数值」。
4. **渲染兜底**：缺三维时显示「—」并带 tooltip，不要把「没采到」静默成空白。
5. **匹配兜底**（可选）：`petsByInstance` 失败时回落到「同名唯一」（家园页已有类似口径），减少整卡空白。
6. **回归测试**：
   - `mergeImportedSnapshot`：incoming pets 缺 `individualBonuses`、本地有 → 合并后仍在；
   - 旧 JSON（`individualStats: string[]`）导入不崩溃、不覆盖本地三维；
   - `petsByInstance`：`captureId` 末段匹配成功 / 同名唯一兜底；
   - 家园卡：有三维显示三格，无三维显示「—」而不是空白。

### 9.4 问题 3：绿窝应该看母本 / 蛋所在窝

**推断（协议 + 游戏规则，非本报文样本）**：

1. 蛋带自己的 `furnitureGuid`；母本 = 这个窝里的母住户；父本被明确排除在「蛋窝」之外（`homeEggAdapter.ts:111-112`）。
2. 因此「绿窝蛋」的语义 = **蛋所在窝（母本窝）是学院小窝**，即 `mother.academy === true`（或直接读蛋窝的 `nestType`）。
3. **`任一亲本 academy` 会误标**：父本在学院小窝、母本在普通小窝时，蛋实际在母本的普通窝里，却被标成绿窝。
4. 「学院那只 100% 遗传性格」是**另一条规则**，可能确实要看任一学院亲本（父本在学院也算）；不要把它和「绿窝」标记绑死（**推断，待产品确认**）。

而 `e0c7d1d` 已经把 `EggStockPanel` 的用例从「父本学院」改成「母本学院」，但**代码和 adapter 测试仍按任一亲本**——两处语义已经不一致（**实证**）。

**建议（只写方案）**：

- `greenNest` 改为只看 `motherInfo?.academy === true`（或蛋窝 `nestType`），`academyParentsOf` 保留给「100% 性格」推断，两者拆开；
