# 分析：蛋仓页反复弹「小组数据已变化」+「蛋仓同步失败」（2026-11-26）

> 反馈场景：家园页 →「我的蛋仓」，时不时先弹「小组数据已变化，请重试」，紧接着「蛋仓同步失败」。
>
> 第一轮是**只读诊断**（没改 `src/`）；修复与复核见下方「修后复核」（提交 `35ead2f` / `aea3613`）。诊断脚本都在 `tmp-diag/`，跑法见 §4。

## 0. 结论先行

**这两条提示是同一个 409 的两个展示位，不是两个问题**（本次实测走的就是这条路径）。
一次 `POST …/egg-matching`（`action.type = 'stock-sync'`）被服务端以 `REVISION_CONFLICT` 打回，`useEggMatching.mutate` 的 `catch` 里 `setError(message)` 渲染成玫红横幅（`api.error`），`useEggStockSync` 的 `catch` 又从同一个异常里 `setSyncError(message)` 渲染成琥珀横幅（`src/ui/plan/EggStockView.tsx:129-140`；组内广场的蛋仓是 `EggMatchingHub.tsx:271-272`）。所以「先一条、后一条」是**一次失败的两处回显**。

**根因：蛋仓同步被绑在「整组共享」的乐观锁 `version` 上，而写这个 version 的通道远不止当前页面。**
`stock-sync` 本来就是「按账号 + 游戏角色合并自己那份库存」的幂等写入（`src/shared/eggWorkflow.ts:245-327` 只动自己的 `eggs` 与水印），但服务端要求 `body.baseVersion === 当前 version`（`functions/_lib/eggMatching.ts:98`），而这个 version 是**组级**的：组里任何人发需求 / 接单 / 挂出、机器人 ingest（`functions/_lib/eggPatrolStock.ts:64`）、巡查 tick（同文件 `:27` 与 `functions/_lib/eggPatrol.ts:181`）都会 `version+1`。页面推蛋时用的是自己手里的 version，冷启动还可能直接吃 60 秒内的本地缓存不做校验（`src/ui/plan/useEggMatching.ts:152`），只要这期间**任意一次外部写**发生，就 409。**实测：组员 B 发一条需求，A 的 stock-sync 就 409（§1.1 场景 2b）。**

**放大器：服务端对「空操作」也 +1。** 同一次采集重发，`state_json` 逐字节完全相同，version 仍然从 1 涨到 2（§1.1 场景 1）。空转写会继续作废其它通道手里的版本。（**已修复**，见下方「修后复核」R2）

**为什么是「反复」而不是「一次」：** 409 之后客户端**不会自动重推**同一次采集（`attemptedCaptures` 只在人工 `retrySync` 时清空，`src/ui/plan/useEggStockSync.ts:74-77/105-109`，实测 1 次后停手），横幅是**粘住**的；用户点「重试同步」或换一次采集再推，只要又撞上外部写就再弹一次。单通道、没人写的时候是能连续成功的（§1.2 场景 3，baseVersion `[5,6]` 都 200）。（**已修复**，见下方「修后复核」R3）

**建议（修前结论）：** 首选 R1——把 `stock-sync` 改成「读最新 → 合并 → CAS 重试」的免 baseVersion 写入，照抄现成的 `recordIngestedHomeEggs`（`functions/_lib/eggPatrolStock.ts:74-87`，4 次重试）；并让空操作不 +1。详见 §5。**（R1–R4 已落地：`35ead2f`，实测见「修后复核」）**

## 2. 链路逐条核对（代码 + 行号）

### 2.1 请求是谁发的、`baseVersion` 从哪来

| 环节 | 位置 | 说明 |
|---|---|---|
| 触发 | `src/ui/plan/useEggStockSync.ts:63-102` | 遍历本机快照，背包蛋 / 家园蛋的 `capturedAt` 比 `partTimes` 新才推；每次推送前把 `attempt` 记进 `attemptedCaptures`（`:74-77`） |
| 发请求 | `:84-89` → `api.mutate` → `src/api/eggMatching.ts:50-55` | body = `{ baseVersion, action }` |
| baseVersion | `src/ui/plan/useEggMatching.ts:163` | 就是 `current.current.version` |
| 何时更新 | `useEggMatching.ts:128`（GET 成功）、`:166`（POST 成功）、`:171-173`（409 补拉） | 只有这三处 |
| 可能不带最新版本 | `useEggMatching.ts:145-152` | 挂载时若 localStorage 缓存 <60 秒，**直接不发 GET**，先拿旧版本；轮询 20s 一次（`:153`），且只在页面可见时跑 |

所以「窗口」是：**上一次成功 GET / 写 → 本次 POST** 之间，最长约 20 秒（页面在前台）或最多 60 秒（冷启动吃缓存 + 首次轮询前）。这期间任何外部写都会让本次 POST 409。

### 2.2 409 之后发生什么

- 服务端：`functions/_lib/eggMatching.ts:98` → `failCode(origin, 409, 'REVISION_CONFLICT', '小组数据已变化，请刷新后重试')`。
- 客户端 `mutate` 的 `catch`（`useEggMatching.ts:167-176`）：先 `setError(message)`（这条会渲染成玫红横幅），再 `if status===409 → await getEggMatching()` 补拉并覆盖 `current`，然后 **`throw` 出去**。
- `useEggStockSync` 的 `.catch`（`:96`）把同一个 message 写进 `syncError`（琥珀横幅），`.finally` 里 `setSyncRetry(n+1)` 触发 effect 重跑；但 `attemptedCaptures` 还留着这一条，重跑会 `continue` 跳过 —— 这就是「只尝试一次」的实现（实测见 §1.2 场景 4）。
- 服务端还有第二个 409 出口：`:154`「小组数据已变化或成员权限失效，请刷新」，来自 CAS `UPDATE … WHERE version=?` 落空（读和写之间又被写了一次）。文案与用户复述的不同，但同属 409。

### 2.3 服务端 version 语义：无条件 +1

`functions/_lib/eggMatching.ts:106-123`：

```ts
const next = applyEggAction(current.state, groupId, accountId, body.action, now);
...
const version = current.version + 1;          // <- 不判断 next 是否真的变了
...
UPDATE egg_matching_groups SET state_json=?,version=?,mutation_id=?,updated_at=?
WHERE group_id=? AND version=? AND EXISTS(…成员校验…)
```

`applyEggAction` 的 `stock-sync` 分支在「两侧水印都没推进」时 `return previous`（`src/shared/eggWorkflow.ts:268`，返回**同一个对象**），这层「没变化」的信息到了 handler 就丢了。对比后台两条同类写入都做了判断：`recordIngestedHomeEggs` 在 `merged.state === state` 时直接返回不写（`functions/_lib/eggPatrolStock.ts:80`），`recordProducedPatrolEggs` 在 `!changed` 时返回（`:48`）。

**结论：每次被接受的 `stock-sync` 都会 +1，哪怕一个字节都没改（修前）。** 这既放大了冲突面，也让「重试成功」本身消耗掉别的通道手里的版本。（**已修复**：`next === current.state` 时直接返回当前 version，见「修后复核」R2）

### 2.4 `autoListStock` / 绿窝回填 / `claimPending` 会不会「每次同步都写」

**不会每次写，但第一次必写，而且写完仍然是「客户端不知道」。**

- `autoListStock`（`src/shared/eggWorkflow.ts:159-172`）：只把「背包 + 五项齐全 + 未挂出 + 未手动下架 + 可流通」的蛋从 `false → true`，永不回退；服务端合并时 `egg.listed = before.listed && canCirculateEgg(egg)`（`:303`）也会保住已挂出状态。所以它只会在**第一次**产生一次真实变化。
- 绿窝回填（`:306-310`）：只补 `greenNest === undefined` 且有学院亲本的行，补一次即稳定。
- `claimPending`：客户端 `reconcileEggStock` 判定后随库存上送，`normalizeEgg` 只认显式 `true`（`src/shared/eggWorkflow.ts:125`），同样一次性。
- 但**客户端的 `stockRef` 是「提交前」算出来的**（`useEggStockSync.ts:78-89`），服务端在合并里补的 `listed=true` / 绿窝 / 状态继承，下一次推送时客户端还是按旧值发；服务端每次都用 `before.*` 兜住，所以**不会抖动**，代价是每次都要重新算一遍。

实测佐证：同一次采集重发后 `state_json` 逐字节相同（§1.1 场景 1）——说明这几个特性**没有**在每次同步里制造新变化。

### 2.5 `9397d90` 的错误提示链路（是不是这次的原因）

- 抛出点：`src/ui/plan/eggStockModel.ts:86-88`，`gameAccountKey` 空串/纯空白 → `throw new Error('库存快照缺少游戏账号标识（gameAccountKey）')`。
- 显示点：`useEggStockSync.ts:99-101` 的 `catch` → `syncError` → 琥珀横幅「蛋仓同步失败：库存快照缺少游戏账号标识（gameAccountKey）」。
- 生产调用方只有一处（`useEggStockSync.ts:78`），key 来自 `inventoryFromSnapshot` → `accountKeyOf(snapshot)`；`accountKeyOf` 返回 `uid:<数字>` 或 `name:<账号名>`，**永远非空**（`src/domain/parseBackup.ts:73-74`）。`EggStockSnapshot.gameAccountKey` 已经是必填类型。
- 结论：**这次不是它**。用户看到的是 409 文案（「小组数据已变化…」），不是 key 文案。但这条链路本身有个真问题：`useEggStockSync` 的 `catch` 把所有异常（含 409、含本地合并异常、含「数据正在更新」）都压成同一句「蛋仓同步失败：<message>」，所以**光看横幅没法区分「版本冲突」和「本地数据异常」**——这也是本次排障要多跑探针的原因。（**已修复**：远程失败按 版本冲突 / 同步繁忙 分类，本地异常单独标「本地合并异常：」，见「修后复核」R4）

## 5. 建议修法（等你拍板，本轮没动）

> **2026-11-26 01:55 回填：R1–R4 已全部落地，提交 `35ead2f`，实测与用例见上方「修后复核」。**
> 下面保留当时的方案原文，方便回看为什么这么修。

### R1（推荐）`stock-sync` 改「合并式写入」，不再要求组级 `baseVersion`

- 做法：服务端对 `action.type === 'stock-sync'` 走一条「读最新 → `applyEggAction` → CAS 写回，冲突重读最多 4 次」的路径，和 `recordIngestedHomeEggs`（`functions/_lib/eggPatrolStock.ts:74-87`）完全同构；客户端这条 action 不再带 / 不再校验 `baseVersion`，服务端在响应里返回新 version 让客户端接管。
- 为什么安全：`stock-sync` 分支只动「本 actor + 本 `gameAccountKey`」的 `eggs` 与水印（`src/shared/eggWorkflow.ts:254,316-325`），不读不写 trades / demands / lines，天然可合并；水印保证幂等。
- 代价：服务端多一条分支 + 单测；客户端 `mutate` 需要区分「stock-sync 不带版本」。**收益最大：组内任何人的换蛋操作、机器人 ingest、另一个标签页都不会再让蛋仓推不上去。**

### R2 「空操作不 +1」+ 409 响应带回当前 version

- `const changed = next !== current.state;` → 不改就不写、不 +1、直接返回当前 version（顺带省一次 D1 写）。
- 409 响应体带上 `{ version: current.version }`，客户端 409 分支直接用，省掉一次 GET（现在是 409 后必发一个 GET，`useEggMatching.ts:171`）。
- 代价极小，但单独做**不能**消除冲突，只是降低放大倍数。建议和 R1 一起做。

### R3 客户端：写前确认版本 + 409 自动重试一次

- `useEggStockSync` 推之前若 `Date.now() - 上次 GET 时间 > 10s` 就先 `refresh()`，或让 `mutate` 内部在写前强制 GET 一次（代价：每次推蛋多一个请求）。
- 409 时只对**这一条**采集做一次自动重试（失败再落横幅）：把 `attemptedCaptures` 的该 key 放开一次，而不是等用户点。
- 代价：会在弱网下多一次往返；收益是用户不再需要手点「重试同步」。**属于体验补丁，不能替代 R1。**

### R4 提示收敛（顺手）

- 同一个 409 现在渲染两条横幅（玫红 + 琥珀），建议合成一条：「蛋仓同步遇到版本冲突，已自动换成最新版本，正在重试」；
- 区分文案：版本冲突 / 本地合并异常 / 「数据正在更新，请稍后重试」（`useEggMatching.ts:159` 抛的这条也会显示成「蛋仓同步失败」）。

### 不建议

- **不要**按 `gameAccountKey` 拆版本号或给客户端本地计数——服务端仍是唯一真相，拆版本会把「同组一致」的语义搞乱，收益还不如 R1。
- **不要**靠前端串行 / 加锁解决——跨设备、机器人 ingest 都不在那个锁里。
