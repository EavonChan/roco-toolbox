# 会话分工与巡检机制（2026-11-22）

> 用途：把「谁在哪个会话干什么、能改哪些文件」写死，避免多个会话抢同一批文件。
> 这是一份**分工契约**，不是路线图；路线图见 `docs/开发规划-里程碑.md`。
> 背景事实来自 `docs/交接-2026-11-22-fork功能对比.md`（18 个冲突文件、3 组重复补丁、32/8 提交差）。

## 1. 依赖与流转

```
P（口径 / 原型 / 截图）
   │  确认后
   ▼
S1（领域接口先冻结）──► S2 / S3（并行）      S4 / S5（独立，随时）
   │                        │
   └────────┬───────────────┘
            ▼
        R（只读审查，出报告）
            │  发现清单
            ▼
      S*（修复轮，限范围）
            │
            ▼
        S6（收尾验证 + 发版）

A：全程旁路，只看不做；PR 预检、日报、风险预警
```

规则：

- **UI 类改动没有 P 的确认不开工**（截图或可交互 HTML，375 / 390 都要）。
- **S2 / S3 开工前，S1 必须先冻结涉及的领域接口**；接口要改，回 S1 改，不在 UI 会话里顺手改 domain。
- **R 不修代码**，只出清单；修复一律回原工作区，避免审查会话变成第二个实现会话。

## 4. 朋友 PR 通道

**结论：维持 fork + PR，不给 `test` / `main` 的直接 push 权限。**

理由（均有据可查）：

1. 他的分支落后 32 个提交仍在开发，有写权限时一次"推上去对齐"就可能把旧实现顶到 `test`。
2. 3 组重复补丁（同 patch-id 重放）说明他习惯跨分支 cherry-pick，有写权限更容易变成 force-push 覆盖。
3. 他重写了 `MotherView`（-370 行、删收集中心入口）；PR 能挡，直推只能事后回滚。
4. 4 个 add/add 冲突说明双方在同一位点各做一套，这是边界问题，权限解决不了。
5. `main` 是正式站，给写权限等于把发版闸门交出去。

**GitHub 分支保护（`test`）**：

- Require a pull request before merging（至少 1 个 review）。
- Require status checks：`verify`（`tsc -b && vitest run && lint-copy`）。
- Do not allow force pushes / Do not allow deletions。
- 可选：Require linear history。

**PR 协议**：

| 项 | 要求 |
| --- | --- |
| 分支 | `friend/<功能>-<日期>`，从 `origin/test` 开 |
| 寿命 | ≤ 7 天，每天 rebase；不许 rebase 已推送历史 |
| 粒度 | 一个 PR 一个目的，≤ 8 个文件 / ≤ 400 行 |
| 验证 | 附 `npm run verify` 真实输出 |
| UI | 附 375 / 390 截图或可交互 HTML |
| 禁区 | 不碰 §3 里非自己名下的文件 |

**合并节奏**：固定每周两次窗口，只在 PR 绿的时候开。

**A 的 PR 预检（机械可复跑，6 项）**：

```powershell
git fetch origin; git fetch eavon
git rev-list --left-right --count test...<pr-branch>          # 落后多少个提交
git merge-tree --write-tree --name-only test <pr-branch>       # 冲突预演
git log -p --no-merges test..<pr-branch> | git patch-id --stable  # 重复补丁查重
npm run verify                                                # 验证复跑
git diff --stat test...<pr-branch>                            # 规模与越界文件
```

## 5. 巡检（手动触发）

不定时；你说"巡检"或给出会话 ID 时执行。输出固定四段：

1. **各会话推进了什么**（按会话标题归类，取最后若干条结论）
2. **卡点**（等确认、等测试、等合并）
3. **仓库风险**（脏工作区、分支漂移、待处理 PR）
4. **建议下一步**（不超过 3 条）

做不到的：实时监听（会话文件是压缩落盘，只能事后读）、替代你拍板产品问题。

## 6. 开动前先做的三件事

1. **处置 104 项脏工作区**：8 个源码改动（`MotherView.tsx`、`plan/*` 等）先提交或 stash 到独立分支；截图与原型类 untracked 归到 `docs/preview/` 或加 `.gitignore`。脏树不清理，所有合并预演都失真。
2. **给 `test` 建分支保护**（按 §4 的设置）。
3. **建 PR 模板** `.github/PULL_REQUEST_TEMPLATE.md`（改动目的 / 涉及口径 / 验证输出 / 截图 / 越界说明）。
