# 协作与合并规则（2026-11-22 起）

面向参与本仓库的协作者（friend/\*）与主线维护者。规则只有两种状态：**已由工具挡住**，或
**靠人守**。下表是本文的骨架，后文逐条给出可执行的命令与落点。

| 规则 | 靠什么挡 | 现状 |
| --- | --- | --- |
| 分支命名 / 来源 / 存活 / rebase | 人 + 每周巡检 | 靠人 |
| 粒度 ≤ 8 文件 / ≤ 400 行 | CI `pr-size` | 本 PR 引入 |
| 文件所有权 | `.github/CODEOWNERS` + 提 issue | 本 PR 引入 |
| 准入（verify 输出 / 375、390 截图） | PR 模板 + 评审 | 本 PR 引入 |
| test 分支保护 | GitHub 分支保护规则 | 需主线在设置里开 |
| 合并窗口 | 人（固定时间） | 靠人 |

---

## 1. 分支

- 命名：`friend/<功能>-<YYYYMMDD>`，例 `friend/egg-share-20261122`。不要用 `fix`、`update` 这类无信息词。
- 一律从 `origin/test` 开，先拉到最新：

  ```bash
  git fetch origin
  git switch -c friend/<功能>-<日期> origin/test
  git branch --unset-upstream   # 防止手滑 git push 直接推到 test
  ```

- **存活 ≤ 7 天**，从首个提交算。第 7 天还没合，就关掉分支、重开一个干净的；不续命、不挂起。
- **每天 rebase 一次**：

  ```bash
  git fetch origin && git rebase origin/test
  ```

- **不许 rebase 已推送的历史**。已经 `git push` 过的分支，只能 `git merge origin/test` 前进；
  确实要清理历史就新开一个分支重来。`--force` / `--force-with-lease` 一律不许用在共享分支上。

## 2. 粒度

- 一个 PR 只做一个目的；标题写目的（"换蛋：分享链接带上目标性格"），不要写文件名。
- 上限 **≤ 8 个文件、≤ 400 行**（口径：`git diff --numstat origin/test...HEAD`，不计
  `package-lock.json`、`*.snap`、图片）。超出由 CI `pr-size` 直接失败。
- 超了先拆成串行 PR（A 合了再开 B），不要在一个 PR 里堆"顺手一起改"。

## 3. 文件所有权：仅主线改

以下路径**只有主线维护者（@sasaki-ishiran）能改**：

- `src/ui/MotherView.tsx`
- `src/ui/Dashboard.tsx`
- `src/ui/plan/*`
- `release/*`
- `scripts/deploy*`
- `.github/**`

协作者确实需要改这些文件时：

1. 先在本仓库开 issue，写清目的、影响面、打算怎么改；
2. 拿到主线明确同意后再开 PR，PR 描述里贴 issue 链接；
3. 主线也可以在合并窗口内替你改，你只提需求。

理由：这几处是发版通道、主界面骨架和 CI 本身，被并发改动时出问题的代价远大于收益。

## 4. 准入：PR 必须带的材料

- **`npm run verify` 的真实输出**：贴命令和尾部输出（通过 / 失败都贴），不要写"本地已通过"。
  `verify` = `tsc -b && vitest run`。
- **UI 变更**：附 375 与 390 两张截图，标出改动点；只改逻辑不用截图，但要在描述里说明"无视觉变化"。
- **说明四件事**：改了什么、为什么、怎么验证、回滚风险。

## 5. 分支保护（比"给不给权限"更根本）

`test` 分支的规则（GitHub → Settings → Branches）：

- Require a pull request before merging（≥ 1 个审批）；
- Require status checks to pass：`verify`；
- Do not allow force pushes；
- Do not allow deletions；
- Require conversation resolution before merging。

这样即使哪天临时给了某人 admin 权限，也仍有检查和评审在挡着——权限能绕过规则，但绕不过
"必须有人点 Approve"。

命令行等价配置（需要有 admin 的 token）：

```bash
gh api -X PUT repos/sasaki-ishiran/roco-toolbox/branches/test/protection \
  -f required_status_checks[strict]=true \
  -f 'required_status_checks[contexts][]=verify' \
  -f enforce_admins=true \
  -f required_pull_request_reviews[required_approving_review_count]=1 \
  -f required_conversation_resolution=true \
  -F allow_force_pushes=false -F allow_deletions=false
```

注意 `enforce_admins=true`：不开这一项，admin 自己仍可强推，保护等于只挡协作者。

## 6. 合并窗口

- 固定每周 **两次**（建议周二、周五晚 20:00–22:00，按团队时间定死写进群里公告）。
- 只在 PR **绿**的时候开窗口：verify 通过 + 已审 + 无冲突 + 在粒度上限内。有一项不绿就不合。
- 窗口外合并要提前在群里说一声；合并后当天不再往 test 追加无关联改动，避免窗口内的验收被冲掉。

## 7. 发版与本文的关系

发版、转正、回滚仍以 `docs/发版与更新规范.md` 为唯一口径；本文只管"代码怎么进 test"。
`release/*` 与 `scripts/deploy*` 属主线所有，协作者不要碰。
