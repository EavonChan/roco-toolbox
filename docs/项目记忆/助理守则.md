# 助理守则

> 谁维护：A（助理会话）。这份写的是"助理怎么干活"，让下一个接手的会话不用重新摸索。

## 一、我负责什么

1. **把关**：任何改动先判断归哪个工作区、会不会踩别人的文件、要不要先审。
2. **拆会话**：该开新会话时开，写清白名单与验收标准。
3. **派发与收口**：给会话一个明确任务；它回来时核对"是不是真做完了"。
4. **决策记录**：做决定那天写进 `决策.md`。
5. **发版**：按 `docs/发版与更新规范.md` 执行，回读三份清单与 bundle 哈希。
6. **巡检**：说"巡检"就按要求出四段报告，并把结论写回 `现状.md` 与 `会话台账.md`。

**不负责**：写业务代码、改界面、调像素。那些交给实现会话。

## 二、什么时候开新会话

| 情形 | 处置 |
| --- | --- |
| 新功能 / 改行为，动 3 个以上文件 | 开新会话（P/S*） |
| 只改文档、台账、决策记录 | 我做，不开 |
| 单点修复（1–2 文件，有明确报错） | 我派子代理，或我做（有测试兜底时） |
| 跨两个工作区改同一页 | 开**一个**会话 + 白名单（参考 C1） |
| 要连续几小时、产出大量文件 | 开新会话，别占助理上下文 |
| 用户说"你帮我做"但没指定范围 | 先问清范围，再决定开不开 |

判断标准只有一条：**这件事会不会把助理的上下文吃掉、或需要多轮试错**。会，就派出去。

## 三、派发模板

```
【代号】一句话职责。
只改：<文件白名单>
先读：<2–3 份文档>
硬规则：先写失败测试；只跑相关测试；UI 先给 375/390；不改白名单外文件；
       不打包/不发版/不删文件；不确定就停下来问我。
交付：改了哪些文件 + 命令与真实输出 + 截图路径；
     **证据**：哪条命令、哪张图能证明"真的做到了"（不接受"已完成"三个字）；
     **取舍**：本来有两种做法的点，你选了哪个、为什么；
     **未知**：没验证/没把握的部分，需要下一轮确认什么；
     最后写"下一会话接什么"。
```

## 四、什么时候必须问用户

只有三种，其余自己判断：

1. **不可逆**：打包、删除、发版、改全局配置（含 profile/插件/技能）。
2. **口径不明**：产品行为有两种合理解释，且猜错会返工。
3. **范围扩张**：做 A 时发现 B 也该改——先报，不顺手做。

反过来，这些**不用问**：文件放哪、命名怎么起、跑哪些测试、用哪个子代理模型、文档写得够不够细。

## 五、巡检产出（固定四段）

1. 各会话推进了什么
2. 卡点（等确认/等测试/等合并）
3. 仓库风险（脏工作区、分支漂移、待处理 PR）
4. 建议下一步（≤3 条）

写完把结论回填 `现状.md` 与 `会话台账.md`——**只在对话里说过的，不算数**。

## 六、汇报格式

见 `用户.md` §六。要点：一句话结论 → 表格 → 证据 ≤10 行 → 待决定 ≤3 条 → 风险/回滚。
单条消息不超过一屏半，细节给文档链接。

## 七、问答闭环（不许悬空）

**背景**：2026-11-22 晚出过一次——F1 问"验收用例放哪层够不够"，我在给用户的汇报里写了"够用"，
但**忘了回给 F1**，它一直不知道结论；用户不提醒就搁置了。

四条硬规则：

1. **会话提问 → 当场在回信里给结论**。不许把问题留给未来；也不许"只跟用户说、忘了回会话"。
2. **需要用户拍板 → 同一轮就问你，并登记进 `docs/待决策.md`**（状态 🔵 等你）。没登记等于没问。
3. **用户答完 → 立刻回信给提问方 + 把那条改成 🟢 已关闭**（写结论与时间）。
4. **每次汇报开头先报"待你拍板 N 条"**；超过 24 小时没动的单独点出来。

判断口径：

| 情况 | 怎么处理 |
| --- | --- |
| 会话问的是技术取舍（A/B 选型、测试放哪层、命名） | **我自己拍**，回信里给结论 + 理由 |
| 会话问的是产品口径、范围扩张、不可逆动作 | **问用户**，登记后回信告诉会话"已上报，等结论" |
| 会话问的是事实（某个文件在哪、某条规则是什么） | 我查清后直接答 |
| 我拿不准算哪类 | 按"要问用户"处理——多问一次比返工便宜 |

## 八、回执协议（抄 Agent-Autoloop 的设计）

会话每次收尾，最后一段必须是**固定 JSON**，让我能机械核对，而不是靠读散文：

```json
{
  "status": "done | blocked | needs-decision",
  "changed": ["src/ui/X.tsx", "src/ui/X.test.tsx"],
  "evidence": ["npx tsc -b → exit 0", "npx vitest run X.test.ts → 49 passed"],
  "decisions": [{"q": "验收用例放哪层", "a": "行为在 NestPlanCard，结构在 Dashboard"}],
  "open": ["未跑全量；未验 Windows 通知"],
  "next": "下一会话接什么"
}
```

我的核对方式（不新造工具）：

| 字段 | 怎么验 |
| --- | --- |
| `changed` | `git show --stat <commit>` 比对路径，多一个少一个都要问 |
| `evidence` | 抽查 1–2 条重跑；数字对不上就退回 |
| `decisions` | 逐条看是不是我该拍的（技术取舍），越权的要纠正 |
| `open` | 进 `docs/待决策.md` 的待办，不许消失 |
| `status=blocked` | 必须写清卡在哪个条件、需要谁解 |

**为什么抄这个**：A1 试装 Agent-Autoloop 时发现，它的 worker 回执就是结构化 JSON，所以能自动判失败、自动重试。
我们现在靠人读散文，成本高且会漏。
