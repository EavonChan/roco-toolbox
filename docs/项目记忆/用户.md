# 用户画像

> 谁维护：A（助理会话）。观察到了就补，不猜、不带评价，只记录"怎么做对你更省事"。
> 用法：每次新会话开工读一遍；写汇报、定流程、判断"该不该问"时对照。

## 一、怎么沟通

- **中文简体**，口语，句子短。不喜欢客套和铺垫。
- 喜欢**结论先行**：先给结果/判断，再给依据；不要先讲过程。
- 接受**表格**，但不要为了排版把一句话拆成五行。
- 反感"工程化说法"代替产品描述（"改了哪个函数"不如"用户能看到什么"）。
- 会**直接推翻**结论（"106→104 可以"），这种一句话就是决定，不要再确认。

## 二、怎么决策

- 会**先问"要不要"再问"怎么做"**；如果方案有明显更优解，直说并给理由。
- **不喜欢被问太多选择题**——一次最多 3 个，每个都要有推荐项。
- 拿不准时会说"我也不太确定，你试试看"——这时可以自己判断，但要先把证据摆出来。
- 对**时间成本**敏感：上班族，白天只能碎片回复，晚上才推进。

## 三、雷区（说一次就够）

| 雷区 | 具体 |
| --- | --- |
| **未经授权打包/发版/删除** | 四类动作必须先问：打包、删除或覆盖、部署发版、新增/改版界面 |
| **先改完再问** | 不接受"按我的理解改完再让你看" |
| **用文字代替截图** | UI 改动必须给 375/390 截图或可交互 HTML |
| **自作主张扩大范围** | 授权了 A 就只做 A，不许"顺手"做 B |
| **提交前不验证** | 说"完成"必须附命令与真实输出 |
| **同一件事反复问** | 已经说过的偏好不要再确认 |

## 四、节奏

- **晚上是主战场**（20:00–24:00 最常见），白天多是"看一眼/点一下"。
- 周末与工作日区分不明显，但**不要假设他随时在线**。
- 长任务要能"停得住"：做到一半停下来给结论，比一口气做到底更受欢迎。

## 五、验收方式

- **看图**：375 / 390 截图、并排对比、标出改动点。
- **看结果**：线上地址点开能不能用；APK 装上能不能跑。
- 不看的：单元测试明细、构建日志（除非失败）。
- 所以汇报里"验证"一栏只要**结论 + 一个可点的东西**。

## 六、汇报格式（照这个来）

```
一句话结论
做了什么（表格，最多 5 行）
证据（命令 + 关键输出，最多 10 行）
需要你决定/做的（最多 3 条，标推荐）
风险或回滚方式（有才写）
```

- 单条消息**别超过一屏半**；细节放文档，给链接。
- 数字必须带来源（命令/接口），不手抄。

## 七、需要被提醒的地方

- 容易**同时开太多会话**，需要提醒"现在有 5 个在跑，先收一个"。
- 有时**给的目标很大**（"全面整改"），需要先拆成 3 步再确认。
- 对**过期文档**没有警觉，引用前需要我先核一遍数字。
- 遇到"朋友那边"的事，倾向**先沟通再定规则**——规则写进文档，别只在对话里说。
