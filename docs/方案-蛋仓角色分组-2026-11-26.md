## 1. 三个方案细节

### 1.1 方案 1：下拉筛选（现状增强）

- 标题行：`‹ 返回  我的蛋仓  [阿甲（5）▾]`；下拉选项带蛋数，**没有「全部角色」**（2026-11-24 口径）。
- 下面仍是搜索 + 条件（全部/已标注/未标注/自产/不可交换）+ 4 列蛋卡。
- 已在 `e852b99` 落了一半：`useEggStockCharacter` + 面板三个 props；差广场那 20 行接线（等三方合流）。
- **适合**：一个人只关心当前在玩的号；列表永远只有一屏但只有一屏。
- **不适合**：「我到底有几个号在挂蛋」「小号还有没有货」——必须来回切。

### 1.2 方案 2：分组

- 每个角色一段，段头 `阿甲` + `5 颗` + 第一段带「主号」标；段内 4 列蛋卡。
- 0 蛋角色不展开网格，只占一行：`阿丙 0 颗` / `这个角色还没有蛋`（`64830cd` 那句仍然有用）。
- 搜索仍在最上面（全局），条件也在最上面，**先过滤再分段**。
- **优点**：一屏看清所有角色；不用切；主号一眼可见；蛋仓天然就是「我的哪几个号、各有多少」。
- **代价**：比方案 1 长——8 颗蛋 + 3 个角色时约多 2 行；蛋多时页面明显变长（见 §2）。

### 1.3 方案 3：分组 + 角色芯片

- 默认 = 方案 2；顶部多一行芯片：`全部（8）` `阿甲（5）` `阿乙（3）` `阿丙（0）`。
- 点某个角色 → 只留那一段（段头保留，因为它还带「主号」标和蛋数）；点「全部」回到分组。
- **和方案 1 的区别**：芯片是「收敛」不是「唯一视角」，默认仍是全部分组。
- **代价**：顶部多一行、芯片和段头信息重复（可接受：一个是导航、一个是锚点）。

### 1.4 选哪个

| | 方案 1 | 方案 2 | 方案 3 |
| --- | --- | --- | --- |
| 一眼看到所有角色 | ✗ | ✓ | ✓ |
| 角色多时快速收敛 | ✓（下拉） | ✗ | ✓（芯片） |
| 顶部高度 | 最省 | 中 | 最费（+28px） |
| 改动量（在已落 hook 基础上） | 最小（20 行） | 中（~80 行 + 段组件） | 中偏大（~120 行，含芯片状态） |
| 与「同类蛋聚合」叠加 | 不冲突 | 天然两层 | 天然两层 |

**推荐 3**；如果用户嫌顶部多一行 → 选 2（段头点一下也能收起，见 §2）。

## 2. 长列表滚动体验

- **页数估**：一页最多 3~5 个角色；每个角色蛋卡数受 U5 聚合影响（同物种合成一张 ×N），8 颗蛋在方案 2 里是 3+3 张卡。
- **段头吸顶（sticky）**：蛋多时有用，但顶栏本身是 sticky 且高度会变（同步失败横幅会让它变高），`top` 只能写死一个近似值，容易错位。**建议先不做**，等真的出现「一屏 3 段以上、每段 10 颗」再加。
- **段头可点收起**：成本低（`<details>` 语义），蛋多时立刻有用；和「0 蛋角色」那行共用同一套收起/展开交互。
- **不引入虚拟列表**：聚合已经把卡片数降一个量级；真要上百颗再说。
- **搜索**：保持在所有段之上，结果仍按段显示（跨角色命中不会合并成一段）。

## 3. 横屏怎么办

- 现状（家园 / 广场一致）：横屏用 `EggStockPanel` 的 `.egg-stock-layout` —— 蛋卡在左、筛选列在右（可收起）、最右一条纵向标题栏「返回 / 我的蛋仓 / 收起筛选」。下拉在横屏进筛选列（`EggStockPanel.tsx:216` 的 `characterBlock`）。
- **方案 1 横屏**：不动（下拉在筛选列里，和现在家园一样）。
- **方案 2 / 3 横屏**，两种做法：
  - **a（推荐）**：段头仍排在主区、纵向排（横屏视野宽，段内自动 6~8 列）。实现上只是「主区从一格网格变成若干段」，`egg-stock-layout` 的 grid 不变。
  - **b**：右栏加「角色锚点」（阿甲 / 阿乙，点击滚到该段）。右栏现在已经有「返回 / 标题 / 收起筛选」三件，再加锚点会挤，且与「收起筛选」互斥逻辑要重排 → 留作后续增强。
- 芯片（方案 3）横屏放哪：**放主区顶部**（和竖屏一致），不塞进右栏——右栏是「筛选条件」，芯片是「角色导航」，混在一起会跟下拉打架。

## 5. 需求按角色过滤：技术评估（**先别做**）

> 复核地点：`src/shared/eggMatching.ts:7-19`（`EggDemand`）、`functions/schema.sql:300-306`（`egg_matching_groups.state_json`）、`functions/_lib/eggMatching.ts:15-17`（整块 JSON 读写）。

### 5.1 要改什么

1. **数据结构**：`EggDemand` 加一个**可选** `gameAccountKey?: string`（口径同蛋上的 `uid:<游戏 UID>`）。
2. **校验/落库**：`createDemand` 构造返回值时把该字段带上（现在是显式白名单，不加就被丢掉）；`applyEggAction` 的 `publish` / `edit` 透传；非法值拒绝。
3. **前端**：发布需求时选角色（默认主号）；「我的收集」需求卡标角色；蛋仓切角色时需求列表跟着筛（如果要）。
4. **不要动的地方**：`canMatchDemand`（只看物种/性格/体型/声音）、成交与换蛋状态机。

**关键结论：不需要 D1 迁移。** 蛋仓的整份工作流状态是 `egg_matching_groups.state_json` 里的一个 JSON（`functions/_lib/eggMatching.ts:15-17` 整块读写），需求就是 `state.demands[]` 的一项。加字段 = JSON 多一个 key，不需要 `ALTER TABLE`，也不需要接口版本号。

### 5.2 改了会怎样

- **老数据**（没有这个字段）：按**账号级**处理——展示为「全部角色」或不显示角色标签，**不能默认归到主号**，否则老需求会突然从别的角色视角消失。
- **老客户端**（发布时不带字段）：落成账号级，行为与现在完全一样。
- **别人的需求单**：可见性不变（组内可见），只是多一个角色标签；撮合不受影响。
- **会变的只有**：自己「我的收集」里需求卡的归属展示、以及蛋仓切角色时需求列表要不要跟着筛。
- **要先定的口径**：同一账号两个角色能不能各发一条同物种需求？（现在 `createDemand` 没有去重，加了角色就会变成两条合法的需求）

### 5.3 工作量

| 只标角色（不做筛选） | 类型 + 白名单 + 发布时选角色 + 需求卡标签 + 测试 | **约 0.5 人日** |
| 标角色 + 蛋仓按角色筛需求 | 上面 + 蛋仓/我的收集的筛选联动 + 兼容测试 | **约 1~1.5 人日** |

## 6. 朋友的「名字自适应」（`fitName`）：**有，而且曾经是能用的**

> 用户问「好像朋友做了自适应」——**是**。而且代码就在我们仓库的提交历史里，是我们自己后来把默认值改死、让它空转的。

### 6.1 朋友的原实现（`eavon/friend/20261119`，提交 `56f23cd`，2026-11-20）

```tsx
// src/ui/PetCardLayout.tsx（朋友版）
const fit = () => {
  const base = fitNameBase ?? 12;              // 基准 12px
  text.style.fontSize = `${base}px`;
  text.style.maxWidth = 'none';
  text.style.width = 'max-content';
  text.style.flexShrink = '0';
  const width = text.getBoundingClientRect().width;   // 实测自然宽度
  text.style.width = ''; text.style.flexShrink = ''; text.style.maxWidth = '';
  const available = heading.clientWidth;
  if (width > 0 && available > 0 && width > available) {
    const scaled = Math.max(
      fitNameMin ?? 9,                            // 最小 9px
      Math.floor(((base * available) / width) * 2) / 2,   // 按比例缩，0.5px 一档
    );
    text.style.fontSize = `${scaled}px`;
  }
};
fit();
const observer = new ResizeObserver(fit); observer.observe(heading);
```

首版在 `0050dca`（2026-11-19），参数化在 `56f23cd`；当时调用方还各自传了值（`fitNameBase={10} fitNameMin={8}`、`{9}/{8}`、`{8}`）。

### 6.2 我们怎么把它弄没的

`466351b`（2026-11-20，「卡片收敛成一种几何——104 高 / 头像 48 / 名字 10px」）：

```
-      const base = fitNameBase ?? 12;     →  +  const base = fitNameBase ?? 10;
-          fitNameMin ?? 9,                →  +  fitNameMin ?? 10,
-        fitNameBase={10} fitNameMin={8}   （4 处调用方参数一起删掉）
```

于是 `base = min = 10`，`Math.max(10, …)` 永远 ≥ 10、且本来就是 10 → **恒等于 10，从此不再缩字号**（P1 的观察正确）。

`831f292`（2026-11-25 性能改造）把它搬进 `src/ui/fitCardName.ts` 批量处理（`flushCardNameFit`、共享 ResizeObserver、canvas 量宽度），但保留了 `base: fitNameBase ?? 10, min: fitNameMin ?? 10`（`src/ui/PetCardLayout.tsx:145-146`）→ **仍然空转**。

### 6.3 现状与建议

- 现在卡名一律 10px + `compactPetName` + `truncate`，长名字靠截断，不缩字号。
- 要恢复朋友的缩字号，**只改一个数**：`min: fitNameMin ?? 9`（或 9.5），调用方不用动；`fitCardName.ts` 的批量实现保持不动（它已经支持 min < base）。
- 两种口径二选一，需要用户拍：
  - **a 恢复缩字号**：长名字 10 → 9px（0.5 档），不截断；代价是同一行卡片名字大小不一（这正是 466351b 当初要消除的）。
  - **b 维持一律 10px + 截断**：整页字号一致，但长名字被截（`title` 里有全名）。
- 建议：先问用户要哪个，再动那一行；不要顺手改。

## 9. 卡名字号对比：A 现状 10px vs B 恢复 12→9（2026-11-26 追加）

> 用户：「朋友做了自适应，看下效果」。同一批卡、同一排、同一批名字（睡铃雪影娃娃 6 字 / 蒲公英娃娃、白金独角兽 5 字 / 喵喵 2 字对照）。
> 一页看完：[U3-字号对比-2026-11-26.png](preview/U3-字号对比-2026-11-26.png)（375 / 390 两行，A 在左、B 在右，图放大 1.6×）。
> 整屏：`preview/U3-{375,390}-字号-整屏.png`；单排元素图：`preview/U3-{375,390}-字号-{A现状,B恢复}.png`。

### 9.1 浏览器实测字号（`node tools/preview/u3/fit-name-check.mjs`）

| 宽度 | A 现状（10/10） | B 恢复（12/9） |
| --- | --- | --- |
| 375 | 全部 10px | 睡铃雪影娃娃 **11.5px**（12 放不下，按比例缩）、其余 **12px** |
| 390 | 全部 10px | 全部 12px（6 字名 72px，卡内可用 75px，刚好放下） |
| 320（仅验证机制） | 全部 10px | 睡铃雪影娃娃 **9.5px**、蒲公英娃娃 / 白金独角兽 **11.5px**、喵喵 12px |

### 9.2 结论

- **B 的主要效果不是「缩」，是「名字整体从 10px 变 12px」**：375 / 390 的 4 列卡里最长只有 6 字（全图鉴仅「睡铃雪影娃娃」一个），只有它在 375 上被缩到 11.5px。
- **9px 下限在 375 / 390 用不到**：要真正落到 9~10px 档得等卡片更窄（320 屏，或以后改成 5 列）。所以「恢复缩字号」不会出现「9px 小字」的观感，只会让名字统一变大。
- A 现在也**没有截断**：6 字名 10px ≈ 60px < 可用 65~75px（与 466351b 当时「0 张截断」的记录一致）。
- 两边的差别就是**字号（观感）**：B 更醒目，但同一屏所有卡的名字都变大；如果以后有更长的名字（7 字以上）或更窄的卡，B 的缩放才会真正发挥作用。

### 9.3 如果要 B，改动是一行

`src/ui/PetCardLayout.tsx:145-146` 现在是 `base: fitNameBase ?? 10, min: fitNameMin ?? 10`。
- **B（朋友的参数化）**：`base: fitNameBase ?? 12`、`min: fitNameMin ?? 9` —— 名字变大、超宽自动缩。
- **B′（只放开下限）**：`min: fitNameMin ?? 9` 保持 `base ?? 10` —— 视觉上几乎无变化（375/390 没有卡会触发缩放），等于没改。
→ 所以真正的选择是「名字要不要整体变大到 12px」，不是「要不要修复缩字号」。等用户拍。
