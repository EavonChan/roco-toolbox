## 0. 一句话结论

**能跑，且一装就成；但现阶段不该当我们的调度内核——只抄它的三处设计。**
它解决的是"无人值守、接活跑完就退出"的流水线；我们主流程是"人在环里、先审后做"的探索型工作。
真要用，唯一说得通的形态是"外部事件触发器"（GitHub PR/Issue → 起一轮），而不是把 A 的派发搬进 `rules.json`。

三条判断按重要性排：

| # | 判断 | 一句话理由 |
| --- | --- | --- |
| 1 | **不当调度内核** | 会造第二份任务状态（`hub.db`），和 W1 刚定的"看板只读 md、不建第二份状态"直接冲突 |
| 2 | **暂不接入运行** | 我们的活要"先给方案/截图、确认再落代码"；它的强项是"一次跑完再汇报"，硬套等于把先审后做降级 |
| 3 | **抄三处设计** | 四向插件切分 / 事实日志+投影 / 回执协议（`ask/notice/later` + key 去重 + 只重写回执不重做业务）——第三条今天就能用上 |

## 2. 四个问题

### 2.1 内核负责什么、插件负责什么；一条事件到起一个 agent 的链路

**分层是硬的**（`[repo]` = `D:\roco-build\automation\agent-autoloop`）：

| 层 | 文件 | 负责 | 不负责 |
| --- | --- | --- | --- |
| `kernel/` | `decide.ts` `store.ts` `evolve.ts` `cron.ts` `due.ts` `http.ts` `query.ts` `rules.ts` | 决策（给定 view + 一条 input → 要记的事实 + 要给的回答）、追加事实、投影重建、定时索引、接口行为 | 不读系统时钟（`now` 由外面传）、不发网络请求、不碰进程；只有 `node:crypto`/`node:sqlite` |
| `host/` | `runtime.ts` `service.ts` `up.ts` `config.ts` `channels.ts` `plugins.ts` | Node HTTP、SQLite 连接、时钟、配置、插件加载、开机服务 | 不做业务判断 |
| `protocol/` | `schema.json` `validate.ts` `client.ts` | 通信格式、JSON Schema、输入校验、HTTP 客户端 | — |
| `worker/` | `worker.ts` `agents.ts` `contract.ts` `usage.ts` | 领活、启进程、心跳、停止、读回执、用量差量 | 不决定派给谁 |
| `plugins/` | `github` `gitlab` `claude` `codex` `acp` `dsh` `zcode` `command` `feishu` `webhook` `desktop` `delivery` | 四向可替换：**来源**（世界→事件）、**Agent**（起 CLI、解析输出）、**通道**（卡片送达/回收回答）、**交付**（CI/CD 流水线） | 引擎不反过来引插件 |

链路（`kernel/decide.ts` 的 `ingest` / `enqueue` / `claimNext`）：

```
外部世界
  │  ① 定时 cron 到点 │ ② POST /v1/in/<source>（来源适配器验签+翻译）│ ③ POST /v1/events（任意系统，来源密钥）
  ▼
ingest(source, event)            kernel/decide.ts:237
  ├─ events 按 source+key 去重（同 id 再来返回 duplicate，不重跑）
  ├─ 规则匹配：when.source + when.types（支持 x.* 与 *）→ 命中的 rule 列表
  ├─ 暂停的规则不接、只记 paused（恢复不自动补跑，要 replay）
  └─ hops > 8 → 只记事件 + 发"事件循环已停止"卡片，不派活
  ▼
enqueue(rule, event, lane)       kernel/decide.ts:195
  └─ runs 表插一条 state=queued，带 rules_version / lane / group
  ▼
worker 长轮询 GET /v1/work?claim=…&running=…     （50 秒，带心跳）
  ▼
claimNext(worker, claim)         租约 5 分钟；同组同 lane 不允许同时领两轮
  ▼
worker spawn 独立进程组 → POST /v1/runs/<id>/started
  ▼
读 stdout → adapter.read() 解析出 text/session/usage/error/finished
  ▼
POST /v1/runs/<id>/result → finish → applyReceipt
  ├─ 回执里的 ask → 卡片（open）→ 通道送达 → 等你回答
  ├─ later → timers（预约复查，到点派回原 rule/lane）
  ├─ events → 新事件（跳数 +1）
  └─ 都没有 → run.state=done，进程退出
  ▼
你回答卡片 → answer → 新的一轮（lane 不变，resume 原 CLI 会话）
```

内核的一句话边界：**它只做"给定视图和一条输入，决定要记哪些事实"**（`decide.ts` 头部注释），所以同样的输入永远得出同样的结果，能 20 万步模拟、能强杀 1000 次不丢已确认记录。

### 2.2 执行端（agent runner）怎么接，支持哪些 CLI

执行端是**协议**，不是 SDK：能收提示词、能打印最后一条回复的命令行工具都能接。

一个 Agent 插件导出四个东西（`docs/plugins.md` §Agent 插件）：

| 方法 | 作用 |
| --- | --- |
| `command(turn)` | 返回 argv 数组（不做 shell 拼接，`{prompt}` 作为独立参数传） |
| `read(stdout, code, stderr)` | 返回 `text` / `session` / `usage` / `error` / `limitedUntil` / `finished` / `started` |
| `link(session)` | 可选，桌面会话链接 |
| `check(program)` | 可选，`doctor` 问它能不能用 |

内置支持：

| CLI | 接入方式 | 会话续接 | 用量 | access 映射 |
| --- | --- | --- | --- | --- |
| Claude Code | 内置 `claude` | ✅ | Token + 费用 | `plan` / `acceptEdits` / `bypassPermissions` |
| Codex | 内置 `codex`（`codex exec`） | ✅ | Token | `read-only` / `workspace-write` / `danger-full-access` |
| ACP（Gemini CLI、OpenCode、Agentica、agy…） | 内置 `acp` | ✅（`session/load`） | 视 Agent | 同意读/搜 → 同意编辑 → 全同意 |
| **DeepSeek Harness** | 内置 `dsh`，要 ≥0.2.2 | ✅（`--session-id`） | 只 Token，无费用 | `read-only` / `workspace-write` / `danger-full-access` |
| ZCode | 内置 `zcode` | ✅ | 只 Token | `plan` / `edit` / `yolo` |
| 任意命令 | 内置 `command` + `["…","{prompt}"]` | ❌（无 session） | 无 | 不管，进程以本机账号跑 |

`dsh` 插件的实际命令行（`[repo]\plugins\dsh\agent.ts:35`）：

```text
dsh headless --json --permission-mode <read-only|workspace-write|danger-full-access>
             --approval-policy never [--session-id <resume>] <prompt>
```

从 `session` 事件拿会话编号、`status/step_end` 累加 Token、`final` 才算跑完；`--approval-policy never` 意味着**要人批准的调用直接拒绝**，不会挂着等人。

第三方插件：`agent-autoloop add <git 地址>` 克隆到 `~/.agent-autoloop/plugins/<仓库名>`，只克隆、不装依赖、不跑安装脚本。

### 2.3 状态存在哪，能不能被外部只读消费

| 东西 | 位置 | 说明 |
| --- | --- | --- |
| 事实日志 + 投影 | `~/.agent-autoloop/hub.db`（SQLite，`node:sqlite`） | 表：`facts`（只追加）/ `projections` / `projection_meta` / `projection_pending` / `projection_refs`；日志和索引**同一事务**落盘，写完才应答；格式变了从日志重建，不写迁移脚本 |
| 单轮执行 | `~/.agent-autoloop/worker/runs/<run>-<attempt>/{entry.json,stdout,exit}` | 领活先存 entry，结果先落盘再交；进程读不到 ≠ 已退出 |
| 用量 | `~/.agent-autoloop/worker/usage/` | 会话累计值差量，worker 重启不多算 |
| 配置 | `rules.json` / `config.json`（0600）/ `secrets.env` / `master.key` | 规则和密钥分离，外部文字不进提示词 |

**外部只读消费：能，两条路，都要凭据。**

1. **直接只读打开 SQLite**（我实测，写零字节）：`new DatabaseSync(hub.db, { readOnly: true })` →
   `facts: 35 行 / projections: 24 行 / projection_refs: 19 行`，`fact #1 type=rules changes=1`。
   优点：一条 SQL 就能查"这轮为什么跑、结果是什么"（事实里有 `seq`）。
   缺点：`fact` 是内部形状（`type` + `changes[]`），投影表结构随版本变——**能读 ≠ 稳定契约**，契约是 `docs/protocol.md`。
2. **HTTP 只读接口**（要 `owner` 密钥，不是无鉴权）：

| 接口 | 用途 |
| --- | --- |
| `GET /v1/state` | 全局汇总：在跑/排队/等你/今日轮数/Token/费用/最近卡片（我实测 200，返回 `seq`/`totals`/`cards`） |
| `GET /v1/stream` | SSE，按日志序号推（外部看板可以做成"读一次 + 订阅增量"） |
| `GET /v1/runs?rule=…&before=…` | 某规则的轮次分页 |
| `GET /v1/runs/<id>/why` | 单轮时间线（就是 CLI `why` 的数据源） |

结论：**它的状态天生适合被第二个程序消费**（这是它相对我们最大的结构优势）；但"读它的库"和"把它的库当我们的状态"是两件事，见 §7。

### 2.4 触发源有哪些

| 触发 | 怎么用 | 现成实现 | 备注 |
| --- | --- | --- | --- |
| 定时 | `when: { "cron": "0 9 * * *" }` | 内核 `cron.ts` | 错过只补最近一次；暂停期间不跑、不排队 |
| HTTP Webhook | `POST /v1/in/<来源名>` | `plugins/github`、`plugins/gitlab`（HMAC-SHA256 验签） | 需要 `secrets.env` 里的来源密钥；要公网/内网可达 |
| 任意系统事件 | `POST /v1/events` + 来源密钥 | 协议内置，不用写插件 | 事件必须带稳定 `id` 和合法 `type`；带 `cwd`/`agent`/`access` 会被拒收 |
| 手动 | `run <规则>` / `emit <类型>` / `replay <规则> --since` | CLI | `emit --dry-run` 可预演"会派给谁"，不连中台 |
| 回答卡片 | 你选完 → 新的一轮 | 内核 `answer` | 事件类型 `card.answered`，lane 不变、接回原会话 |
| 预约复查 | 回执里 `later` | 内核 `timers` | 到点派回原 rule/lane |
| Agent 自触发 | 回执里 `events` | 内核 `ingest` | 跳数 +1，超过 8 层熔断，人改不了 |
| PR 交付 | PR 打 `deliver` 标签 | `plugins/delivery/poll.ts` | 审查→等 CI→合并→等发布→核对线上版本；只读 `main` 上的配置 |
| 轮询脚本 | `examples/recipes/github-issues/watch.ts` | 示例 | 5 分钟查一次新 Issue（不是内核能力） |
| 消息 | 飞书通道（发卡/回收回答） | `plugins/feishu` | 只做"卡片通道"，不是聊天机器人 |

注意：**没有"用户直接对话"入口**。它是无人值守中台，人只出现在"拍板卡片"上。这跟我们的入口（用户只跟 A 说话）是相反的。

## 4. 我们现有链路是什么

依据：`docs/项目记忆/助理守则.md`（§一/§二/§三）、`docs/任务看板.md`（§五 规则）、`docs/会话台账.md`（§三/§六）。

```
用户（只跟 A 对话；DSH Web GUI 侧栏看会话）
  ▼
A 总调度（助理会话 a4288d1c）
  ├─ 判断：归哪个工作区、会不会踩别人的文件、要不要先审（守则 §一）
  ├─ 拆会话：动 3 个以上文件 / 要连续几小时 → 开新会话（守则 §二）
  ├─ 派发：session_create / session_send，带"只改哪些文件 + 先读哪两份 + 硬规则 + 交付格式"（守则 §三）
  ▼
子会话 P2 / C1 / F1 / M1 / BOT / R（各自一条 DSH 会话，带 skills、白名单、验收命令）
  ├─ 执行：多轮对话 + 工具 + 仓库读写（受会话权限策略约束）
  └─ 产出：代码 / 截图 / 文档 / 报告
  ▼
回信：session_send 回给 A（要求含 证据 / 取舍 / 未知 / 下一会话接什么）
  ▼
A 收口：不信自述，查 commit / 测试 / 文件 / 截图（守则 §一.3）
  ▼
看板：docs/任务看板.md（进行中 / 等你 / 已完成 / 待派，六条更新规则）
台账：docs/会话台账.md（谁能干什么、ID、进度落盘三层）
记忆：docs/项目记忆/{现状,决策,助理守则,用户}.md
```

这套链路真实的强项（不是客套）：

| 强项 | 具体 |
| --- | --- |
| **判断力** | A 读上下文后决定"派给谁、要不要先审、要不要拆"；`rules.json` 式的静态表做不到 |
| **上下文连续** | 一个会话一条线程，改 UI 时能记住上一轮为什么这么改 |
| **收口纪律** | "不信自述、查提交/测试/文件"已经写进守则和看板规则 |
| **人只出现一次** | 用户只跟 A 说；不再被六个会话轮流问 |

它真实的弱项（这次对比才看清楚的）：

| 弱项 | 具体表现 |
| --- | --- |
| **调度不可复现** | 为什么派给 C1 而不是 S3？只在看板留一行，理由在 A 的上下文里，会话一重开就没了 |
| **无队列、无租约** | 派出去就是"等回信"；子会话崩了/卡了，靠 A 巡检或用户问才发现 |
| **无自动重试** | 返工靠 A 手派第二轮（F1 就是这样） |
| **成本不可见** | 看板不记 Token/费用；我这边没有"今天花了多少"的统一口径 |
| **触发只有人** | 只有"用户说话"和 DSH 的定时 prompt；GitHub 开了 PR 不会自动起一轮 |
| **状态非结构化** | md 给人看很好，给程序读很差；会话记录是 zstd 压缩，要按 ID 解压 |

## 5. 对照表

| 维度 | 它有的（Autoloop） | 我们有的（A + DSH 会话） | 两者差异（对我们要害） |
| --- | --- | --- | --- |
| **触发** | cron、HTTP webhook（GitHub/GitLab 验签）、`POST /v1/events`（任意系统）、手动 `run/emit`、卡片回答、`later` 复查、回执发事件（≤8 跳）、PR 标签轮询 | 用户说话；DSH 定时任务（把一条 prompt 定时投到会话）；小阿布 QQ 消息（业务功能，另一套） | 它面向"外部世界推活"，我们面向"人开口"。**外部事件是我们唯一的真缺口** |
| **调度** | 规则表 `rules.json`（source+type → agent/cwd/lane/parallel/maxActive）+ 内核匹配 + 队列 + 租约 ;暂停/补跑/重放 | A 读上下文后手动派发（`session_create`/`session_send`），分工写在 `docs/会话分工与巡检机制` 与台账 | 它的调度**可复现、可审计、无人值守**；我们的调度**灵活、能处理模糊需求**，但不可复现、不能无人值守 |
| **执行** | worker 领活 → 独立进程组 → CLI 一轮跑完退出；`resume` 接回原会话；四档 access 映射到 CLI 参数 | DSH 会话内的 agent（多轮对话、上下文连续、带 skills 与工具），一个工作区一个会话 | 它是"一次性进程"，我们是"长会话"。**等待时零消耗**是它的独有优势；**多轮打磨**是我们的独有优势 |
| **状态存储** | SQLite `hub.db`：只追加 facts + 投影，同事务；worker 本地 runs/*/entry.json；可从日志重建 | `docs/*.md`（人写、git 版本化）+ DSH 会话日志（zstd）+ 台账；无事件表、无 run 表 | 它是**日志（可追溯、可重建、可机读）**，我们是**文档（可读、可改、可评审）**。我们想结构化就得新造一份，正好撞上 W1 的"不建第二份状态" |
| **回信** | 卡片投递到通道（桌面/飞书/钉钉/企微/Slack/Discord），长轮询领卡、送达回执、回答回调；**回执协议**：Agent 最后一条回复里一段 `agent-autoloop` 标记的 JSON 块（`ask`/`notice`/`resolve`/`later`/`events`）；等你期间进程退出，回答后接回原会话 | 子会话 `session_send(reply:true)` 回给 A，自由文本 + 证据/取舍/未知；要用户拍板时 A 用 `ask_user_question` 或直接在对话里问；看板记"等你" | 我们的回信**靠人读**，它的回执**靠程序核对**（key 去重、同 token 同内容只确认一次、写错只重写回执不重做业务）。这条我们可以直接抄 |
| **失败重试** | `attempts` 1..10，退避 `5min × 2^(n-1)` 上限 60min；用量到限 → 到重置时间前不派活并发一次通知；worker 掉线 10min 发卡片；租约 5min 判 `unknown`（迟到结果照收）；停止有 `cancel_at`；连续 3 次失败通知你 | 靠 A 收口时发现 → 手派返工；会话本身能续聊；没有退避、没有上限、没有掉线告警 | 它的失败是**状态机**，我们的失败是**人的注意**。差别不在"能不能修"，在"谁先发现" |
| **可观测性** | `why <轮次>` 逐轮时间线；`runs` 分页；`status` 今日/7 日轮数+Token+费用；`/v1/stream` SSE；20 万步模拟 + 强杀 1000 次 + 一致性测试 | 看板一张表（人维护）、台账、DSH 会话列表/搜索；没有逐轮追溯、没有成本口径 | 它的"为什么跑了这一轮"是一条命令；我们的"为什么"要翻会话记录 |

表外两条，我认为也重要：

| 维度 | 它 | 我们 |
| --- | --- | --- |
| **权限闸门** | `access` 映射到 CLI 参数（`read`/`edit`/`full`），`askFirst` 只是提示词里的建议，**内核不强制**"删数据/停服/花钱先问" | 会话级 DSH 权限策略 + 守则 §四（四类动作必须问）+ 用户雷区。闸门在**人和规范**上，不在代码里 |
| **并发与隔离** | 同组同 lane 串行、`parallel` 按 subject 分 lane、`maxActive` 限并发；一机多 worker 可分布 | 一个工作区一个会话，并行靠"开多个会话"；文件冲突靠白名单（§3 冲突防火墙） |

## 6. 差异的根源（三条）

1. **谁做调度决策**：它是"声明式规则 + 算法"，我们是"人读上下文 + 判断"。前者可复现、可审计、能无人值守；后者能处理"需求还没说清"的情况。我们的活大半属于后者。
2. **状态是日志还是文档**：它的一切从只追加日志长出来，所以能重建、能追溯、能被程序读；我们的状态是给人看的 md，可读可改可评审——两者服务的对象不同，不是先进落后。
3. **执行单元是进程还是会话**：它一轮一个进程，"等待时不占进程、不花 Token"；我们是一条会话，"上下文连续、能来回打磨"。它省的是等待成本，我们省的是重述成本。

## 7. 结论：值不值得引入、接在哪一层

### 7.1 当调度内核：**不建议**

四条理由，按分量排：

1. **第二份状态**。它的权威状态是 `hub.db`；我们的权威状态是 `docs/任务看板.md` + 台账。一旦它的 run 状态成为"任务到哪一步"的另一个答案，看板一定漂。而 W1 刚定下的原则是"只读 md、不建第二份状态"——这条不能自己先破。
2. **我们的活是"人在环里"的**。UI 先审后做、四类动作先问、验收看截图——这些要求"跑之前停一下"。它的设计目标是"跑完再汇报"，把"先审"塞进 `askFirst` 提示词等于把闸门降级成自觉。
3. **权限闸门不对应**。它的 `access=full` 就是 `danger-full-access`，没有"打包/发版/删除"这几类动作的拦截；我们靠的是守则 + 用户雷区 + A 的把关。换内核等于把闸门从"人"搬到"提示词"。
4. **规则表跟不上动态分工**。P2/C1/F1/M1/R 是按"谁熟、谁有空"轮转的，`rules.json` 是静态表；维护它、跟看板对齐的成本会超过省下的判断。

### 7.2 当事件源：**可选，且只值一小块**

我们唯一真缺的是"外部世界主动推活"。这块它现成，但整套引入不划算；三种形态成本对比：

| 形态 | 做法 | 成本 | 收益 | 判断 |
| --- | --- | --- | --- | --- |
| A. 整套 autoloop | 常驻服务 + `rules.json` + 只读巡检 Agent | 高（第二套运行时、第二份状态、开机任务） | 外部触发 + 去重 + 重试 + 卡片，全都现成 | ❌ 现在不值 |
| B. 最小事件桥 | ~100 行：一个本地 HTTP 收 GitHub webhook（验签）→ `session_send` 给 A 或新会话 | 低（一个脚本 + 一条规则） | 只解决"PR/Issue 开了自动起一轮" | ⭕ 将来首选 |
| C. 不做 | 继续靠人看到 PR 再派 | 0 | 0 | ✅ 现在够用 |

**再评估的触发条件**（满足任意两条再做）：
1. 连续两周，每周都有 ≥3 次"外部事件本该自动起一轮"的情况（PR 开了、CI 红了、Issue 来了）；
2. A 需要"无人值守过夜"跑巡检/早报（比如每天 8 点自动出一份仓库风险摘要）；
3. 需要"等你拍板但不想占着会话"的卡片化待办（发版前 checklist）超过 1 个。

到那时也**先做 B，不做 A**：桥能接进现有看板，不需要第二份状态。

### 7.3 只抄它的插件设计：**建议，且分三档**

| 抄什么 | 落到哪 | 收益 | 什么时候做 |
| --- | --- | --- | --- |
| **回执协议**：子会话最后一段固定 JSON（做了什么/证据/待决定/未知），A 机械核对；写错只重写回执、不重做业务 | 派发模板（守则 §三）+ 会话开工卡 | A 收口从"读散文"变成"对字段"；返工只返错的部分 | **现在就能做**，成本最低 |
| **四向切分**（来源/执行/通道/交付） | 用来体检我们自己的"会话类型"是否该收敛成接口（P/S/R/BOT），**先写文档不写代码** | 派发模板可以按"来源"分类（人/定时/外部），少拍脑袋 | 下一轮分工调整时 |
| **事实日志 + 投影** | 如果将来要给看板做"结构化进度"，照这个形状设计（只追加 + 可重建），而不是先上 SQLite 表 | 避免"状态表"变成第二个真相 | 看板 W1 要动数据模型时 |

## 8. 不做什么（防止为了接而接）

1. **不装成常驻/开机自启服务**。`init` 不带 `--no-service` 会 `Register-ScheduledTask` 注册登录启动任务——这是改系统，不属于这轮授权。
2. **不把 `hub.db` 接进看板或 W1**。那是第二份任务状态；看板只读 md 这条不破。
3. **不把 A 的派发改成 `rules.json`**。不搞双调度：一处人在派、一处规则在派，看板就没人敢信。
4. **不让它的 worker 碰仓库写权限**。`access` 只用 `read`；不接 `edit`/`full`，不接改代码、提交、发版。
5. **不接打包/部署/删除/改界面**。这四类动作在它那里没有闸门，只有提示词；接了就等于绕过守则 §四。
6. **不接飞书/钉钉/企微通道**。没有账号体系，而且回答链接要 `hub.publicUrl` 能被手机打开——我们本机没有公网入口。
7. **不为它改 DSH profile / 全局依赖 / PATH**，也不 `npm install -g`。
8. **不做双跑对比**（同一任务两套调度各跑一遍）。只会让看板更乱，且烧两份 Token。
9. **不因为"装都装了"就留着跑**。已停；要再跑就重新 `up`，用完停。
