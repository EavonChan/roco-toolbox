# 方案 · 页面区块化与「可回退」（2026-11-28）

> 起因（用户原话）：
> 「我们的项目从一开始到现在已经发生过很多颠覆性的变化了，所以我期望后面尽量做到，新增小功能时能加到合适的位置，如果不好，可以随时去掉，回到以前的一个稳定页面。」

## 一句话

把每个页面从「一个大组件」改成「**一串可插拔的区块**」：新功能 = 加一个区块（或加一项到配方里），不要了就删那一项，页面自动回到上一个稳定组合。

## 现状问题（为什么现在做不到「随时去掉」）

| 现象 | 后果 |
| --- | --- |
| 页面是一个 500~1500 行的组件，区块之间共享局部状态 | 删一块要动周围几处，容易连带坏掉 |
| 排版写死在 JSX 里（`text-[10px] px-3 rounded-lg`） | 没有「区块」边界，视觉也改不动 |
| 新功能常常"就地改"老区块 | 想回退只能靠 git revert 整个提交，会带走同一提交里的别的东西 |
| 没有"当前稳定版"的显式定义 | 没人说得清"回到哪个版本" |

历史证据：个人主页在 4 天内出了 4 版（P1 列表 → P2 四宫格 → P3 大卡+宫格 → P4 新鲜度卡），每版都是**重写页面组件**，而不是换配方。

## 设计

### 1. 三层结构

```
页面（Page）      = 配方（recipe）        —— 一个数组，决定"放哪些块、什么顺序"
区块（Section）   = 独立组件 + 元数据      —— 自己管数据、空态、开关
原语（Primitive） = Card / Row / Chip …   —— 只认 tokens，不认业务
```

关键技术点：**区块之间不共享可变状态**。需要联动时通过页面级 context（只读 + 回调），不直接互相引用。

### 2. 区块的元数据（决定它能不能被安全摘掉）

```ts
// src/ui/sections/types.ts
export interface SectionDef {
  id: string;                       // 稳定标识，配方和开关都用它
  title: string;                    // 用于设置页/调试面板
  render: ComponentType<SectionProps>;
  /** 什么时候出现；返回 false 就不渲染（也不占高度） */
  when?: (ctx: PageContext) => boolean;
  /** 数据依赖：页面只在需要时才去取，摘掉这块就不再请求 */
  needs?: Array<'account' | 'groups' | 'eggs' | 'nearby' | 'demands'>;
  /** 实验开关：新功能默认 off，验证后再默认 on */
  flag?: string;
}
```

### 3. 配方（这是「回退」的抓手）

```ts
// src/ui/sections/recipes/profile.ts
export const PROFILE_STABLE_V1: SectionDef[] = [
  SECTIONS.accountCard,
  SECTIONS.collectActions,
  SECTIONS.nearbyTargets,
  SECTIONS.groupsList,
  SECTIONS.settingsList,
];

// 新方向：只改这个文件，不改组件
export const PROFILE_V2: SectionDef[] = [
  SECTIONS.freshnessCard,      // 新增块
  SECTIONS.collectActions,
  SECTIONS.todayTasks,         // 新增块
  SECTIONS.nearbyTargets,
  SECTIONS.settingsList,
];

export const PROFILE_ACTIVE = PROFILE_STABLE_V1;  // ← 一行切换
```

**回退操作 = 把 `PROFILE_ACTIVE` 改回上一行，或者把某个区块从数组里注释掉。**
不需要 revert 提交、不影响别的页面、其它会话的改动也不会被带走。

### 4. 三个保证（让"随时去掉"真的成立）

| 保证 | 怎么做 |
| --- | --- |
| **删得掉** | 每个区块有独立测试：只挂它一个也能渲染、断数据时不炸、`when=false` 时不占高度 |
| **不互相拖累** | 区块间禁止直接 import 彼此；共享数据走 `PageContext` |
| **删了页面还是对的** | 配方层测试：给定任意子集（含空数组），页面都能渲染出合理空态 |

### 5. 迁移顺序（不要一次改全站）

```
第 1 步  先做原语层：tokens + 6 个基础组件（Card/Row/Chip/Section/Skeleton/EmptyState）
第 2 步  抽「我的」页 → 5~7 个区块 + 配方；做出 PROFILE_STABLE_V1 快照
第 3 步  用同一套重做 V2；对比截图；选定后把 PROFILE_ACTIVE 切过去
第 4 步  验证一轮：删掉一个区块、加回一个区块、切换配方，页面都不崩
第 5 步  推广到「收集 / 家园 / 附近 / 换蛋」（按页面复杂度排）
```

**第 2 步之前不要碰别的页**——先在一页上把模式跑通。

## 与设计系统的关系

区块化解决"结构可回退"，设计系统解决"视觉一致"。两者必须一起做：

```
tokens  →  原语（Card/Row/Chip）  →  区块  →  配方  →  页面
```

如果只做区块不做 tokens，每个新区块又会带一套自己的字号间距，等于把"脏"分散到更多文件里。

## 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 过度抽象 | 为了"可插拔"把简单页拆成 20 个文件 | 一个页面最多 8 个区块，超了就说明该分页 |
| 配方分叉 | 同时存在 V1/V2/V3 三份配方，谁也不知道线上是哪个 | 只允许 **1 份 active + 1 份 candidate**，其余删掉 |
| 性能 | 区块多了包变大 | 区块按需 import；首屏只加载首屏区块 |
| 状态共享 | 联动需求（如"切角色后蛋仓要刷新"）被禁止互相引用 | 走 `PageContext` + 显式事件，不隐式依赖 |

## 验收标准（做到这四条才算落地）

1. 「我的」页由 **≥5 个独立区块**组成，每个区块单独有测试；
2. 从配方里删掉任一区块，`npm test` 仍全绿、页面仍可用；
3. 存在 `PROFILE_STABLE_V1`，且**切到它只需改一行**；
4. 每个区块的间距/字号都来自 tokens，页面里**不出现** `text-[10px]` 这类硬编码。
