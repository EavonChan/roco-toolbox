# 多会话协作实践（可迁移版）

> 2026-11-22 整理。从一个真实项目里跑出来的做法，去掉项目细节后可以直接搬到别的仓库。
> 核心一句话：**把"一个长时间对话"换成"一个总调度 + 若干短命执行窗口"，用四份活文档当共享内存。**

## 一、为什么需要它（三个失败模式）

| 失败模式 | 表现 | 根因 |
| --- | --- | --- |
| **长会话崩** | 聊到几十轮后变笨、变慢、开始忘事、忽略之前的约定 | 上下文塞满，压缩后细节丢失 |
| **单窗口干所有事** | 改 A 功能时把 B 的文件带改，两件事互相覆盖 | 没有文件边界，也没有并行 |
| **交接靠记忆** | 新会话不知道"昨天为什么这么定"，于是重做或推翻 | 决策只存在于对话里，没有落盘 |

三条对应三个动作：**拆会话 / 划文件所有权 / 写决策记录**。

## 二、结构

```
        你（人类，单一入口）
              │
              ▼
     ┌─────────────────┐
     │  A 总调度        │  ← 只做协调、把关、决策、发版
     └─────────────────┘
        │      │      │
        ▼      ▼      ▼
      P2     C1     S1…S6    R（审查）   BOT（运维）
        └── 各自短命：干完一件就回信、然后休眠 ──┘
                        │
                        ▼
              需要时再派子代理（一次性、隔离上下文）
```

**两条铁律**：

1. 人类只跟 A 说话。要动手的事由 A 判断开哪个窗口、写清边界，再派出去。
2. 执行窗口之间不直接对话，全部经过 A 转达——否则就是第二个单窗口问题。

## 三、四份共享内存（这是最关键的部分）

放在仓库里，跟着代码走，不像聊天记录一样会丢。

| 文件 | 回答什么问题 | 更新时机 | 建议长度 |
| --- | --- | --- | --- |
| `现状.md` | 现在是什么版本、部署在哪、谁在改什么、有什么坑 | 每次巡检 / 发版 | ≤100 行 |
| `决策.md` | **为什么现在是这样做**、否掉过什么方案 | 做决定当天 | 每条 5 行 |
| `用户.md` | 决策者怎么说话、雷区、节奏、验收方式 | 观察到就补 | ≤80 行 |
| `守则.md` | 助理怎么干活：何时开会话、何时必须问 | 流程变了就改 | ≤60 行 |

### `决策.md` 的条目格式（照抄）

```markdown
## YYYY-MM-DD · 一句话决定
- **决定**：
- **被否掉的替代方案**：
- **为什么**：
- **影响面**：
```

为什么要写"被否掉的替代方案"：三个月后不会有人重新提议同一个方案；
为什么写"影响面"：改回来时知道要动哪些地方。

### `用户.md` 必须有的四块

沟通方式（长短、结论先行还是过程先行）、决策风格（几个选项、要不要推荐）、
雷区（说一次就够的那些）、节奏（什么时候在线、验收看什么）。

> 这一份是给"下一个 AI"看的，不是给人看的。写具体行为，不写性格评价。

## 四、会话台账（登记表）

一张表管住所有窗口：

| 代号 | **说人话的名字** | ID | 状态 | 产出 |
| --- | --- | --- | --- | --- |
| A | 总调度 | a4288d1c | 运行中 | — |
| C1 | 改收集页 | f614095a | 运行中 | 方案图、实现 |
| R | 审代码 | 3b5b7bd0 | 运行中 | 审查报告 |

再加一张**「我想干什么 → 找谁」**的索引表，人类不用记 ID：

| 我想…… | 找谁 |
| --- | --- |
| 改 X 功能 | C1 |
| 发版 / 回滚 | A |
| 代码审查 | R |

## 五、文件所有权（防冲突的核心）

每个执行窗口开工时，必须拿到一份**文件白名单**：

```
只改：src/ui/MotherView.tsx(+test)、src/ui/plan/*（两个文件）
禁区：src/domain/*、src/ui/Dashboard.tsx —— 要动先停下来问
```

三条规则：

1. **一个文件只能有一个所有者**。同一个文件被两个窗口改，必然互相覆盖。
2. **跨两个工作区改同一页 → 开一个窗口，不要开两个**。（真实教训：收集页的入口和内容分属两个模块，分两个窗口改必定打架。）
3. **改别人的文件要先报**，不要"顺手"。

## 六、交互协议

### 什么时候必须问人类（只有三种）

1. **不可逆**：打包、删除、发版、改全局配置（插件、技能、profile）。
2. **口径不明**：产品行为有两种合理解释，猜错会返工。
3. **范围扩张**：做 A 时发现 B 也该改 —— 先报，不顺手做。

其余全部自己定：文件放哪、命名、跑哪些测试、用哪个模型、文档写多细。

### 汇报五段式（单条消息不超过一屏半）

```
一句话结论
做了什么（表格 ≤5 行）
证据（命令 + 关键输出 ≤10 行）
需要你决定/做的（≤3 条，标推荐）
风险或回滚方式（有才写）
```

### 结论落盘

**只在对话里说过的，不算数。** 每轮结束把结论写回 `现状.md` / 台账；
执行窗口干完活，必须"回信"给总调度（不是等人来问）。

## 七、命名规范（人类可读优先）

- 格式：`【代号】动词开头的短句`，6–10 字。
- **反例**（需要解码）：`原型基准重建阶段0`、`收集页改造与方案梳理`
- **正例**：`【P2】照线上做原型稿`、`【C1】改收集页`、`【BOT】维护小阿布`
- 不带状态（状态会变，名字不跟着变）、不带"阶段/梳理/重建"这种内部词。
- 自检：这句话念给不在项目里的人听，他能不能猜出在干什么。

## 八、工具层（以 DSH 为例）

需要的**能力**（换任何工具都对应得上）：

| 能力 | 用途 | DSH 对应 |
| --- | --- | --- |
| 列出所有会话 | 巡检、找窗口 | `session_list` |
| 读某个会话最近消息 | 知道它做到哪了 | `session_read` |
| 给会话投一条消息 | 派活、催进度、回信 | `session_send`（`reply: true` 要求回信） |
| 新建会话并带首条任务 | 开新窗口 | `session_create`（可指定标题/目录/预设） |

DSH 上装两个插件即可（装完**必须重启**）：

```sh
dsh plugin --profile <名字> add @laoyuehanni/dsh-session-tools      # 读写/发送/新建
dsh plugin --profile <名字> add @deepseek-ai/dsh-experimental-session-search   # 只读检索
```

**不要**用脚本直接去解压会话日志——那会绕过授权与压缩层（官方明确不建议）。
没有插件时，退化成"人工复制粘贴"也能跑，只是累。

## 九、第一周怎么搭（三天）

| 天 | 做什么 | 产出 |
| --- | --- | --- |
| 第 1 天 | 建四份共享内存 + 台账 + 在 AGENTS.md 顶部加"开工清单" | 四份文档、一条清单 |
| 第 2 天 | 拆出**一个**执行窗口，完整跑一遍"派活 → 它干 → 回信 → 你验收" | 一次闭环 |
| 第 3 天 | 加闸门：合并/发布前的预检脚本 + 采纳记录 | 一个脚本、一份记录 |

先只开 2~3 个窗口。**同时跑超过 4 个**，人的注意力会成为瓶颈，冲突也会变多。

## 十、踩过的坑（都是真的）

1. **"零冲突"比冲突更危险**：两个分支合并显示无冲突，但结果覆盖了 120 个文件——因为一方把自己的版本"解决"进去了。合并前要看 diff 规模，不只看有没有冲突。
2. **交接文档的数字会漂**：昨天写的"32 个提交差、18 个冲突"，今天变成"1 和 0"。所有统计都要带命令，引用前重跑。
3. **分支保护对管理员无效**：不勾 "include administrators"，自己照样能直推，保护等于只防外人。
4. **中文路径会打断构建**：某些原生工具链不认非 ASCII 路径，要在英文路径开 junction 再构建。
5. **依赖会莫名消失**：`node_modules` 被别的窗口清空过一次，跑测试前先确认关键包还在。
6. **删东西前先备份成引用**：删除前用 tag / stash 快照留一份，比"我记得改了什么"可靠。
7. **规则写在对话里等于没写**：同一条协作约定，写进仓库文档后朋友那边的 AI 才开始遵守。
8. **给建议要"双向"**：单向的约束读起来像防范，对方不会配合；写成"你能得到什么 + 我们会做什么"才推得动。
9. **提交必须带路径**：多个窗口共用一个工作区时，`git commit` 会把别人**已暂存**的改动一起带走。一律用 `git add <路径>` + `git commit -m "…" -- <路径>`，或者每个窗口一个 worktree。

## 十一、判断表：什么时候开新会话

| 情形 | 处置 |
| --- | --- |
| 新功能 / 改行为，动 3 个以上文件 | 开新窗口 |
| 只改文档、台账、决策记录 | 总调度自己写 |
| 单点修复（1–2 文件，有明确报错） | 派子代理或自己做 |
| 跨两个模块改同一页 | 开**一个**窗口 + 白名单 |
| 要连续几小时、产出大量文件 | 开新窗口 |
| 需求没边界 | 先问清，再决定开不开 |

判断标准只有一条：**这件事会不会把总调度的上下文吃掉、或需要多轮试错**。会，就派出去。
